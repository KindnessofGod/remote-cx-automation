# DEPLOY 2026-08-31 — UC-05's three terminal Zendesk nodes

**Workflow `WORKFLOW_UC05_ID` — "RCX UC-05 🟡 Resignation Notice Calculation". Three `n8n-nodes-base.zendesk` "update
ticket" nodes.** Not deployed by this pass; this is the paste-ready target.

## Why this exists

A Zendesk node carries no `jsCode`, so `npm run verify-deployed`'s body diff
is **structurally blind** to it and `test/n8nUc05TerminalZendeskNodes.test.js` cannot see it either
(parity compares DECISIONS — a node that reaches the right verdict and describes
it in false words passes every time). The prose on these three nodes was typed
once into a node parameter, written onto real customers' tickets, read back by
no check and versioned by nothing.

The note is now composed in `workflows/nodes-uc05/noticePeriodGates.js` — a
file `verify-deployed` **does** diff byte for byte — and these nodes only
interpolate it. Same split as UC-01 and UC-04.

## Order of operations, and it matters

1. **Deploy the gates Code node first.** `noticePeriodGates.js`'s
   `composeInternalNote()` is what `internalNote` interpolates. Publishing
   the Zendesk nodes first leaves them dereferencing a field nothing produces,
   which renders as an **empty string on a fully green execution** — the ticket
   would get the routing sentence and nothing else, and every layer would report
   success. `npm run deploy-node` publishes one Code node from its file.
2. **Then the three Zendesk nodes below**, by hand in the editor or by
   `PUT /api/v1/workflows/WORKFLOW_UC05_ID`. Remember §6: a REST `PUT` **publishes in
   place**; the MCP `update_workflow` writes only a draft. Whichever you used,
   check `activeVersionId === versionId` — that comparison is the only thing
   that answers "is this live?".
3. **Read the deployed bodies back and diff them** before trusting a success
   flag, then drive one real, unpinned execution and read the NODE statuses and
   the ticket's rendered comment — never the run status.

## What NOT to change while doing this

`tags` on the **Escalate** and **Unrecognised** nodes carries
`={{ $('Assign Routing').item.json.routing.queueTag }}`, which is
rca-iih7 / D-14's fix and is owned by
`workflows/nodes/escalationQueueTagSpec.js`. It is reproduced in the blocks
below so they can be pasted whole. **Do not drop it**: without it the ticket
claims a queue tag it never receives, and the owning team's Zendesk view is
empty. The two specs are held equal by a cross-spec test — if you edit one, edit
both, in one change.

## The three blocks

Each is the complete `parameters.updateFields`. `authentication: "oAuth2"`,
`operation: "update"` and
`parameters.id: ={{ $('Notice Period Gates').item.json.externalRef }}`
are unchanged and are listed in `workflows/nodes-uc05/terminalZendeskNodesSpec.js`
rather than repeated here — a spec that cannot be pasted gets hand-assembled,
which is how the prose these nodes carried got there.

**These blocks are read by `test/n8nUc05TerminalZendeskNodes.test.js`**, which parses them out of this
file and asserts they equal the spec. A paste-ready block that has drifted from
the checker is worse than none: an operator follows it and `verify-deployed`
then reports the drift they were told to create.

### `Flag Awaiting HR Ops Sign-off`
**Two changes, and the second is not prose.**

1. `internalNote` — retires *"AI prepared discrepancy report … **No Remote
   write exists for resignations** — the signed-off report IS the durable
   artifact."* That sentence is a claim about **Remote's platform** that
   `docs/use-cases/UC-05.md` §1 **retracted on 2026-08-21**:
   `PUT /v1/resignations/{offboarding_request_id}/validate` exists, scope
   `resignation:write`, and the boundary is a **policy choice**. The behaviour
   does not change — this system still writes nothing — only the stated reason.
   *"AI prepared"* goes too: this graph has 16 nodes and one http call, to
   Remote, and no LLM node at all. *"discrepancy report"* goes because this node
   is reached **only** when there is no discrepancy.

2. `status`: `pending` → **`open`**. Zendesk `pending` means *waiting on
   the requester*; the requester is the resigning employee, who has nothing left
   to do, and the work is with **HR Ops**. UC-06's and UC-09's equivalents are
   already `open` — UC-05 was the outlier. Leaving it stops the requester-wait
   SLA clock and exposes the ticket to any *"auto-solve pending after N days"*
   business rule on the account.

No queue tag here: `isEscalation('prepared_for_signoff')` is false, so
`routingTag` already **is** the queue tag.

### `Escalate Resignation Ticket`
Retires *"AI summary — ESCALATED: … **No report was prepared for sign-off**."*
That is true of six of the eight escalate reasons and **misleading for two**: on
`statutory_discrepancy` and `pto_balance_unusable` the notice period is fully
computed before the branch and `Create Resignation Record` writes the
`notice` and `payout` columns on **every** decision. The figures are durable
and in the row; what is absent is the sign-off **path**. Those are exactly the
two escalations where the specialist most needs to know the arithmetic is
already done.

## After deploying

- `npm run verify-deployed` — 0 drifted, and note it **exits 2, never 0**, when
  it cannot reach n8n, so its silence is never a pass.
- Drive one real, unpinned execution per branch and **open it**: read each
  node's status and the ticket's **rendered** internal note. A green run proves
  nothing on its own — a pinned node reports success having done nothing, and a
  dereference of a missing field renders empty on a fully green execution.
- Check one real ticket's `status` field is `open` after a sign-off run. That
  is the one change here a reader of the note cannot see.
