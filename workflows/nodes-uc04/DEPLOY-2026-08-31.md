Everything below is prepared, tested and **not deployed**. `WORKFLOW_UC04_ID`
was read live on 2026-08-31 (17 nodes, `active: true`,
`versionId === activeVersionId === 50e33f3c-23bc-4e1c-b1d3-016751e57744`) and

Read `CLAUDE.md` §7b before doing any of it. The two rules that matter here:
`PUT /api/v1/workflows/{id}` **publishes in place** (the MCP `update_workflow`
only drafts), and the only thing that answers "is this live?" is
`activeVersionId === versionId` read back afterwards.

### Why the note moved into the Code node

Because a note typed into a node parameter is versioned by nothing. This one

now composed in `workationGates.js`, which `verify-deployed` diffs byte for

## Change 3 — the intake trigger's loop guard, RECOMMENDED, SEPARABLE

**Measured 2026-08-31, live.** UC-04's intake trigger `99900000000009` fires
on `current_tags includes uc04_test` AND `custom_fields_9990000000001
present` AND `current_tags not_includes "uc_processed uc01_auto_resolved
verification_exception"`. Nothing sets `uc_processed`: grepped across all nine
deployed graphs, **0 occurrences**. The loop guard exists on all nine triggers
and is fed by nothing.

So this graph's own terminal Zendesk write re-satisfies its own trigger and
re-fires the workflow. Harmless durably — `Claim Ticket (Idempotency)`
conflicts and the redelivery stops at `Duplicate Delivery — Stop` — which is
why nothing has ever gone red. Not free: `Fetch Employment (Remote)` runs
**before** the claim and carries no `onError`, so once the employment id ages
out, the next comment anybody adds to a long-finished ticket produces an
errored run, an `ops_alerts` row and a Telegram push.

**If applied, apply to all four**, or the other three branches keep re-firing
and the half-fix reads like a whole one:

| node | add to `updateFields.tags` |
|---|---|
| `Flag Awaiting Specialist Approval` | `uc_processed` |
| `Flag Blocked Workation` | `uc_processed` |
| `Escalate Workation Ticket` | `uc_processed` |
| `Unrecognised Workation Decision` | `uc_processed` |

**The risk, stated:** `uc_processed` sits in all nine triggers' `not_includes`,
so a ticket carrying it is excluded from every intake, not just UC-04's. Only
reachable for a ticket also carrying a second `uc0N_test` tag, which nothing
produces today — but UC-03 routes work on to UC-04, and if that hand-off ever
becomes tag-driven this is what would silently drop it.

## What is NOT in this deploy, and why

**No new node, no new branch, no graph-shape change.** See `docs/BUILD-LOG.md`
§3.109 for the argument. In short: the graph cannot reach an employer approval
even in principle (`Claim Ticket (Idempotency)` claims `(UC-04, ticketId)` on
the intake run, so the re-fire an approval causes dies at the NoOp), and
moving a branch upstream of the claim to get round that is the shape that
produced 21 duplicate customer replies on UC-01. The stage-3 hand-off already
happens synchronously in `handOffToMobility()` (`src/remoteui/server.js`),
after both durable writes, with its own failure audited and reported to the
manager in the HTTP response — an n8n leg would be a slower, less reliable
second copy.

## Proving it afterwards

`uc04_test` currently matches **0 tickets** on `your-subdomainhelp` (measured
2026-08-31), and all 20 real UC-04 tickets are portal-raised and carry `uc04`,
not `uc04_test` — so nothing will drive this graph on its own. To prove the
deploy, raise one ticket carrying `uc04_test` **and** the employment field
`9990000000001`, then read the ticket's internal note back rather than the
run status. Expect exactly two executions: one that writes, and one that stops
at `Duplicate Delivery — Stop` (or one only, if change 3 was applied).
