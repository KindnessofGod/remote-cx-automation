# UC-02 live-graph deploy — 2026-08-31, `Expense Gates` + all five terminal Zendesk nodes

Everything below is prepared, tested and **not deployed**.

`WORKFLOW_UC02_ID` was read live on 2026-08-31 (30 nodes, `active: true`,
`versionId === activeVersionId === fe90bbff-c0cf-4fdb-8554-9b70c54858bf`) and
the five nodes' parameters quoted as "old" below are that capture, verbatim.

Read `CLAUDE.md` §7b before doing any of it. The two rules that matter here:
`PUT /api/v1/workflows/{id}` **publishes in place** (the MCP `update_workflow`
only drafts), and the only thing that answers "is this live?" is
`activeVersionId === versionId` read back afterwards.

**Order is not optional.** Change 1 (the `Expense Gates` body) must land first.
All five node changes interpolate `internalNote`, and `Resolve Expense Ticket`
also interpolates `customerReply` — neither field exists until the updated gates
body is deployed. Deploying the nodes first would give every ticket an internal
note consisting of the routing sentence and nothing else, **and would send the
customer an empty public reply**, on a fully green execution with nothing red
anywhere. An n8n expression that dereferences a field nothing produces renders
as an EMPTY STRING.

## Why all five change at once

None of these nodes carries `jsCode`, so `verify-deployed`'s body diff is
structurally blind to them. The prose they write onto real customers' tickets
was typed once into a node parameter, versioned by nothing and read back by no
check. `test/n8nUc02Parity.test.js` cannot see it either: it compares
DECISIONS, and a node that reaches the right verdict and describes it in false
words passes it every time.

What the retired sentences got wrong is enumerated with its evidence in
`workflows/nodes-uc02/terminalZendeskNodesSpec.js`'s header. In one line each:

| node | retired sentence | what is wrong with it |
|---|---|---|
| `Escalate Expense Ticket` | "No auto-approval issued." | **misleading for 3 of the 6 reachable escalate reasons.** All three Remote reads carry `onError: continueRegularOutput`, so `upstream_unavailable` and `upstream_record_not_found` are genuinely reachable, and `GATE_SEQUENCE` says of them *"this expense was never evaluated. **Nothing has been decided about it either way**."* Same for `identity_not_verified`. Saying "no auto-approval issued" about a claim nobody assessed implies an assessment ran and came back negative. |
| `Unrecognised Expense Decision` | "Routed to a human rather than dropped." | true at the Zendesk layer and **directly contradicted by the sidebar**. `src/uc02/reviewPolicy.js:196` refuses any row whose `decision !== "human_review"` with *"it was never routed to Finance Ops, so it has no review path here."* One ticket, two surfaces, opposite claims. |
| `Flag Blocked Expense` | "This claim was blocked, not approved." | not false, and one sentence short. The ticket is assigned to the owning team while nothing on it is open to that team's approve or decline — the sidebar says so and the ticket did not. |
| three of the five | "AI summary — …" | UC-02 **does** have a real LLM node, so "AI" is defensible in a way it is not on UC-07 — and it is still wrong per node: FALSE on `Flag Blocked Expense` (both blocked reasons are decided at gates 5–6, before gate 7 reads the classifier), FALSE on `Escalate Expense Ticket` (every escalate reason is gate 0–4), and true-of-some-false-of-others on `Flag Expense For Review`. Replaced by the classifier's `source` + confidence **and** `describeDecidingGate()`'s own sentence about whether that figure was consulted at all. |
| `Resolve Expense Ticket` | "Your expense claim has been automatically approved." | **verified TRUE and kept.** This node is reachable only downstream of the real `PATCH /v1/expenses/:id`, and that node has no `onError`, so a failed write can never produce this reply. What is added is the figure — the employee used to get a bare "approved" with no amount. |

## The expressions, and why they address `$('Expense Gates')`

**Not `$json`.** At four of these nodes `$json` is whatever `Assign Routing`
emitted; at `Resolve Expense Ticket` it is `Carry Context After Approve`'s
output. Both happen to spread the gates' fields *today*, which is exactly what
makes `$json` the wrong thing to depend on: the day either Code node stops
spreading, the expression renders as an empty string on a green run.

**`.first()` and not `.item`, for the gates lookup.** `.item` resolves through
n8n's pairedItem chain, and the chain from `Expense Gates` to these nodes is
eight hops and crosses a Supabase node with `onError: continueRegularOutput`, an
HTTP node and four Code nodes. A broken link makes `.item` **throw** — which on
`Resolve Expense Ticket` means an expense that really was approved delivers no
reply at all. `.first()` needs no pairing, the graph is single-item by
construction, and `.first()` is already the established form for reaching this
node here: `Carry Context Forward` and `Carry Context After Approve` both do
`$('Expense Gates').first().json`.

**The four existing `$('Assign Routing').item.json.routingNote` appends are
left alone.** They are proven by real executions (10162, 10292) and are not the
regression being fixed. Only `Resolve Expense Ticket`, whose expressions are
new, takes the pairing-free `.first()` form.

The routing sentence is **appended in the node** rather than composed into
`internalNote`, because `Assign Routing` has not run when the gates run, so the
group and tags it resolves do not exist yet.

## Change 1 — the `Expense Gates` Code node body (DO THIS FIRST)

Publish `workflows/nodes-uc02/expenseGates.js` to the `Expense Gates` node on
`WORKFLOW_UC02_ID`. `npm run deploy-node` does one node from its file.

What is new in it, all of it inside the `COMPOSED TICKET PROSE` sentinels:

- `GATE_SEQUENCE` + `CONFIDENCE_GATE_POSITION` + `describeDecidingGate()`,
  **generated** from `src/uc02/policyEngine.js`'s exports rather than retyped,
  and held byte-equal to them by test;
- `composeInternalNote()`, emitted for **every** decision including
  `auto_approve`, so all five nodes can adopt it without this file changing
  again;
- `composeCustomerReply()`, which returns `null` for every decision but
  `auto_approve`.

Two new fields appear on the node's output: `internalNote` and `customerReply`.
Nothing branches on either, and nothing may — `Route by Decision` switches on
`decision` and must go on doing so.

**This change is also independently useful before any node moves**: it does not
alter a single decision, reason, flag or write payload, which is what
`test/n8nUc02Parity.test.js` re-confirms.

## Change 6 — `Resolve Expense Ticket` (the CUSTOMER-FACING node)

Two changes: the public reply, and **one new field**.

**`updateFields.publicReply`**

- old:
  ```
  Your expense claim has been automatically approved.
  ```
  (a literal, not an expression — no leading `=`)
- new:
  ```
  ={{ $('Expense Gates').first().json.customerReply }}
  ```

which renders, for a 125.00 USD claim:

> Your expense claim for 125.00 USD has been automatically approved. It was
> checked against the spend cap recorded for its expense category, and the
> approval has been written to the expense record at Remote. No further action
> is needed from you.

**PLAIN TEXT, AND IT MUST STAY PLAIN TEXT.** n8n's Zendesk node sends
`publicReply` as plain text and **silently escapes HTML** — its `internalNote`
sibling is the one documented "(Accepts HTML)". UC-01 delivered a whole letter
to a customer as literal `&lt;!doctype html&gt;…` source on a fully green run
because of exactly this. `composeCustomerReply()` emits no tag and no entity,
and `test/n8nUc02TerminalZendeskNodes.test.js` asserts it.

If the amount cannot be read as a whole number of minor units, the figure clause
is **dropped**, never printed as `0.00` — money is the one thing the
substitution ladder forbids fabricating outright.

**`updateFields.internalNote` — NEW, AND SEPARABLE.** This node has never
carried one, so the one decision on this graph that **moved money** is also the
one nobody can reconstruct from the ticket. Adding the composed note fixes that
at no risk (`.first()` needs no pairing) and is strictly an addition: **drop
this one field if you want the smallest possible change**, and nothing else in
this deploy is affected.

`group` is deliberately **not** added. This node has never set one, and
assigning a solved auto-approved ticket to a queue is a routing change wearing a
prose change's clothes.

```json
{
  "publicReply": "={{ $('Expense Gates').first().json.customerReply }}",
  "internalNote": "={{ $('Expense Gates').first().json.internalNote }}\n\n{{ $('Assign Routing').first().json.routingNote }}",
  "status": "solved",
  "tags": [
    "uc02_auto_approved"
  ]
}
```

## Proving it afterwards

Drive one real ticket and **read the ticket back**, never the run status. A
green node that wrote an empty note is the exact failure these expressions can
produce, and every layer reports success when it happens.

The cheapest proof is a `human_review`: raise a ticket carrying `uc02_test` and
the employment field `9990000000001` against any pending Sandbox expense whose
category has no cap (`policy_cap_unknown`, gate 12 — the outcome §4 records as
the common one). Then open the ticket and check the internal note has the
headline, the gate sentence, both money figures, the category line and the
"WHO DECIDES, AND WHERE" paragraph.

The **green** path is harder and the reason is a Sandbox limit, not a defect:
`POST /v1/expenses` mints only already-approved expenses, so no *pending* claim
can be created and each pending claim the Sandbox happens to hold gives exactly
one clean run (gate 6 blocks the repeat).
`scripts/make-demo-receipt.mjs --total <minor> --date <iso>` tunes a receipt to
one. If one is available, that run is the only way to see the new customer reply
on a real ticket — check the **rendered public comment**, not the node's success
flag.
