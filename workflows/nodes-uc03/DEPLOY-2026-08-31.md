# UC-03 live-graph deploy — 2026-08-31, the five terminal Zendesk nodes and the customer-facing reply

Everything below is prepared, tested and **not deployed**. Nothing in this pass
touched n8n; every read against `WORKFLOW_UC03_ID` was a `GET`.

`WORKFLOW_UC03_ID` was read live on 2026-08-31 (21 nodes, `active: true`,
`versionId === activeVersionId === 63ceb10d-0ec3-4fa4-926a-e3eb1cb84b38`) and
the parameters below are that capture with the note expression replaced.

Read `CLAUDE.md` §7b before doing any of it. The two rules that matter here:
`PUT /api/v1/workflows/{id}` **publishes in place** (the MCP `update_workflow`
only drafts), and the only thing that answers "is this live?" is
`activeVersionId === versionId` read back afterwards.

**Order is not optional.** Changes 1 and 2 below are Code-node bodies; changes
3–7 are the Zendesk nodes that read what those bodies produce. Deploying a
Zendesk node first would give every ticket an internal note consisting of the
routing sentence and nothing else — on a fully green execution, with nothing red
anywhere, because an n8n expression that dereferences a field nothing produces
renders as an **empty string**.

## Why anything changes at all

None of these six nodes carries a checkable body today. The five Zendesk nodes
have no `jsCode`, so `verify-deployed`'s body diff is structurally blind to
them; `Render Informational Answer` had a `jsCode` and **no repo file**, so
nothing diffed it either. All six are baselined in
`scripts/lib/unguarded-node-baseline.json`. So UC-03's least-checked strings
were the ones that reach real people.

`test/n8nUc03Parity.test.js` cannot cover this — it compares DECISIONS, and a
node that reaches the right verdict and describes it in false words passes it
every time. It did: 61/61 green over both of the false sentences below.

| node | retired sentence | what is wrong with it |
|---|---|---|
| `Render Informational Answer` → `Reply + Solve Ticket` (**PUBLIC**) | "…reply to this ticket and a specialist will review and issue it." | **A FALSE INSTRUCTION TO A CUSTOMER.** The graph claims `(UC-03, <ticket id>)` in `workflow_claims` before its first durable write, so a reply that re-triggers it stops silently at `Duplicate Delivery — Stop`. `docs/use-cases/UC-03.md` already quotes this line and calls it "advice to do the one thing that produces nothing". |
| `Flag For Formal Letter Review` | "Formal travel support letter DRAFTED text is available in the UC-03 app; NOT auto-issued — specialist sign-off required." | **False on 100% of reachable inputs, three ways.** Nothing is drafted (this graph has no letter-render node). The "UC-03 app" has never held it (the ZAF panel and `by-ticket` resolve a `cases` row; this graph writes none, so they answer 404). And `src/uc03/signoffPolicy.js` refuses a sign-off on the branch that used to be this node's only reachable input: "a formal letter built from an extraction the router itself refused to trust is not something anybody can responsibly sign." |
| `Escalate Travel Ticket` | "AI summary — ESCALATED: … No letter was issued." | The **sentence is true** for all ten reachable escalate reasons and is kept. What was wrong was the **flags** it printed — four fabricated `letter_missing_*` findings on every run, whatever the record. Root cause fixed upstream in `b5227da`; re-driven on this pass in both directions. |
| `Route To UC-04` | "…recorded for inspection only, never dispatched automatically." | **True in both halves and kept.** What was missing is everything about what happens now: no `uc04_*` tag (so UC-04's intake trigger cannot fire), no `uc04_authorizations` row, no `cases` row on either use case (so both sidebars answer 404), and no statement of who acts or where. |
| `Unrecognised Travel Decision` | "Automation produced an unrecognised decision (…). Routed to a human rather than dropped." | Not false — just unversioned, and it discards everything the gates body knows. |

**"AI summary" — judged per node, and the answer came out "per run".** UC-03 does
have a real `Classify Inquiry (LLM)` node, so the word is defensible here in a
way it would not be on UC-05. It is still not a fact about any particular run:
the model is validated against a strict shape and any failure falls back to the
deterministic rules. And on `Route To UC-04` the content is a handoff event
assembled from fields already read — deterministic, so "AI summary" was wrong
there in kind, not degree. `composeInternalNote()` now reports
`classification.source` instead.

## The expression, and why it addresses `$json`

All four note-carrying nodes get the **same** `internalNote`. The per-decision
difference is composed upstream, in a file `verify-deployed` diffs byte for
byte, rather than typed four times into four node parameters where four copies
drift independently — which is exactly how the sentences above came to exist.

```
={{ $json.internalNote }}

{{ $('Assign Routing').item.json.routingNote }}
```

**`$json`, not `$('Travel Router Gates')` — and this is the one place UC-03
deliberately differs from UC-04's identical fix.** On UC-04, `Assign Routing`
sits directly downstream of a Supabase node and spreads that node's insert
response, so `$json` there carries none of the gates' fields. On UC-03 there is
a `Carry Context Forward` node in between
(`return [{ json: $('Travel Router Gates').first().json }];`), and `Assign
Routing` spreads its input — so `$json` at UC-03's terminal nodes **is** the
gates' output plus the routing fields. That is not inferred: all five live nodes
already read `$json.externalRef`, `$json.decision`, `$json.reason` and
`$json.flags`, and the graph has run green.

And `.item` would be the **riskier** form here, not the safer one: it resolves
through item pairing, and `Carry Context Forward` returns a bare `[{json}]` with
no explicit `pairedItem` — precisely what its sibling `Carry Context After
Claim` sets `pairedItem` for, with a comment saying an unpaired Code node
"breaks the chain".

The routing sentence is **appended here** rather than composed into
`internalNote`, because it is produced downstream of the gates — `Assign
Routing` has not run when the gates run, so the group and tags it resolves do
not exist yet.

## Change 1 — `Travel Router Gates` (Code node)

Publish `workflows/nodes-uc03/travelRouterGates.js` as `parameters.jsCode`.

It gains `composeInternalNote()` and emits `internalNote` on the output item for
**every** decision. `route()` is untouched, so the decision vocabulary is
unchanged and `test/n8nUc03Parity.test.js` stays green (61/61, re-run).

The gate meanings are ported verbatim from `src/uc03/policyEngine.js`'s
`GATE_SEQUENCE`, with **one declared substitution**: two of the fourteen name
**Global Mobility** as the owning team, while `Assign Routing` sends UC-03's
tickets to **Travel & Mobility Support** and `routingNote` — appended a few
words later — spells that correctly. Porting them raw would put one team, twice,
in two names, six words apart on a real ticket: the defect already recorded for
UC-04 at `docs/ESCALATION-DESTINATIONS.md` §2.2. The substitution is applied to
exactly those two strings and the test applies the same rewrite to the src side
before comparing, so a drift in the reference wording still fails.

Already in `scripts/lib/deployedNodeMappings.mjs`'s `MAPPINGS`, so
`verify-deployed` diffs it the moment it is published.

## Change 2 — `Render Informational Answer` (Code node) — **the customer-facing one**

Publish `workflows/nodes-uc03/renderInformationalAnswer.js` as
`parameters.jsCode`. **This body has never existed in this repository before**;
the file is byte-identical to what should be deployed, and wiring it into
`MAPPINGS` is a separate change (owned elsewhere) that makes it diffable.

Everything above the closing paragraph is unchanged. The closing paragraph
becomes:

> If you need a formal travel support letter for this trip (for a visa
> appointment or a port-of-entry check), it is a separate request rather than a
> reply here. This ticket has already been recorded as answered, so replying to
> it does not start a letter request. Raise one in Remote's Request Hub and it
> is handled on its own.

**It deliberately does NOT copy what `src/uc03/letter.js` now says.** That file's
`renderInformationalAnswer()` promises the opposite — accept the offer and the
letter "is written and issued to you straight away" — which is true on the
Node/portal path and unbackable here: accepting is
`POST /api/cases/:id/request-letter`, which needs a `cases` row, and this graph
writes none. Replacing one false promise with another is the failure mode this
change exists to end. The divergence is argued in that file's header so the next
reader does not "fix" it by harmonising the two.

**PLAIN TEXT.** `publicReply` silently escapes HTML — UC-01 shipped a rendered
letter through it and the customer received literal `&lt;!doctype html&gt;…` on
a fully "successful" run. No tags, no entities. Asserted on the rendered body by
`test/n8nUc03TerminalZendeskNodes.test.js`, along with no harness vocabulary and
no compensation.

## After publishing

1. Read the graph back and confirm `activeVersionId === versionId`.
2. `npm run verify-deployed` — `travelRouterGates.js` is already in `MAPPINGS`,
   so a drifted body is now visible. It exits **2**, never 0, when it cannot
   reach n8n, so its silence is never a pass.
3. Drive one real ticket per branch and **read the node OUTPUT, not the run
   status**. The specific thing to look at: the internal note must be several
   paragraphs, not one routing sentence. A one-sentence note means the
   `$json.internalNote` expression resolved to an empty string, and every layer
   will report success.
4. On the `auto_resolve` branch, read the **rendered public comment on the
   ticket**, not the node's success flag.

## Named follow-ups, not done here

- `Render Informational Answer` is not yet in `MAPPINGS` / `STRUCTURAL_MAPPINGS`,
  and neither are the five Zendesk nodes' checkers. Wiring them is what turns
  this spec from "tested" into "enforced against the deployment".
- `Reply + Solve Ticket` sets no `group`, so an auto-resolved UC-03 ticket lands
  in the account's default `Support` group.
- The node name `Flag For Formal Letter Review` and the tag
  `uc03_formal_letter_review` both describe a review of a document that does not
  exist on this path. Renaming either has readers outside this file
  (`src/surfaceverify/registries/index.js`) and is a live-queue migration.
- `src/uc03/policyEngine.js` says "Global Mobility owns it" in four rendered
  strings that reach the PORTAL surfaces. The graph is clean of it and this
  change keeps it that way; the src-side wording is a separate call, and
  `docs/ESCALATION-DESTINATIONS.md` argues a straight rename would make the
  sentences contradict themselves.
- `letter_missing_contract_type` is unreachable on BOTH execution paths:
  `normalizeEmployment()` and its port both default `contract_type` to the
  literal `"unknown"`, so the letter-scope gate never sees it blank and a letter
  would print "unknown" rather than being refused.
