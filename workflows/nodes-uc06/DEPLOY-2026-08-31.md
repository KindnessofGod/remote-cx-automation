# DEPLOY 2026-08-31 — UC-06's three terminal Zendesk nodes

**Workflow `WORKFLOW_UC06_ID` — "RCX UC-06 🟡 Contract Amendment / Payroll Cutoff". Three `n8n-nodes-base.zendesk` "update
ticket" nodes.** Not deployed by this pass; this is the paste-ready target.

## Why this exists

A Zendesk node carries no `jsCode`, so `npm run verify-deployed`'s body diff
is **structurally blind** to it and `test/n8nUc06TerminalZendeskNodes.test.js` cannot see it either
(parity compares DECISIONS — a node that reaches the right verdict and describes
it in false words passes every time). The prose on these three nodes was typed
once into a node parameter, written onto real customers' tickets, read back by
no check and versioned by nothing.

The note is now composed in `workflows/nodes-uc06/amendmentGates.js` — a
file `verify-deployed` **does** diff byte for byte — and these nodes only
interpolate it. Same split as UC-01 and UC-04.

## Order of operations, and it matters

1. **Deploy the gates Code node first.** `amendmentGates.js`'s
   `composeInternalNote()` is what `internalNote` interpolates. Publishing
   the Zendesk nodes first leaves them dereferencing a field nothing produces,
   which renders as an **empty string on a fully green execution** — the ticket
   would get the routing sentence and nothing else, and every layer would report
   success. `npm run deploy-node` publishes one Code node from its file.
2. **Then the three Zendesk nodes below**, by hand in the editor or by
   `PUT /api/v1/workflows/WORKFLOW_UC06_ID`. Remember §6: a REST `PUT` **publishes in
   place**; the MCP `update_workflow` writes only a draft. Whichever you used,
   check `activeVersionId === versionId` — that comparison is the only thing
   that answers "is this live?".
3. **Read the deployed bodies back and diff them** before trusting a success
   flag, then drive one real, unpinned execution and read the NODE statuses and
   the ticket's rendered comment — never the run status.

## What NOT to change while doing this

`tags` on the **Escalate** and **Unrecognised** nodes carries
`={{ $('Assign Routing').item.json.routing.queueTag }}`, which is
rca-iih7 / D-14's fix and is owned by
`workflows/nodes/escalationQueueTagSpec.js`. It is reproduced in the blocks
below so they can be pasted whole. **Do not drop it**: without it the ticket
claims a queue tag it never receives, and the owning team's Zendesk view is
empty. The two specs are held equal by a cross-spec test — if you edit one, edit
both, in one change.

### `Flag Awaiting Dual Approval`
Retires *"**AI drafted** amendment … — awaiting dual approval (**Customer Admin
+ Payroll Specialist**)."* Two defects in one sentence:

- **Nothing here is AI.** This graph has 18 nodes and three http calls, all to
  Remote. The "drafted amendment" is `draftSummaryTemplate()`, a string
  concatenation of the requester's own figures.
- **It names two roles and not where either acts.** `customer_admin` is
  **employer-side** — "customer" means Remote's customer — but the only surface
  rendering both slots is the **ZAF sidebar**, a Zendesk *agent* surface, and
  this account holds two agent seats, both the project owner's. A Zendesk agent
  could reasonably read both slots as theirs, collapsing a cross-organisational
  dual control into two Remote employees **with every control still reporting
  satisfied**.

The mechanism is **not** changed — that the employer's signature is its own act
is a decided product call (`qa/HUMAN-DECISIONS-REQUIRED.md` §F1 / `[A-4]`,
answered 2026-08-21). What changes is that the note now names who fills each slot
and on whose side, quoting `src/uc06/dualApprovalPolicy.js`'s own refusal text.

`status` unchanged at `open`. No queue tag: `isEscalation('dual_approval_required')`
is false.

### `Escalate Amendment Ticket`
Retires *"… this request **needs manual payroll/HR handling** and will not go
through dual approval."* Accurate for **6 of the 12** reachable escalate reasons
and false for the rest:

| class | reasons | why the sentence is false |
|---|---|---|
| authentication | `identity_not_verified` | nothing was assessed; the remedy is a session, not a contract |
| upstream outage | `upstream_record_not_found`, `upstream_unavailable`, `country_schema_unavailable` | a **Remote API failure**. `src/shared/upstreamFailure.js` exists so these are not mistaken for policy refusals; this sentence undid that at the last hop |
| malformed request | `change_value_underivable`, `schema_invalid` | the requester re-states the change; keying it in for them substitutes our reading for theirs, on a contract |

**Sharpened by routing:** UC-06's row in `src/shared/escalationRouting.js` has
no `escalationGroup`, so an upstream 502 lands in **Payroll Ops' own queue**
carrying a note telling Payroll Ops it is theirs to do by hand.

## After deploying

- `npm run verify-deployed` — 0 drifted, and note it **exits 2, never 0**, when
  it cannot reach n8n, so its silence is never a pass.
- Drive one real, unpinned execution per branch and **open it**: read each
  node's status and the ticket's **rendered** internal note. A green run proves
  nothing on its own — a pinned node reports success having done nothing, and a
  dereference of a missing field renders empty on a fully green execution.
- Drive at least one **upstream** escalation (point the Remote read at a dead
  employment id) and confirm the ticket no longer tells Payroll Ops it is their
  manual work. That is the change with the largest blast radius and the one a
  passing test cannot demonstrate on a live queue.
