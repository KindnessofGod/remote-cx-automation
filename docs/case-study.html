What this system is

A CX automation layer for an Employer-of-Record platform. Nine support use cases, three risk tiers, one architecture. An LLM reads messy human language and classifies intent. Every decision that changes anything — a customer-facing reply, a payroll-amendment payload, a state change in a case — is made by plain, testable JavaScript, with no AI in the loop at decision time.

Prime directive: LLMs interpret; deterministic code decides. An LLM may classify, extract and draft. It may never perform a state change, and its output may never reach a gate unvalidated. Validate against a strict shape, fall back to rules on any failure.

Architecture: risk tiers select the execution path

The tier is not a label. It is a code branch. Every use case is assigned to exactly one tier, and the tier determines how much automation is allowed at all.

Low
Validate → auto-execute → resolve. Exception-gated only.
Medium
AI prepares + risk-scores → human approves in ZAF sidebar → then execute. Dual approval for sensitive changes.
High
AI compiles a dossier → escalate. No automated execution — and for UC-07/08, no execution path exists at all. Asserted by test, not by hope.

Honest status — what is built, what is live, what is not

Scope was deliberately widened. The original plan was three use cases built deep and nine specified, on the reasoning that three complete builds read better than nine shallow ones. That decision was later overturned on purpose, so that every tier is demonstrated by working code rather than by a document. All nine use cases are now built: core decision logic, a runnable HTTP API, a registered ZAF sidebar panel, and an n8n workflow whose Code-node body is parity-tested in a node:vm sandbox against the Node implementation it mirrors (test/n8nParity.test.js plus one per use case).

All nine n8n workflows are active on a live n8n instance, each credentialed against the same real OpenAI, Remote Sandbox, Zendesk and Supabase accounts.

The nine APIs are deployed and public — and for two days refused every approval, by design

The sidebar runs in the agent’s browser inside Zendesk and fetches these APIs directly, so “the APIs are running” has to mean running on the public internet, not running while a laptop is open. What follows describes the two days before the database and the identity verifier were attached, when reads returned nothing and writes were refused, both on purpose. The write refusal is the interesting half, and the reasoning is kept because it is the design record — it is the reason nothing unsafe happened during that window. The rule for whether a signed approver identity is required is: a durable store is attached OR the deployment is publicly reachable. The two conditions are ORed so that the platform check can only ever add the requirement, never remove one. Without that OR, this URL would have accepted a payroll approval from anyone able to set an HTTP header, during exactly the window where the URL is live but the database is not yet attached. The deployment therefore answers every approve/deny with 401 signed_identity_not_configured, loudly, by design.

1. Measuring impact

Most automation projects can tell you what they built. Far fewer can tell you whether it’s working, and almost none can tell you when to stop.

The metrics layer (src/metrics/, npm run metrics) answers all three questions, and its central idea is that every judgement is tier-aware. A dashboard that maximises “% automated” would reward exactly what the architecture exists to prevent:

Green tier
A high auto-resolution rate is success. Measure it and push it up.
Amber tier
Auto-rate is meaningless. The human gate IS the design. Measure specialist acceptance of AI recommendations instead.
Red tier
An auto-resolution on a high-tier case is an integrity violation. Count them — the number must be zero.

Five verdicts, in the order recommend() actually evaluates them

integrity_violation → insufficient_data → stop → iterate → healthy
  1. integrity_violation — any invariant breach at all. Checked first, so it can never be masked by a good-looking rate.
  2. insufficient_data — two distinct checks, both before any rate is judged. First: fewer cases than the configured minimum sample size. Second, and the one that fixed a real bug: a medium- or high-tier use case with zero decided review rows. That used to read as healthy. There was no data to be healthy about.
  3. stop — below the floor. For low tier, the auto-rate is so low that nearly every case reaches a human anyway, so the automation is adding review load rather than removing it. For medium and high tier, specialists accept so few AI recommendations that the recommendation is noise.
  4. iterate — above the floor but under target. The same two rates, one threshold up.
  5. healthy — the fall-through, reached only when every configured threshold is met.

“Stop” is a first-class verdict, not a failure. A system that can only recommend “build more” is not a measurement system. Two safety invariants are checked against every row and reported as a count that must read zero, never as a rate:

Flagged auto-resolution. A case that auto-resolved while carrying escalation flags — evidence something bypassed the gates. Count must be 0.
Auto-resolution on a red-tier use case (UC-07/08/09). No high-tier case may ever be resolved by the automation alone. UC-07 and UC-08 have no execution path at all; UC-09 has one, but only behind a multi-role approval floor — so an auto_resolve appearing on any of the three means a gate was bypassed. Count must be 0.

What the dashboard actually reports

  • Auto-resolution rate — per use case and overall, a headline number only for green-tier cases.
  • Exception reasons, ranked — the top row is the next thing worth engineering. Denominator is exceptions, not all cases, so auto-resolutions never dilute the share.
  • Specialist acceptance rate — of every human approve/deny decision made in the sidebar, the share where the specialist agreed with the AI’s recommendation. Fed by real audit_log rows written on every recorded decision. Pending cases are excluded; the rate is null (not 0) when nothing has been decided, because “no data” and “everyone rejected it” are opposite situations.
  • Redundant-call detection — the audit trace records every LLM/API attempt, not just the final decision. A trace group whose attempt numbers are not a clean 1..n sequence is flagged as a genuine duplicate call, which is what distinguishes it from the retry wrapper’s own legitimate bookkeeping.
  • Median handling time (zero-touch path only — queued cases excluded, honestly labelled).

The offline dashboard runs ~120 tickets through the real workflow gates when Supabase is unconfigured — not a hand-written fixture. Change a gate in policyEngine.js and the numbers move, because the seed is a run of the actual code, not a snapshot.

2. Knowing when NOT to automate

The clearest example was not a judgement call. It was produced by the impact dashboard, from live production data, and it says to switch something off:

UC‑02 · STOP — Auto‑resolution is 0%, below the 15% floor. Nearly every case reaches a human anyway, so the automation is adding review load, not removing it.

That verdict is computed, not written — the same run reports ITERATE for two use cases and INSUFFICIENT_DATA for six more, and refuses to grade a use case with fewer than ten cases on record. Regenerate it with npm run metrics; the rendered dashboard is demo/metrics.html.

Three further decisions were taken not to automate, each argued from evidence rather than instinct:

The strongest proof is UC-08

Cross-border tax and social security is exactly the kind of domain where an AI that can write to a real record would be dangerous. UC-08 is designed so that no execution path is even reachable, enforced at four layers:

  • Code: handleTaxInquiry() takes no remote or zendesk dependency at all. There is no parameter through which a write-capable client could ever be passed in. Not a runtime check that could have a bug — the literal absence of any object this code could call to change anything.
  • Store: dossierStore.js has exactly one write method (createDossier) and zero mutation methods — no approve, no deny, no status column to flip, no markExecuted. There is nothing on this store a bug could ever grow into a write against a real record.
  • API: src/uc08/server.js has a GET route and no POST route in the file — not one that merely refuses at runtime, simply absent. Any POST 404s.
  • n8n graph: The n8n workflow has no Switch/IF node anywhere. Every execution ends at the same single Zendesk internal-note update, never an automated public reply.

A test asserts all of this — structurally (source-level, comments stripped, asserting no reference to either REST client’s write methods) and behaviorally (the decision is always "escalate" across varied inputs). A policy check that merely refuses to call a write method is one bug away from calling it. Removing the parameter entirely removes the bug’s precondition. UC-07 is the second build of the same shape, which is how it stays a pattern rather than a one-off.

UC-09: when automating is right, but only behind a floor

The mirror-image judgement matters just as much. UC-09 (off-cycle payroll adjustments) is framed high-tier and moves real money — and it is the one high-tier use case that does get a real execution path, because refusing to build one would just push the work back to a spreadsheet. What makes that defensible is where the floor sits:

  • The required approval count is Math.max(2, riskEvaluation.minApprovalSlots). Risk can raise it to three (requester + approver + payment releaser); nothing can lower it below two. The AI can never execute alone, whatever the risk assessor returns.
  • Segregation of duties is enforced, not documented: the same person filling two roles is refused with same_person_cannot_fill_multiple_roles.
  • The payload is validated against the employment’s country schema before the first approval slot is even offered — an adjustment that could never legally be written has no business collecting human sign-off first.
  • The employment record is re-read immediately before the write, so an approval given days ago cannot execute against an employee who has since been terminated.

The sidebar is built to refuse things

The ZAF sidebar drives all nine use cases from one bundle — a shared shell plus a per-use-case panel registry. The shell owns the only question that decides whether any controls appear; a panel is only ever asked what the controls should look like, never whether there should be any. Four of the nine panels (UC-02, UC-03, UC-07, UC-08) deliberately supply no controls at all, each with its reason written down next to it: a compliant expense auto-approves inside the workflow and its exceptions belong to a Finance Ops queue elsewhere; UC-03 is a router with no write route in its API; UC-07 and UC-08 have no execution path to approve.

On the panels that do have controls, the refusals are the point: a human can see an escalation, but the approve/deny buttons that exist for human-review cases are never rendered for it — the safe path must not double as a dismiss button. A decided case cannot be decided twice. And an approval re-reads the employment record first, because the gate checked “is this employee active?” when the ticket arrived and approval can happen days later. That is a freshness re-check, not a duplicated gate.

What broke when it met reality

Everything in this section was found by running the system against live services and then reading the destination — the database row, the rendered customer comment, the deployed graph — rather than by reading a green status. None of it was caught by the test suite, and that is the point: every one of the tests passed throughout, before and after.

The through-line: a system that fails closed and a system that is structurally incapable of succeeding look identical from the outside. Both refuse. Both log a reason. Both pass every safety assertion you can write. Only a positive test — “this known-good input MUST succeed” — can tell them apart.

1. UC-03 could never have said yes — and every test passed anyway

UC-03’s supported-destination gate compared two-letter country codes (ES) against a list built from the real API’s code field, which is the alpha-3 form (ESP). The field the code actually wanted, country_code, does not exist on that endpoint at all, and the rows sit directly under data rather than data.countries as the comments claimed. A successful 224-row fetch therefore yielded an empty supported list, and not one request could ever auto-resolve.

It survived for weeks because every fail-closed assertion passed. An escalation is what a cautious system does; it is also what a broken one does. The fix is proven both ways now — Spain auto-resolves (the first auto_resolve this use case has ever recorded) and an unsupported destination still escalates.

Why the fixture did not catch it: the local mock server served {data:{countries:[…]}} with flat country_code rows — an envelope and a row shape the real API does not use. The mock agreed with the code instead of with the API, so it confirmed the bug rather than exposing it. Making the mock faithful then broke three tests, all of them real findings, including one named “falls back to the 3-letter code when alpha_2_code is absent” — a test that had pinned the defect as intended behaviour and passed for its entire life.

Lesson: a fixture that disagrees with production is worse than no fixture, because it manufactures confidence. And a test suite made only of negative assertions cannot distinguish safety from paralysis.

2. Four identity gates verified a claim against itself

In UC-03, UC-05, UC-06 and UC-09, the n8n identity gate could report verified: true having proved nothing. Two of them echoed the caller’s own employmentId back as the “authoritative” record id and then compared the session against it — a tautology. The other two compared session.companyId against a company_id that defaulted to null, so null === null passed.

All four still refused the request — but only by accident of gate ordering, because a later status check happened to catch the run first. An identity control whose correctness depends on a downstream gate is not a control. The recorded reason was wrong even though the decision was right, and an audit log full of confidently wrong reasons sends people to fix the wrong thing.

Fixed at the construction site rather than at the comparison: no usable record now yields a record object at all. Proven in production on UC-05 with identical input either side of the fix, where the recorded reason moved from employee_not_active to identity_not_verified.

Lesson: “it failed closed” and “the control works” are different claims. The reason field, not the decision field, is the one worth auditing.

3. A failed API read was recorded as the customer failing identity checks

Four graphs carried onError: continueRegularOutput on their Remote reads. That setting does not mark the node red: it reports success and quietly emits an error object in place of the data. Downstream gates then evaluated that error object as though it were a record, escalated, and named the wrong cause — so an outage upstream was written into the permanent audit trail as a customer identity failure.

Three states are now distinct: upstream_record_not_found (a 404 — an authoritative answer about the record), upstream_unavailable (403/5xx/transport — the request was never evaluated at all), and an unchanged policy refusal. The attribution is fail-closed by construction: every verdict it can return is an escalation, and it is consulted only at gates that are already refusing, so it can correct a refusal’s recorded reason but can never manufacture an approval.

Lesson: “I don’t know” is a distinct answer from “no”, and collapsing the two corrupts every metric computed downstream.

4. A duplicate webhook sent a second letter to a real customer

Zendesk ticket #5 fired its trigger three times in quick succession. Nothing in the graph asked “have I already handled this one?”, so it produced two audit_log rows 30µs apart and posted a second verification letter publicly to the customer.

Webhook delivery is at-least-once by definition; a retry or a double-fired trigger is normal traffic, not an incident. Every path now claims (use_case, external_ref) in one shared ledger before its first durable write, and the guarantee is that table’s PRIMARY KEY, not application code — a check-then-insert in a Code node has precisely the race that caused the bug. A redelivery leaves by the error output and stops at a no-op, silently: paging a human every time Zendesk behaves normally would train everyone to ignore the alert.

Lesson: if correctness depends on not being called twice, the constraint belongs in the database, not in the workflow.

5. …and the check on that fix was itself wrong — twice-learned

A draft of this page claimed the opposite of what is written above: that UC-04’s claim node was silently failing and the use case had no exactly-once guarantee. The reasoning was that workflow_claims held no UC-04 rows while UC-04’s claim-proof drives had written audit_log rows.

That inference was wrong, and the way it was wrong is the interesting part. workflow_claims is a mutable table whose test rows had been purged; audit_log is append-only and survived. Absence in a deletable table means “no row now”, never “no row ever”. The disconfirming evidence was already on the screen and misread: claim-proof-uc07-a has no claim row either, and UC-07 is the one case demonstrated in both halves — which identifies a purge, not a defect.

The graph was correct all along, and the wiring is what proves it: the claim node’s error output reaches a no-op that continues to nothing, and the first durable write is reachable only through the claim. So a failed claim ends the run, and an audit row for a reference is itself proof that that reference’s claim succeeded. All ten doubly-driven claim-proof references have exactly one audit row each.

Lesson: this project’s standing rule is “a green run is not evidence — check the destination.” It has a mirror image that cost a wrong headline to learn: an empty destination is not evidence either, when the table is mutable. Match the strength of the claim to the durability of the table you read it from.

6. A fully “successful” run delivered escaped HTML source to a customer

The n8n Zendesk node’s publicReply field is plain text and silently escapes HTML; its internalNote sibling is the one documented as accepting HTML. The customer received the verification letter as literal &lt;!doctype html&gt;… source. The execution was green, every node succeeded, and nothing anywhere in n8n indicated a problem.

Lesson: for anything customer-facing, the artefact the customer actually receives is the only acceptable evidence. A green run status is not a rendering check.

Why this section is in a portfolio at all

Because the alternative is a case study that describes a system nobody ever pushed hard enough to break. All six were invisible to a passing test suite, and several were safe — wrong reasons attached to correct refusals, which is the hardest class of defect to notice precisely because nothing looks wrong. Finding and publishing them is worth more than the original claims were, and the corrections are dated rather than silently edited out.

It also produced the one engineering rule most worth carrying into a real CX org: measure the reason, not just the outcome. An automation reporting 100 % safe refusals may be perfectly calibrated or completely broken, and the outcome column cannot tell you which.

3. Named tooling

Every tool in the stack is used for a specific, defensible reason — never because it’s trendy.

n8n

The production orchestration backbone. All nine use cases have a built n8n workflow, and all nine are active on a real n8n instance with credentials attached for OpenAI, Remote Sandbox, Zendesk (OAuth client_credentials), and Supabase. UC-01’s is the reference graph (WORKFLOW_UC01_ID), now 19 nodes — 150 across the nine, all published. Every Code node body lives as a real .js file in workflows/nodes*/, compiled and parity-executed on every test run — which catches the escaping bugs the n8n editor silently accepts, and pins the fact that the gates now exist twice.

Zendesk + ZAF

The customer-facing channel and the human-in-the-loop interface. A ZAF v2 ticket sidebar (zaf-app/) drives all nine use cases from one bundle — a shared shell with a per-use-case panel registry. The sidebar itself holds no credentials: it POSTs the agent’s decision to the review API, which is the only side that can reach Supabase and write the audit_log row. That split is deliberate — a browser extension with database credentials in it would put the audit trail one devtools console away from being forged. Zendesk’s REST API handles reply, resolve, internal notes, tags, and ticket creation (for the live demo). OAuth client_credentials, live-verified — a Zendesk MCP doesn’t exist, which is consistent with the deliberate choice to use REST for every deterministic path.

Remote REST API

The system was built against Remote’s real Sandbox API, not guessed from the docs. Every request/response shape was verified live. normalizeEmployment() bridges the real API’s nested shape to the mock’s flat one so the policy engine and letter generator never need to know which source answered. Remote’s MCP server is read-only here — not because it lacks writes (it has them), but because it authenticates as a user via OAuth2 PKCE, which is the wrong shape for an unattended backend service that must retry idempotently and attribute actions to a system actor.

OpenAI

gpt-4o-mini for classification and summarisation only. Every LLM call returns validated JSON with an exact schema; the call is retried up to three times with backoff, and any continued failure (network error, bad JSON, invalid shape) falls back to deterministic rule-based logic. Every result is tagged source: "llm" or "rule_based_fallback", so which path answered is never implicit. The LLM seam was deliberately kept narrower for UC-06 and UC-08 than for UC-01: there the LLM only drafts display/audit text from already-decided facts, and the text is never read back into a decision or a payload. A narrative-faithfulness judge checks whether the drafted prose invented figures or dropped jurisdictions — its verdict is attached for a specialist to see, never read by any gate, and it fails open to an explicit not_evaluated rather than fabricating a verdict.

Supabase (Postgres)

The durable operational state. audit_log (append-only immutable trail), audit_trace (per-attempt, not just per-decision), cases (mutable current state), review_queue, documents, consent_records, request_artifacts, extracted_requirements, uc06_amendments, uc08_dossiers, and uc08_treaty_citation_vectors (pgvector for UC-08’s embedding-similarity treaty retrieval). RLS enabled with zero policies on every table — a backend-only service model, not a per-user one. Two backends reach it: the Node app connects as the postgres role over a direct connection string, and n8n writes audit_log through a Supabase API-key credential, because the raw host/port/user/password connection n8n’s Postgres node needs never existed for this account. cases and audit_log are never conflated.

Webhooks

The live n8n workflows receive Zendesk ticket events via webhook triggers, scoped to test-tagged tickets with a tag-based single-fire guard: fire only while none of the automation’s own outcome tags are present. That guard replaced an original status: new condition, which could never match — this Zendesk account moves agent-created tickets straight to Open. That guard is now confirmed firing on a real ticket — Zendesk ticket #6 went from customer comment to solved, tagged and audited in about five seconds. UC-01 is so far the only one of the nine triggered this way; the other eight are driven by webhook POSTs.

4. Documentation as part of “done”

This page is itself evidence of the discipline. Every build decision in the repo carries a “why” entry in docs/BUILD-LOG.md’s decision log (§4), including bugs that were found only by running against live services and the reasoning behind architectural choices.

The evidence-tagging system

Every claim about Remote’s API, Zendesk’s behaviour, or the underlying business logic is tagged with exactly the confidence it deserves:

[CONFIRMED] — verified live against the real Sandbox or real Zendesk account | [VENDOR-PUBLIC] — from Remote's public product and support content | [INFERRED] — reasoned from strong evidence | [PROPOSED] — a design choice, not a discovered fact

This matters because a reviewer who catches one overstatement discounts everything else. The status tables in README.md and docs/BUILD-LOG.md are load-bearing: if something says “not built” or “not yet confirmed”, it really isn’t. The same discipline has repeatedly been applied against this project’s own earlier claims — the note in workflows/README.md correcting “execution 10 ran through to audit” exists because that claim turned out to be false: the node was pinned, and a pinned n8n node reports success without touching the database. Finding and publishing that was more useful than the original claim was.

The repo also shows how a system is documented for AI collaboration: CLAUDE.md carries explicit continuity rules, gotchas-already-paid-for, and a session log that tracks what changed in each working session — because the project was built with AI assistance, and documenting for AI-driven workflows is what makes that reproducible.

What the repo demonstrates

Beyond the code, this project was built to demonstrate four things that are genuinely hard in CX automation:

  1. Measuring impact, not just shipping features. The metrics layer is tier-aware, includes “stop” as a first-class verdict, distinguishes “no data” from “bad data”, and is fed by real audit rows written on every recorded decision — not simulated and not a vanity dashboard.
  2. Knowing when NOT to automate. UC-07 and UC-08 have no reachable execution path, asserted structurally and behaviorally by test through the code, the store, the API surface and the n8n graph. Four of the nine sidebar panels deliberately render no controls. And UC-09 shows the other half of the judgement: automate the money path, but put an unlowerable floor of two approvers under it.
  3. Named tooling used for actual, defensible reasons. n8n as the production orchestrator, Zendesk + ZAF as the channel and the HITL interface, Remote’s REST API as the backbone, and Supabase as the operational store. Not a stack assembled to check boxes.
  4. Documentation as a first-class deliverable. BUILD-LOG.md, the evidence-tagging system, this page, and the honesty discipline throughout — including the corrections.

Design decisions worth defending

Money is an integer scaled ×100 everywhere. One module, tested hard. Getting it wrong overpays someone by 100×.
Every n8n workflow is parity-tested against the Node one. The gates exist twice; one parity test per use case executes the real n8n Code node body in a sandbox and asserts it decides identically. Duplication acknowledged and pinned, not hoped about.
cases and audit_log are never conflated. One is mutable current state, the other is append-only history.
Identity comes from an authenticated signal, never a claim. In the Node path that’s the Remote session; in the n8n path it’s the Zendesk-authenticated requester matched against the employment record. Both fail closed.
The letter template has a hard field whitelist. Compensation cannot leak regardless of what a request asks for.
The audit row is written before the customer-facing action. True on both paths and live, not drafted: the deployed graph reads gates → claim → audit → route, confirmed by activeVersionId == versionId. Found by checking the destination rather than trusting a green execution.
Every port is allocated in one registry, enforced by a test. Three separate files each claimed in a comment to have picked a unique port; three were wrong the same way. A comment asserting uniqueness cannot be checked. A test can.
Every test stays hermetic. Dependencies are injected so no test ever reaches a real network, regardless of what’s in the local .env. This was a bug twice — the fix was structural, not procedural, and a sudden jump in the suite’s runtime is now treated as a hermeticity signal in its own right.
Built against Remote’s real Sandbox API, a real Zendesk account, and a live n8n instance. Tests are hermetic and run with no credentials. Status verified 2026-08-18 against the live n8n instance and the live database, not against this project’s own notes — two claims did not survive that check and were corrected above. docs/BUILD-LOG.md §1 is the authoritative snapshot.
