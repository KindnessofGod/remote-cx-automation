# UC-04 — Remote Work Authorization / Workation

> Inherits `00-FOUNDATION.md`. **Canonical source:** live primary-source research, `docs/verification/uc04-workation-authorization.md` — supersedes all three raw UC-04 docs' proposed boundary, which agreed duration-based framing was wrong but hadn't replaced it with anything grounded in real evidence. **Supporting:** `UC-04 BUILDPACK v2.0`'s stress-test methodology (expected-routing phrasing, not asserted legal verdicts).
>
> **Renamed from "(<30 Days)"** — there is no duration threshold anywhere in this spec, at any dimension. See §7.

## 0. Business case

**[VENDOR-PUBLIC]** Remote's own support content confirms this is a named,
real internal process ("Remote Work Authorization"), reviewed case-by-case
by a dedicated Mobility Team — the existence of a staffed review process is
itself evidence the underlying need is real, independent of any ticket-volume
number. **Cost mechanism**: every request needs the same five factors
gathered (nationality/visa status, home-country absence rules, travel
history, visa type, job duties) before a human can decide — fact-gathering
that doesn't require judgment but currently consumes specialist time before
any judgment can start. **[UNCONFIRMED]**: request volume, and how much of
the Mobility Team's time is fact-gathering vs. judgment — no public data.
**Ships regardless**: the four-dimension fact-gathering + escalate-when-
unconfirmed engine (cost is fixed, and it accelerates the human's work
without ever substituting for it). **Gated on nothing further at the
architecture level** — this UC never auto-approves, so there's no "auto-rate"
investment decision the way UC-06's dual-control piece has; the risk-scoring
depth itself is the whole deliverable.

## 1. Summary
| Field | Value |
|---|---|
| **Trigger** | An existing Remote Work Authorization / travel-letter request appears (via webhook), created by the employee in Remote's own "Request Hub" UI — **not** originated by this automation |

### 1a. Who decides, and where — corrected 2026-08-30

**This section replaces an earlier claim in this file that "a mobility specialist
reviews in ZAF and makes the employer-side call."** That was wrong about the actor, and
consistently wrong: the entitlement, the sidebar button, the approval floor and the audit
row all named a Remote CX specialist as the person making a decision that belongs to the
customer. Recorded as a product call with the API evidence in
`qa/HUMAN-DECISIONS-REQUIRED.md` §K14.

| Stage | Decider | Surface | Written to Remote? |
|---|---|---|---|
| 1 · request | the employee | `/portal` | **no** — Remote publishes no `POST`, so the request object is a stand-in record (ladder rung 3, self-identifying) |
| 2 · employer approval | **the customer's own manager** | `/remoteui` — the Remote-product stand-in | **yes** — `PATCH` `approved_by_manager` / `declined_by_manager`, the only work-authorization write the API allows any client |
| 3 · Remote's mobility review | Remote's Mobility Team | the ZAF sidebar | **no** — `approved_by_remote` is a status **no endpoint can set**. Since 2026-08-31 the reviewer's verdict IS recorded, durably and audited, in **this** system (`src/uc04/mobilityReview.js`); it is never transmitted, and the panel, the audit row, the employee's page and the issued document all say so in the same sentence |

**What stage 3 became, 2026-08-31.** The panel used to offer no control at all, on the
reasoning that a button which cannot change anything at Remote should not exist. That
left the reviewer with nowhere to record a decision they had genuinely made, and left the
employee with no way to learn the answer — so the chain stopped one stage short of the
person it was for. The verbs are **`clear` / `decline`**, deliberately not `approve`: the
employer already used that word on this same record at stage 2, and one record carrying
two people's "approved" is how a reader comes to believe one of them settled the other.
Three properties are pinned by test rather than argued — `submitMobilityReview()` takes
**no Remote client**, so there is no path along which it could transmit; it refuses by
name when the employer has not approved first (`employer_approval_not_recorded`); and no
code path anywhere writes `approved_by_remote`.

**Where the n8n graph sits in this, corrected 2026-08-31.** `WORKFLOW_UC04_ID` decides
**stage 1 only**, and until this date it told the reader otherwise: its summary and the
internal note on the ticket both said a `ready_for_approval` request was *"awaiting ONE
mobility specialist's approval"* — a decision `src/uc04/approvalPolicy.js` refuses a
Remote agent and the ZAF panel offers no button for. Both now name the customer's own
manager and the surface the decision is made on. **Stage 3 is deliberately NOT in this
graph**, and the reasons are measured rather than argued: `uc04_test` (the intake
trigger's own condition) matches **0 tickets**, while all 20 real UC-04 tickets are
portal-raised and carry `uc04` — so no real request reaches the graph at all; and
`Claim Ticket (Idempotency)` claims `(UC-04, ticketId)` on the intake run, so the
re-fire an employer approval causes dies at `Duplicate Delivery — Stop` and any branch
downstream of the claim could never run. The stage-2 → stage-3 hand-off is
`handOffToMobility()` in `src/remoteui/server.js`, which runs after both durable writes
and reports its own failure to the manager. `docs/BUILD-LOG.md` §3.109;
`workflows/nodes-uc04/DEPLOY-2026-08-31.md` is the live-graph change.

The evidence is Remote's own published API, read live 2026-08-30: four endpoints total
(two `GET`, two `PATCH`), no `POST`, exactly two accepted transitions from `pending`, and
an **`employer_approver`** field whose published example value is `user0@company.com` — a
customer address. The Sandbox was probed the same day and answers the read (200, correct
shape, 0 rows) while refusing every create route (404), which is why stage 1 is a stand-in
and the stage-2 `PATCH` is real.

## 2. Trigger & user story
"Can I work from Spain for 3 weeks?" / "I need to extend my trip with some
remote days." The employee submits inside Remote's own product, not via
Zendesk or this automation — UC-03 may route a Zendesk conversation about
this topic here, but the actual authorization request object always
originates in Remote's UI. This automation reacts to that request appearing,
gathers and scores risk across the dimensions below, and prepares the
employer-side decision **for the customer's own manager** rather than making it —
see §1a. A Remote specialist never fills that slot.

## 4. Tools
- **REST reads/writes:** travel-letter-request read + `PATCH` (employer-side decision only), employment record, custom fields.
- **No RAG.** Coverage/role/immigration facts are looked up against maintained tables sourced from primary authorities at build time, not retrieved from a fuzzy knowledge base — false precision here has real legal consequences.
- **Foundation:** `risk-engine`, `remote-rest-client`, `zaf-app`, `audit-logger`, `identity-service`, `mock-remote-server`.

## 5. Workflow (n8n)
```
travel_letterrequested webhook → n8n → identity verify
 → REST: fetch request + employment + custom fields + trip history
 → LLM: extract structured facts from any free-text travel_reason_details
        (extraction only — never classifies risk or residency itself)
 → deterministic 4-dimension gate, each independently confirmed or escalated:
     1. totalization/treaty coverage for this country pair
     2. role/activity PE-sensitivity (contract-signing/sales/exec authority
        or founder/sole-operator status forces escalation regardless of
        anything else)
     3. cumulative days in a rolling 12-month window (not just this trip)
     4. immigration-authorization document on file (never inferred from
        "this destination usually doesn't enforce it")
 → ALL 4 confirmed with high confidence → risk summary → ZAF sidebar,
   specialist 1-click approve/decline → on approve → PATCH approved_by_manager
   → audit
 → ANY dimension unconfirmed/ambiguous → escalate to Mobility/Legal Tier-2,
   stronger safe-escalation treatment, not a simple 1-click → audit
```

## 6. LLM reasoning scope
**Does:** extract structured facts from free-text trip details (dates,
destination, stated reason); compile the 4-dimension summary for the
specialist; draft plain-language explanation of why a dimension escalated.
**Must NOT:** decide tax residency; calculate PE exposure as a fact; decide
role sensitivity from a fuzzy read of a job title without the maintained
category table; approve or `PATCH` anything itself; collapse the 4
dimensions into one score.

## 7. Deterministic logic
- **No *invented administrative* duration threshold, anywhere. A statutory limit with a named source IS a gate.** *(Narrowed 2026-08-21 per DRIFT-019 — `DECIDED · NOT YET BUILT`. The sentence previously read "No duration threshold, anywhere", absolutely, and a reader applying it literally would delete the Schengen 90/180 block, which is Reg. (EU) 2016/399 art. 6(1) via `docs/knowledge/layer-1-statutory/D-07`. DRIFT-013 cites this sentence in its own defence, so it is load-bearing in a second contract. What follows is the original claim and it stands, for administrative caps.)* Confirmed wrong by every primary source checked: Remote's own process has no stay-duration cap (only a 3–8 week lead-time requirement); the OECD's Nov 2025 PE framework is a 50%-of-working-time-over-rolling-12-months test, not a day cap; only one competitor (Deel, 45 business days/70 calendar days) publishes a hard number, and frames it explicitly as an internal administrative cap with an escalation path, not a legal-safe-harbor claim.
- 4 independent gating dimensions (§5), never collapsed into a single composite score — each must be confirmed with high confidence or the case escalates.
- Role/activity PE-sensitivity: contract-signing/sales/exec/founder authority forces escalation outright, regardless of every other dimension.
- Cumulative rolling-window day counter uses trip history, not just the current request.
- Immigration legality is a document-presence check, never an enforcement-likelihood guess.
- **Restricted-jurisdiction screen, checked first (added 2026-08-18).** A destination absent from Remote's own country registry (`GET /v1/countries` — CU, IR, KP, SY, RU, BY, MM, VE, AF, IQ) is `blocked`, not escalated. Two reasons, and the second is the material one: (a) before this, Iran and Montenegro returned the same decision *and the same reason* (`destination_out_of_scope`), which describes the matrix's coverage rather than the request; (b) `escalate` is one of the two decisions that create a real Remote work-authorization record, and Remote's own OpenAPI types that record's `destination_country` as the `Country` schema — "A supported country on Remote" — so the record being created was one the platform cannot represent. The screen is a floor, not a verdict: a registry country outside the curated matrix still escalates, for the reason that is true. It is deliberately **not** `eor_onboarding: true` (that flag answers "can Remote *employ* here", 91 of 224 rows — it would block Martinique for a French employee). Evidence and the full argument: `docs/research/COUNTRY-SUPPORT-SEMANTICS.md` §10.

## 8. Human control points
- **Mandatory specialist approval gate** for every case, no exceptions — this UC never auto-executes even when all 4 dimensions confirm cleanly (see tiering note below).
- Role/legality failures route toward stronger safe-escalation treatment (Tier-2 Mobility/Legal), not a simple 1-click approve.
- The specialist's `PATCH` can only forward-approve or decline; Remote's own Mobility Team performs the final approval the automation structurally cannot touch.

## 9. Failure modes & fallbacks
| Failure mode | Guard |
|---|---|
| Unconfirmed treaty/totalization coverage | Escalate — never guess a country isn't covered |
| Ambiguous role classification | Escalate — no inferred allowlist/denylist |
| Incomplete trip history | Escalate — cumulative check needs complete data, not a partial one treated as complete |
| No immigration document on file | Escalate — never inferred from destination-country enforcement patterns |
| Free-text `travel_reason_details` misparsed | Deterministic gate still runs on the extracted structure; low-confidence extraction routes to human review, not a guessed classification |

## 10. Audit & logging
Log: request id, all 4 dimension results + confidence, extracted facts,
coverage-table lookup result + source, cumulative day count + window,
specialist decision + reasoning, `PATCH` outcome.

## 11. Success metrics
Per `docs/METRICS.md`'s three-bucket framework:
- **Zero** auto-approvals that bypass the specialist gate (bucket 1 —
  integrity check; this UC has no auto-execute path by design).
- % of cases where all 4 dimensions were confirmable without escalation
  (informs whether the coverage/document tables need expansion).
- Specialist time saved on fact-gathering vs. manual baseline (bucket 3 —
  pending a real baseline; the actual value claim, not a deflection-rate
  metric).
- **Specialist-accept rate of the AI's 4-dimension summary** (bucket 2,
  reusing the accept/reject shape rather than a separate "escalation
  precision" concept): does the specialist accept the summary as-is, or does
  it need substantial rework? `≥60%` healthy/iterate, `<30%` stop,
  `DEFAULT_THRESHOLDS`. **Specified, not yet computed by `compute.js`** —
  tracking issue #20.

## 12. Test plan
Phrased as **expected routing outcome**, never as an asserted legal verdict
(multiple primary sources, including a Big 4 firm's own caveat, warn against
claiming that kind of precision):
1. UK destination, no single threshold applies → routes to escalation (ties-based test can't be reduced to a lookup).
2. Ireland/Germany/Poland, A1 coverage confirmed, individual-contributor role, document on file → routes to specialist 1-click.
3. India/Philippines/Mexico, no US totalization coverage → routes to escalation on dimension 1.
4. Canada, coverage confirmed (contrast case) → routes to specialist 1-click if other 3 dimensions clear.
5. Portugal, Digital Nomad Visa on file → dimension 4 passes on document presence, not destination assumption.
6. Sales/contract-signing role, any destination → routes to escalation regardless of other dimensions.
7. Cumulative trip history pushes rolling-window total high even though this single trip is short → routes to escalation.
8. Country outside the 9-country list → escalate-by-default.
8b. **Restricted jurisdiction (IR/RU/KP/…) → `blocked`, reason `sanctioned_region`, and no Remote work-authorization record created.** Paired with a positive test: a listed non-EOR country (Montenegro) must NOT be blocked, so the screen can never be silently re-pointed at `eor_onboarding`.
9. Missing immigration document → escalate, never inferred.

**Defect found and fixed this session: a sanctioned destination was
indistinguishable from an ordinary one, and could reach a real Remote
write.** Before the sanctions gate above existed, `policyEngine.js` had no
notion of sanctioned/restricted destinations at all — a request to a
country like Iran or Cuba with an otherwise clean profile (no
contract-signing authority, no PE-risk role, no hard visa/Schengen rule)
fell straight through to the risk matrix like any other pair, landed on
`riskLevel: "low"` exactly like a routine trip, and `policyEngine.js`
returned `decision: "ready_for_approval"`. `workflow.js` calls
`remote.createWorkAuthorization()` for BOTH `"ready_for_approval"` and
`"escalate"` (only `"blocked"` is exempt) — so a sanctioned-destination
request could produce a real Remote work-authorization record and reach a
one-click specialist approve, one PATCH away from actually issuing it.

Fixed by adding an explicit sanctions gate, checked BEFORE the
employer-permission gate and the risk matrix, resolving to `"blocked"`

### 15.2 The create that wrote into nothing (2026-08-19)

**`POST /v1/work-authorization-requests` does not exist.** `src/uc04/workflow.js`
called `remote.createWorkAuthorization()` on **every** `ready_for_approval` and
**every** `escalate`, and swallowed the failure with a `console.error`, so the
workflow could not tell a written record from an unwritten one. Three further
defects sat at the same two call sites: the create sent `status:
"pending_mobility"`, which is not a member of Remote's enum; the approve PATCHed
`approved_by_remote`, which is *Remote's own* verdict rather than the employer
manager's; and that PATCH carried `approved_by` / `approved_at` /
`decision_reason`, all refused by a closed schema. (The PATCH half was corrected
earlier the same day by the `deny → decline` unit; the create half is this pass.)

**§3 of this document had the right answer the whole time** — *"no `POST`; the
request is created inside Remote's own 'Request Hub' UI, not the partner API"*,
tagged `[CONFIRMED — live]`. `src/remote/restClient.js` cited that very section
as authority for the opposite, and `src/remote/mockServer.js` then implemented
the invented endpoint, so the suite agreed with the code and neither was ever
compared to Remote. Evidence: `docs/REMOTE-VOCABULARY.md` §13.1 and §13.0.

#### What UC-04's input and output now are

| | |
|---|---|
| **Input** | A work-authorization request that already exists in Remote, raised by the employee in the Request Hub, announced by the `work_authorization.requested` webhook and identified by `ticket.workAuthorizationId`. |
| **Output** | The employer manager's verdict, PATCHed back onto that request: `{status: "approved_by_manager", employer_special_instructions?}` or `{status: "declined_by_manager", reason}`. |
| **Our record** | `uc04_authorizations` is the decision's **audit trail**, never the request itself. |

`src/uc04/requestLink.js` resolves the request, and returns one of three states.
The distinction between the last two is the point:

- **`linked`** — Remote has it, it is `pending`, and its `destination_country`
  matches the trip the gates judged.
- **`unlinked`** — Remote answered that there is no such request. An **answer**,
  and the portal's ordinary case. Changes no decision.
- **`unresolved`** — we could not establish *which* request this is: the read
  failed, the request is no longer pending, the destination differs, or two
  candidates fit. A **failure**, and never resolved by guessing.

With no id in hand the request is looked up by `employment_id` + `status=pending`
(both documented query parameters on Remote's own list endpoint) and matched on
destination. Employment alone may not identify a request: two pending trips for
one person are two different requests, and PATCHing the wrong one records an
employer verdict against a trip nobody assessed.

#### A request with no Remote counterpart is carried, not refused

Refusing would make every portal submission fail and turn UC-04 into a use case
that can only ever be observed refusing — the failure shape `docs/BUILD-LOG.md`
§3.30 records as this project's most expensive. Fabricating an id would reinstate
the defect one layer down. The `src/remoteui/` stand-in pattern does not transfer
either: that stands in for a product *surface* and then creates a genuinely real
artifact (a Zendesk ticket); here the artifact would have to be a Remote
work-authorization request, and no API can create one, so a stand-in would have
nothing to stand in with.

So the decision is recorded and settled, and every durable surface says plainly
that nothing was sent: response `code: "approved_no_remote_record"` (never
`executed`), `remoteWrite.transmitted: false`, a durable
`workation_not_transmitted` audit row, and a `remote_result` transmission record
the settled-decision sentence reads explicitly rather than treating as a landed
write.

#### The decline now transmits

Before this pass the decline path made **no Remote call at all**, so the request
the employee raised stayed `pending` — "awaiting manager review" — for ever after
the employer had said no. Remote provides `DeclinedWorkAuthozation` with `reason`
**required**, which is the API stating that a refusal must carry one and must
reach the request. When no note is given, the reason sent states what happened
and invents no rationale.

#### Fail-closed, in one direction only

An `unresolved` link downgrades `ready_for_approval` to `escalate` and can never
do the reverse. An already-escalated request keeps its own reason (first failure
wins) and carries the link reason as a flag. A `blocked` request resolves nothing
at all — Remote is not touched for a hard stop.

#### Open items

- **`remote_request` is not a column.** The provenance block rides on the API
  response and the append-only audit row (which the audit viewer renders); the
  ZAF sidebar reads the durable row, so surfacing it there needs a
  `remote_request` jsonb column on `uc04_authorizations`. Recorded here rather
  than half-done by adding a field the store would silently drop — the same call
  already made for `reason_text`.
- **The n8n graph has no resolution step.** It never called the missing create,
  so it has no defect to fix, but it also cannot link a decision to a Remote
  request or transmit a verdict. That is an n8n change and belongs with whoever
  next touches `workflows/nodes-uc04/`.
- **Nothing here has been exercised against the live Sandbox**, which holds zero
  work-authorization requests (`total_count: 0`, verified live). Every positive
  path above is proven against the mock, whose fixtures are transcribed from
  Remote's own OpenAPI rather than from our code.

## 16. Free-text intake — "somebody texting an AI" (added 2026-08-20)

### The gap this closes

Every route into UC-04 required a human to have already filled in seven
structured fields: the portal form, the n8n graph, and `POST` to the API all
begin at `factors`. There was an LLM seam in `src/uc04/requestParser.js`, but it
runs in the **outbound** direction — structured facts in, display prose out. So
the one thing people most often describe when they picture this use case — an
employee writing *"can I work from Spain for three weeks in September?"* — was
not a supported entry path.

Three of the nine use cases already accepted free text (UC-03, UC-07, UC-08),
and UC-05 accepts a resignation letter body. UC-04 accepted none.

### What was built

| File | What it is |
|---|---|
| `src/uc04/intakeExtractor.js` | The **inbound** LLM seam. Free text in, *candidate* facts out. Retried, source-tagged, rule-based fallback, injectable. |
| `src/uc04/textIntake.js` | `handleWorkationTextRequest()` — assembles the seven factors from three sources, runs the **same** `evaluate()` and the **same** `handleWorkationRequest()` a form submission runs, and turns an incomplete request into a clarification. |
| `POST /api/intake/extract` | Reads a request and returns candidates plus what is still outstanding. Decides nothing, writes nothing. |

No gate was added, changed, or duplicated. `src/uc04/policyEngine.js` remains
the only judgment in UC-04 and sees the identical seven factors whichever door
the request came in.

### The design decision: what happens when the extraction is incomplete

**Free text can never complete a UC-04 request**, and that is not a limitation of
the extractor — it is a property of the request. `src/uc03/uc04Intake.js` already
wrote this down, input by input, when it explained why a UC-03 routing cannot be
dispatched into UC-04: four of the seven required inputs have `source: null`
there.

| Input | Where the text intake sources it |
|---|---|
| `homeCountry` | **The employment record** (`employment.country_code`) — authoritative, and not something prose may overwrite |
| `destination.country` | Read from the message — a **candidate** |
| `startDate` / `endDate` | Read from the message — **candidates** |
| `nationality` | Nowhere. Asked for. |
| `visaType` | Nowhere. Asked for, with its seven allowed values. |
| `jobDuties` | Nowhere. Asked for, with its seven allowed values. |
| `hasContractSigningAuthority` | Nowhere. Asked for. **Absent is not `false`.** |

That table is not restated in the extractor; `NEVER_EXTRACTED_FIELDS` is pinned
to `UC04_REQUIRED_INPUTS` by a test, so if UC-04's requirements move, the test
goes red rather than the two lists drifting.

So an incomplete extraction is the **normal** case here, and what happens next is
the whole design. There were two defensible answers:

**(a) Ask the requester for the missing facts.** ✅ **Chosen.**
**(b) Proceed to a human with the gap named explicitly.**

**Why (a).** Option (b) hands a mobility specialist a case whose deciding gate is
`factors_invalid` — a refusal that describes *our incomplete reading* while
reading as a finding about the employee's trip. That is precisely the
manufactured-refusal shape `docs/BUILD-LOG.md` §3.30 keeps costing this project,
and it spends a specialist's time on something the requester could answer in four
seconds. A workation request missing its visa type is not a hard case; it is an
unfinished one. Escalation is for judgement, not for stationery.

**But the ask is subordinate to the gates, and that is the load-bearing part.**
A clarification is offered **only** when `evaluate()` — the real one, on the real
record, with identity already checked — returns `factors_invalid` as the
**deciding** reason. Every gate above completeness therefore still decides first,
in its own words:

| Situation | Outcome — and no question is asked |
|---|---|
| unverified session | `escalate / identity_not_verified` |
| non-active employment | `escalate / employee_not_active` |
| **sanctioned destination** | **`blocked / sanctioned_region`** |
| no employer workation permission | `blocked / employer_permission_not_granted` |

A message naming Iran is **blocked**, never asked a follow-up question, because
the sanctions gate is position 3 in the ladder and completeness is position 5.
The list of things to ask for is `evaluate()`'s own `factorIssues` array — there
is no second copy of UC-04's requirement list in the intake code.

**And the answers come back through a picker, not through prose.** Each
outstanding input carries its allowed values, taken from `policyEngine.js`'s own
exported `VALID_VISA_TYPES` / `VALID_JOB_DUTIES`. A country must arrive as an ISO
alpha-2 code and is refused otherwise (`"Spain"` never reaches a
`Set.has("ES")`). **No model runs on the answering path at all.** The portal has
a picker precisely to prevent the single most expensive recurring defect in this
repository's history; an extraction has no picker, so the clarification puts one
back.

**A clarification writes no decision, and that is mechanical as well as
semantic.** `handleWorkationRequest()` claims `(use_case, external_ref)` in
`workflow_claims` before its first durable write. If the first turn ran the full
workflow, the second turn — the same request, now complete, under the reference a
chat naturally reuses — would be refused as a **duplicate delivery** and its
decision would never be recorded. A question is not a decision, so it must not
consume the decision's exactly-once claim. The ask itself *is* recorded, as an
`audit_log` row with `action: "clarification_requested"`, so a request that was
answered with a question is still findable. The cost of this choice is one extra
`getEmployment` read per clarified request, paid knowingly.

### How a hallucinated country is stopped

The most dangerous single failure this system could have is a country the model
invented reaching the sanctions gate and the risk matrix. Four checks stand
there, all deterministic and all applied **after** the model answers, to both the
LLM and the rule-based path:

1. **Shape** — a strict validator on the whole reply; an invalid shape retries,
   then falls back to rules (`source: "rule_based_fallback"`).
2. **Canonical form** — the value must be a well-formed alpha-2 code.
3. **Vocabulary** — it must be a code this repo's own curated dictionary can
   produce. The dictionary is *imported* from `src/uc03/classifier.js`, not
   copied, so it derives its restricted entries from `SANCTIONED_OR_RESTRICTED`
   itself; a test asserts every sanctioned code is nameable in prose, because a
   country nobody can name is a gate nobody can trip.
4. **Grounding** — a name mapping to that code must actually appear in the
   request, at a word boundary. The check is on the text; it never asks the model
   whether it made the fact up.

Dates get the same treatment: real calendar date, and **the year must appear in
the request**. This is deliberately stricter than `uc03/classifier.js`, which
fills a missing year in from `new Date().getFullYear()`. UC-03's dates feed a day
count on a 🟢 router; UC-04's feed `start_in_past` and the Schengen 90-in-180
hard block, where the year *is* the answer. The one inference permitted is about
scope, not value: when the text states exactly one year and a month-name date
carries none of its own, that stated year applies — it is written in the request
and there is no second candidate. Two years in the text and a bare date between
them yields nothing.

### An extracted value is marked as one everywhere a human sees it

| Where | What it carries |
|---|---|
| The response | `extraction.provenance` — per factor: `read_from_request_text`, `supplied_by_requester`, `employment_record`, or `not_sourced` |
| `audit_log.details.extraction` | the same block, durably |
| **`summary`** (a real column, so the ZAF sidebar and the API view render it) | a deterministic caveat naming every factor that was read rather than stated, ending *"Confirm them before approving."* |

The caveat is **appended by code, never asked for in the prompt**: a model told
not to add facts must not also be relied on to add this one, and a provenance
warning a model can omit is one that will sometimes be omitted. It rides on the
`sanctioned_region` branch too — that is the strongest claim this system makes
about a request, and the claim a wrong extraction would most plausibly produce.

Form submissions are unaffected: `extraction` is `null` for every existing
caller, so the stored row, the audit row and the summary are byte-identical to
before.

### Why there is no `POST /api/intake/submit`

`handleWorkationTextRequest()` needs an authenticated `session` whose `companyId`
is compared against the employment's — that is UC-04's identity gate. Over HTTP
the only place a session could come from is the request body, and **an identity
taken from the body is a claim**, which `CLAUDE.md` §3 directive 3 forbids
outright. This API has no session source of its own. The surfaces that do — the
portal, which resolves a persona server-side, and any future chat client — call
`handleWorkationTextRequest()` in process, exactly as the portal already calls
`handleWorkationRequest()`. Publishing a submit route that trusted a
body-supplied session would let anyone who can set a JSON field file
authenticated workation decisions against real employments: the same shape as the
finding closed on 2026-08-18 (every GET served unauthenticated). A test asserts
the route does not exist.

`POST /api/intake/extract` is read-gated by the same `requireSignedIdentity`
posture as the GETs, for a second reason: on a public deployment it costs an LLM
call per request, and an unauthenticated LLM endpoint is somebody else's budget.

### Reconciling this with `docs/INTAKE-RESEARCH.md` (read after that file lands)

That research, written in parallel with this build, concludes that Remote's real
intake is a **structured in-product form** with one or two prose boxes bolted on,
and its §6.2 lists `destination_country`, `travel_date_start` and
`travel_date_end` among the fields **"an LLM may never supply"**, under the rule
*"if Remote types the field, the model does not get to write it."*

That rule and this seam do not conflict, and the reason is worth stating
precisely, because reading them as conflicting would be an easy mistake:

- **Where Remote types the field, this seam never touches it.** The precedence
  order in `assembleFactors()` is fixed — a supplied/typed value beats an
  extracted candidate, always, and a candidate can only ever occupy a slot that
  is otherwise **empty**. There is no path by which a reading overwrites a
  stated fact.
- **This seam exists for the channel where no typed field exists at all** — the
  Zendesk/free-text fallback the research itself identifies as "what you fall
  back to when no request object models what you want". In that channel the
  choice is not *typed value vs. extracted value*; it is *extracted candidate,
  clearly marked, vs. nothing*.
- **The marking is what makes that safe.** An extracted destination is never
  presented as a typed one: it is `read_from_request_text` in the provenance, it
  is named in the summary a specialist reads, and the specialist is told in
  words to confirm it. The research's real worry — a model's output becoming
  indistinguishable from the platform's own data — is the exact thing the
  provenance block prevents.

The research's §6.4 also independently confirms the split this section is built
on. Comparing the portal's UC-04 form against Remote's own
`WorkAuthorizationRequest`, it finds that **five of UC-04's gate inputs are facts
Remote's request object does not collect**: `homeCountry` (recoverable from the
employment record) plus nationality, visa type, duty category and prior travel
days (in no Remote object it could locate). It then names the consequence —
*"a gate whose input has no source is a gate that can only ever escalate, which
is exactly the 'structurally cannot succeed' failure."*

Those are, field for field, the source assignments this section made from
`src/uc03/uc04Intake.js`, arrived at independently. And the clarification turn is
a direct answer to the consequence: **the requester becomes the source.** Asking
is what stops those four gates from being ones that can only ever escalate.

### Open items

- **The portal has no text box.** `src/portal/**` was owned by another change in
  flight. The seam and its API path exist and are tested; the one-screen change
  the portal owner needs to make is written up in the report accompanying this
  work and repeated here: add a `<textarea id="uc04-text">` to the UC-04 card,
  send `text` in `BUILDERS.uc04`, and in `server.js`'s `uc04` adapter call

- **`extraction` is not a column.** Like `remote_request` and `reason_text`, the

## 17. The day arithmetic, made reachable from the form (2026-08-20)

Two findings, one root. Both came from the project owner driving the real
portal, and both are recorded here because the *decision* in each case was
correct and the *reachability* was not — which is this repository's recurring
shape.

### 17.1 The defect: a prior-stay row that was half filled in

They continued a UC-03 routing into this form and were refused:

> **Refused** `travel_history_unreadable`
> A prior stay could not be read, so no day count was attempted: **prior stay 1:
> start date missing, end date missing; prior stay 2: start date missing, end
> date missing.**

**The refusal is correct, and it is the good kind.** `buildTravelHistory()`
(`src/portal/server.js`) NAMES an unreadable row rather than dropping it, because
`computeCumulativeDays()` answers NaN for a stay it cannot read and NaN loses
every threshold comparison silently — so one bad row would **clear** a traveller
that the same history would otherwise block. The rows should never have looked
like that.

**The diagnosis is in what the message does not say.** There is no "no country",
so both rows held a country and no dates: a row started and not finished, or —
the whole-row version of the same leak — a row left behind by an earlier
interaction. Reproduced in a real browser before anything was changed: click the
"Two counts, two answers" quick-fill, walk to UC-03, submit a workation,
continue the routing, and **both Spanish stays are still in the form**, silently
counted into a decision about Portugal that nobody stated them for. The
continuation carries five fields (`CARRIED_FIELDS`, `src/portal/uc03Continuation.js`)
and touched nothing else.

**The fix makes the invariant true rather than patching the symptom:**

> After **any** prefill — quick-fill or continuation — no row may be left half
> populated. Either a row is wholly filled or it is wholly empty.

`blankForm(typeId)` empties every control in the form, and both prefill paths
call it first. The alternative — having the continuation name a value for all
eighteen boxes, as the quick-fills do — is more code and, worse, a **second copy
of the form's field list** living in a file the form does not import: add a box
next year and the copy keeps a stale value in it, a failure with no symptom.
Clearing derives the list *from* the form, so a box added later is covered by
existing. Two controls are deliberately skipped and pinned as skipped: the
reference control's `new`/`reuse` radios, because blanking them leaves the form
in neither mode.

The quick-fills' existing guarantee is unchanged and now belt-and-braces:
`test/portalCopy.test.js` still asserts that within a request type every
quick-fill names **exactly** the same key set (an equality, not a superset), and
the four new scenarios below name all eighteen.

### 17.2 The gap: none of the arithmetic was demonstrable

> "I thought we worked on everybody having travel history, whether it is 0 or
> the required variations of days, so that we can easily demo what this system
> is supposed to do under several circumstances."

Correct, and this is the substance of UC-04: the Schengen 90/180 window, the
183/365 tax-residency watch, the union-not-sum overlap rule, and the refusal on
an unreadable stay. **None of it is reachable from the form unless prior stays
are filled in**, and until now exactly one quick-fill stated any.

Five variations now exist. **Every figure below was produced by driving the real
handler**, not estimated — a scenario that refuses when its label says it clears
is worse than no scenario, because it teaches a demo viewer that the system is
arbitrary. All five use Anna Müller (DE, employee, active), destination ES,
1–14 September 2026, `schengen_short_stay`, engineering, no signing authority.

| Quick-fill | Prior stays stated | Decision / reason | Schengen | 183/365 | Flags |
|---|---|---|---|---|---|
| **Low-risk Schengen trip** (existing) | none | `ready_for_approval` / `all_gates_passed` | — | 0 over 0 trips, **"a floor, not a count"** | `a1_certificate_recommended` |
| **Prior stays, well inside** | ES 1–20 Apr (20 d) | `ready_for_approval` / `all_gates_passed` | 34 of 90 | 34 of 183 | `a1_certificate_recommended` |
| **Exactly on the Schengen line** | ES 1 Jun–15 Aug (76 d) | `ready_for_approval` / `all_gates_passed` | **90 of 90 — 0 days of headroom** | 90 of 183 | `a1_certificate_recommended` |
| **Two stays that overlap** | ES 1 Jun–15 Jul (45 d) + ES 1 Jul–10 Aug (41 d) | `ready_for_approval` / `all_gates_passed` | **85 of 90**, from **71** distinct prior days | 85 of 183 | `a1_certificate_recommended` |
| **Over the Schengen limit** | ES 1 May–15 Aug (107 d) | `blocked` / `schengen_90_180_exceeded` | **121 of 90 — over by 31** | **not reached** | `schengen_overstay` |
| **Two counts, two answers** (existing) | ES 1 Jul–14 Aug + ES 1 Oct 25–28 Feb 26 | `ready_for_approval` / `all_gates_passed` | 59 of 90 | **210 of 183** | `tax_residency_watch` |

Four of these rows are worth reading twice:

1. **"a floor, not a count" versus a real 20.** Without a scenario whose count
   changes nothing, "a number appeared" and "a number mattered" are
   indistinguishable across the whole set.
2. **90 of 90 clears.** `schengenPeakDays()` breaches on `peakDays > 90`, not
   `>= 90`. Paired with the block two rows down, this is what shows the line
   sits exactly where the code says it does; a set that only ever demonstrated
   121 of 90 leaves "over" and "at" looking like the same case.
3. **The overlap is the proof of the union rule.** The two stays are 45 and 41
   days and share 1–15 July, so they cover **71** distinct days, not 86. With
   the trip, that peaks at 85 of 90 — allowed. **Summed it would read 100 of 90
   and this request would be blocked**, which is exactly the defect `73920c9`
   fixed. A traveller refused on days they did not spend is not a stricter
   system, it is a wrong one, and this is the row that goes red if the
   arithmetic regresses.
4. **"Not reached" is not "under the line."** The block decides before the
   rolling-window count is taken, and the panel says so rather than printing a
   figure nobody measured.

`test/portalUc04TravelScenarios.test.js` drives each row and asserts the
decision, the reason, the flags and the printed figures, plus a sweep asserting
that every quick-fill's `fails` mark matches the decision it actually produces.

### 17.4 Why this result panel carries no offer — and what its dialog does carry (2026-08-20)

**CORRECTED THE SAME DAY, and the heading above changed with it.** The project
owner: *"I want the answer for everything to always be in the pop up, and then
in this case a recommendation."* That does not overturn the rule below — it
corrects its premise. **An answer is not nothing.** It is the one thing the
requester came for, and it was measured below the fold on every result this
portal produces, at both 1180×900 and 340×740 (`UC-03.md` §21 has the fourteen
numbers). So every decided result now opens with a dialog carrying the ANSWER,
and this section's real subject is narrower than its original title: what this
panel has no **offer** to put underneath it.

The reasoning that follows is unchanged and is why that dialog holds an answer
and a way out and nothing else — an interruption carrying a button nobody can
act on is the thing the rule refuses, and it would refuse it just as firmly
inside an answer's dialog as on its own.

Recorded in full in `docs/use-cases/UC-03.md` §19. In short: a UC-04 result is a
**hand-off** — a named approver decides it (**the customer's own manager**, per §1a;
this sentence said "mobility specialist" until 2026-08-30 and named the wrong party),
and the requester's next step is to wait. There is no action for the reader to take, so
there is nothing to interrupt them with, and a modal carrying nothing actionable
trains people to dismiss modals without reading. `blocked` is a refusal and
offers less than that. Verified in a browser: the Schengen block renders no
dialog (`portal-uc04-schengen-block-no-modal.png`).
