# UC-09 — Off-Cycle Payroll / Adjustment & Tax Withholding

> Inherits `00-FOUNDATION.md`. **Canonical source:** `UC-09 Chatgpt BUILD CASE`'s dual-approval/four-eyes model. **`UC-09 _ DRAFT 1 … Architecture Research`'s approval matrix is explicitly rejected at its Tier 1 and Tier 2** — see the tier-framing note below and `00-FOUNDATION.md` §5, tracking issue #10.
>
> **Tier-framing note (why this UC gets a real execution path when 07/08 don't).** DRAFT 1 specified a **Tier 1: "Direct commit; no human sign-off required"** for low-composite-risk-score adjustments — a real bank payout with zero human involvement — and a Tier 2 with only single sign-off. The ChatGPT doc never proposed a human-free tier at all, requiring four-eyes (requester ≠ approver ≠ payment releaser) for high-risk cases. **DRAFT 1's Tier 1 and Tier 2 are rejected outright, at any composite risk score** — a risk score cannot be trusted to decide *whether* a human is involved, only how many above a floor of two. 🔴 High tier's actual rule is "AI never executes unilaterally," not "AI never executes": 07/08 satisfy it by having no execution path at all; UC-09 satisfies it by requiring independent dual-human approval before every execution, with composite risk scoring surviving only to set escalation *severity above* that floor (e.g., triple approval for extreme/compliance-flagged cases), never whether a human is involved at all.

## 0. Business case

**[VENDOR-PUBLIC]** Off-cycle payroll corrections (relocation top-ups, bonus
corrections, manual withholding fixes) are a named, real category — payroll
errors read as platform-integrity issues for an EOR specifically, the same
trust dynamic UC-06's cutoff-timing cost mechanism rests on, except here the
failure mode is a wrong or fraudulent *payment* rather than a wrong date.
**Cost mechanism**: manual off-cycle processing is slow and error-prone
(gross-to-net math, correct schema mapping, off-cycle limit checks) *and*
carries real fraud/error exposure once money moves — the two failure modes
this spec is built to prevent are wrong amounts and unauthorized/unilateral
disbursement. **[UNCONFIRMED]**: request volume — no public data. **Ships
regardless**: the deterministic gross-to-net validation, ×100 money scaling,
and the dual-approval gate itself — none of these are volume-dependent, they
prevent specific failure modes that are costly per-incident regardless of
frequency.

## 6. LLM reasoning scope
**Does:** map unstructured adjustment requests to the correct Remote incentive/recurring-incentive schema.
**Must NOT:** execute disbursements; approve; bypass dual gate; perform final tax withholding math autonomously.

## 7. Deterministic logic
- Gross-to-net validation.
- **Money ×100** normalization (critical — over/underpayment risk).
- Company off-cycle limit check.
- Manager authorization verification.
- Composite risk score computed **only to set escalation severity above the dual-approval floor** (e.g., a third approver for extreme/compliance-flagged amounts) — never to decide whether the floor applies. Every request gets at least dual approval, with no risk-score value low enough to skip it.

## 8. Human control points
- **Mandatory dual approval, unconditionally** — Customer Admin + Remote Payroll specialist, enforced as segregation of duties: requester ≠ approver ≠ payment releaser are three distinct identities, never the same person wearing two hats. No composite risk score, however low, waives this floor. Extra (triple) approval gate for large amounts or manual tax adjustments, added *above* the floor, not instead of it.

## 9. Failure modes & fallbacks
| Failure | Guard |
|---|---|
| Over/underpayment from scaling error | `money-middleware` ×100 enforced + tests |
| Unauthorized disbursement / fraud | Dual approval + manager-auth check. ⚠️ **The manager-auth check does not exist** (DRIFT-049), so the stated defence against fraud is currently the approval floor alone doing the work of two controls. Decided 2026-08-21: build it, at the corrected §3 endpoint — and state on the screen that it verifies *an authorised manager at this company*, **not** *this employee's manager*, which is what the roster can actually answer (`[P-16]`…`[P-18]`) |
| Miscalculated statutory withholding | No autonomous tax math; human authors |
| **A `net` figure costing the company more than the screen shows** | **Disclosure, never computation.** Remote's `AmountTaxType`: *"`net` … Remote will gross this up."* Remote performs the gross-up, so a figure derived here would be fabricated money. The control is saying the cost is higher and unknown to this system (`[P-21]`, invariant 13). **Not built** |
| **A payment made in Remote's product, bypassing this use case entirely** | **Nothing sees it today.** The floor of two governs requests that come *through* UC-09; an admin creating an incentive directly in Remote's own UI moves money with zero signatures. `incentive.created` is the only thing that can observe it (`[P-28]`…`[P-30]`) |
| **A write that may or may not have landed** | The row stays `executing` and is never retried — deliberate. But **no audit row records that an attempt was made**, the queue reports it *settled*, and nobody is told (DRIFT-053, DRIFT-115). Decided: a durable in-doubt row, a queue reclassification, a named owner, and the adjustment id in Remote's `note` so `GET /v1/incentives` can answer *did it happen?* (`[P-9]`, `[P-12]`…`[P-15]`) |

Over-threshold / manual tax → additional escalation before execution.

## 11. Success metrics
Per `docs/METRICS.md`'s three-bucket framework: % adjustments prepared for
dual 1-click; **dual-approval accept rate** — do both approvers accept the
drafted adjustment as-is vs. send it back? (bucket 2, `≥60%` healthy/iterate,
`<30%` stop, `DEFAULT_THRESHOLDS`; **specified, not yet computed by
`compute.js`** — tracking issue #20); **zero** scaling errors; **zero
disbursements executed under single or zero approval, at any risk score**
(bucket 1 — integrity invariant, not a rate to optimize); zero un-approved
disbursements; cycle time vs. baseline (bucket 3 — pending a real baseline).

> **Status, 2026-08-21: none of the four is computed, and issue #20 understates
> it.** `compute.js` builds its whole report from `cases` and `review_queue`, and
> **UC-09 writes to neither** — deliberately, because `review_queue` has one
> status slot and UC-09 needs two or three independently identified ones. So no
> UC-09 row reaches `computeMetrics()` at all: not the accept rate, not the
> exception ranking, and **not the integrity invariant**, which is the one item
> here that is not a rate.
>
> **Decided:** `uc09_adjustments` becomes a **second source** rather than UC-09
> being forced into `review_queue`. Accept rate is `executed / (executed +
> denied)`; the invariant is a query — any `executed` row whose distinct
> canonicalised approver count is below 2 — reported as a count that must read
> zero. Closes #20. `[P-23]`…`[P-27]`.
>
> **One trap, and the ordering matters.** `findIntegrityBreaches()` flags any
> high-tier row reaching `auto_resolve` on the premise *"high-tier must have no
> execution path"*. **That premise is false for UC-09**, the one 🔴 that
> deliberately has one — so routing UC-09 rows in naively manufactures breaches on
> **correct** payments, which teaches a reader to discount the single alarm this
> use case exists to raise. **`[P-24]` before `[P-23]`.**
>
> **And one measure this list could not have asked for.** The invariant above
> answers *"did we ever pay on one signature?"* for payments **this system made**.

### Defects found and fixed this pass (each reproduced live before fixing)

1. **CRITICAL — concurrent approvals double-executed the payment.**
   `submitAdjustmentApproval()` checked "are we fully approved?" and then
   called `remote.createIncentive()` with nothing in between holding a claim.
   Two approvals fired with `Promise.all` against the last required slot each
   read a row that, by the time they looked, already showed every slot
   filled — both executed. Reproduced live: two concurrent approvals on a
   $5,000 adjustment produced **two** `createIncentive` calls, both reporting
   `"executed"`. Fixed with a `pending_approval -> executing` compare-and-set
   (`adjustmentStore.claimForExecution()`) that exactly one caller can win;
   the loser gets `execution_already_claimed` having still recorded its own
   approval. Verified fixed both as a unit-level race test and as a real HTTP
   race against the running server (`npm run uc09-api`).
2. **Segregation of duties was a byte comparison.** `approval.approver ===
   approver` treated `"Jordan Lee"` and `"  jordan   LEE  "` as different
   humans. Reproduced live over HTTP: the same person filled both required
   roles under a case/whitespace-varied name and the adjustment executed.
   Fixed with a canonicalising comparison in `multiApprovalPolicy.js` (trim,
   collapse whitespace, lowercase — the raw string is still what the audit
   log records, only the comparison is normalised). Re-verified live: the
   same variant is now refused `same_person_cannot_fill_multiple_roles`, and
   a genuinely different person can still complete the approval.
3. **`isFullyApproved()` trusted a missing requirement as zero.**
   `filledCount >= adjustmentRow.approvalSlotsRequired` evaluates `1 >= null`
   as `true` (JavaScript coerces `null` to `0` in a relational comparison).
   Also found: **three independent copies** of this function existed
   (`multiApprovalPolicy.js`'s exported one, a private duplicate in
   `workflow.js` that was the one actually on the execution path, and
   `adjustmentStore.js`'s own method used only by tests) — the correctly-
   floored version was dead code while the money flowed through a different,
   unguarded copy. Consolidated to one definition, now floored at 2
   regardless of what `approvalSlotsRequired` claims, and counts DISTINCT
   (canonicalised) humans rather than filled slots.
4. **Identity gate: `null === null` counted as verified.**
   `session.companyId === employment.company_id` matched when both sides were
   absent. Reproduced live: a request with no company id on either side
   reached `dual_approval_required` instead of escalating
   `identity_not_verified`. Fixed by requiring both sides truthy before
   comparing.
5. **The free-text parser guessed a payment amount out of prose with a
   regex — and the LLM seam that should have replaced it was wired to
   nothing.** `workflow.js` passed `{askJson: remote.askJson, isConfigured:
   remote.isLlmConfigured}` — neither exists on `RemoteClient` — so the LLM
   path never ran and the regex fallback ran on every free-text request.
   Reproduced live: `"Q3 2024 relocation top-up of $12,500.00"` parsed to
   `amount: 3` (the `3` in `"Q3"`) — a 4,000x error. Fixed by giving
   `adjustmentParser.js` real defaults from `shared/llm.js` and removing the
   guessing fallback entirely: an unconfigured or failed LLM call now
   **refuses** (`REFUSED_SOURCE`), and `workflow.js` turns that into
   `escalate` / `amount_not_extracted` — audited, never a guess.
6. **A crash, found while fixing #5.** An unresolvable employment id (a 404)
   combined with a null/invalid amount crashed `handleAdjustmentRequest()`
   with an unhandled `TypeError` (`Cannot read properties of null (reading
   'id')`) inside the payload-building fallback, **before any audit row was
   written** — the request vanished with no record it had ever arrived, on
   the one use case that moves real money. Fixed with an explicit guard
   before `fromRemoteInteger()` (which throws on a non-integer) and a
   null-guard on the payload-building fallback.

### The n8n port — both gaps this section used to flag are CLOSED

An earlier draft of this section claimed `workflows/nodes-uc09/
adjustmentGates.js` still carried defect #4's `null === null` identity risk
and defect #5's regex-based amount guessing. **Both claims were verified
against the node's actual source during the merge and are false — the fixes
landed on the main branch separately** (the 2026-08-17 identity-fix pass, see
CLAUDE.md §4): the identity gate requires both `ticket.session.companyId`
and `employment.company_id` truthy before comparing, and the rule-based
extractor is gone entirely — the node's free-text path can only `refuseToGuess()`
(`REFUSED_SOURCE`), mirroring `adjustmentParser.js`. The lesson stands:
a report about a shared file's state is a claim to verify against that
file, not a fact to copy forward.

## 17. Read as a deliverable, 2026-08-19 — three readers, and an unsourced list deciding how many of them sign

Full write-up: `docs/BUILD-LOG.md` §3.73.

**The three readers are not one audience**, and collapsing them is how a record
ends up answering none of their questions:

| Role | Decision | Turns on |
|---|---|---|
| requester (Customer Admin) | "Is this the adjustment I meant to ask for?" | the amount, its currency, **gross vs net**, the type, the effective date |
| approver (Payroll specialist) | "Should this be paid at all?" | all of the above, plus **why** this many signatures and **who has already signed** |
| payment_releaser (only above the floor) | "Should I release it?" | all of the above plus the **specific** risk that summoned a third pair of eyes |

### C-27, one use case over, on the only path where money moves

C-27 was *"I did not see the amount, the cap, by how much, or by what percent."*
A payment releaser here was told `high_risk_adjustment_needs_triple_approval`
and the flag `high_amount_risk`. The gate cannot raise that flag without the
amount, the threshold, the overage and the percentage; it reported none of them.

`describeApprovalRequirement()` (`src/uc09/approvalView.js`) now reports the
signature requirement dimension by dimension with the figures —
*"15,000.00 EUR exceeds the 10,000.00 EUR high-value threshold by 5,000.00 EUR
(50% over the threshold)"*. Every dimension is reported whether or not it fired,
and an amount that could **not** be established reports `evaluated: false` rather
than a bare `triggered: false` that would read as "inside the limit".

### Two more P7s on the same record

- **Who has signed, while the row is still open.** `describeSignatures()` names
  every signature — and only on a **settled** row. An adjustment awaiting
  approval reported, in full, `"Awaiting approval."` So the second of three
  approvers could not see that the first had signed, who they were, or which role
  was outstanding. `describeApprovalProgress()` reports the roles actually in
  scope (never listing `payment_releaser` as outstanding on a two-signature
  adjustment), who filled which, and — stated **before** it refuses anyone rather
  than only as a 409 — that the humans already on the row may not sign a second
  slot.
- **Gross vs net in the sentence a human signs.** `validateAdjustment()` calls
  `amount_tax_type` *"the only gate in this file whose absence would have been
  silently paid for in cash"* and refuses to default it — because Remote grosses
  a `net` figure **up**, so the company pays more than the number. The summary
  read `Off-cycle bonus: 5000.00 EUR.` and stopped. It now states the basis, and
  the faithfulness judge is given the same fact so a correct adjustment does not
  begin scoring as an invention.

### The unsourced country list — `docs/KNOWLEDGE-SOURCES.md` §1 Test B

```js
const highRiskCountries = ["DE", "FR", "IT"]; // Hypothetical high-tax-complexity countries
```

Three invented country codes raising the required signature count from two to
three on the money path. `docs/KNOWLEDGE-SOURCES.md` names it as the repository's
clearest case of *"if this were wrong, nothing would catch it"*, and §12 item 2
gives the remedy: bind it to a source, or make it impossible to read as a
compliance determination. There is no source.

**The direction of harm is the opposite of the obvious one.** For DE/FR/IT the
list fails safe — it only ever raises the count, and `Math.max(2, …)` means no
entry can lower it. The danger is the inverse: a genuinely high-complexity
jurisdiction **not** on the list collects two signatures where it should collect
three, silently, and nothing said the list was a guess.

**Not fixed by adding countries** — a longer invented list is the same defect
with more rows, looking more authoritative while being no better founded. What
changed:

1. `HIGH_TAX_COMPLEXITY_HEURISTIC` carries the codes **together with**
   `basis: "unsourced_heuristic"`, a null authority, a null version, a null
   review date, an explicit `[PROPOSED] — illustrative, no authority` provenance
   string, and `requiredForARealVersion` — the authority, version, retrieval date
   and named owner-with-review-date a real version needs, recorded as a
   requirement rather than left as a comment.
2. `evaluate()` returns a new `riskBasis` key naming, per dimension, where its
   answer came from. **A new key, not a new flag**: `flags` is compared field for
   field against `workflows/nodes-uc09/adjustmentGates.js`, so adding an entry
   there would silently diverge the two execution paths — a worse defect than the
   one being closed. Renaming the flag was rejected for the same reason.
3. `workflow.js` writes `riskBasis` into the audit row, so the **decision record**
   itself says the list was a guess.
4. The API view says it at the moment the approver acts, and **the absence case
   is visible too**: a country not on the list reports `assessed: false` and
   *"⚠ NOT ASSESSED … which is NOT a finding that its payroll tax is
   straightforward … a country's absence from it means only that nobody looked."*
   That is `docs/GATES.md`'s `passed` versus `not_reached` distinction, one layer
   up.
5. The **floor-of-2 invariant is untouched** and now asserted directly across the
   listed countries plus `CA`, `US`, `null`, `undefined` and an unknown code.

### Still unavailable, and why

- **The list still has no authority.** That is a sourcing task, not an
  engineering one. What is now true is that nobody can read it as a compliance
  determination, and its absence-case can no longer read as a pass.
- **`uc09_adjustments` has no country column**, so an older row cannot name which
  country triggered the jurisdiction dimension. New rows carry it via
  `riskBasis.observedCountryCode`; older ones report it as not recorded rather
  than guessing.

16 new tests in `test/uc09.test.js` — including the **positive** one the collapse
in `CLAUDE.md` §3.30 demands: an unsourced-heuristic country must reach three
slots AND the record must say why the third was required. Each proven
load-bearing by a reverting mutation.

## 18. Why this result panel carries no offer — and what its dialog does carry (2026-08-20)

**CORRECTED THE SAME DAY, and the heading above changed with it.** The project
owner: *"I want the answer for everything to always be in the pop up, and then
in this case a recommendation."* That does not overturn the rule below — it
corrects its premise. **An answer is not nothing.** It is the one thing the
requester came for, and it was measured below the fold on every result this
portal produces, at both 1180×900 and 340×740 (`UC-03.md` §21 has the fourteen
numbers). So every decided result now opens with a dialog carrying the ANSWER,
and this section's real subject is narrower than its original title: what this
panel has no **offer** to put underneath it.

The reasoning that follows is unchanged and is why that dialog holds an answer
and a way out and nothing else — an interruption carrying a button nobody can
act on is the thing the rule refuses, and it would refuse it just as firmly
inside an answer's dialog as on its own.

The rule is written down once, with the full nine-row table, in
`docs/use-cases/UC-03.md` §19: **a result earns a modal when it offers the
reader a next action they would otherwise have to discover by scrolling.** An
offer interrupts; a hand-off says so in place; a refusal is never a modal. A
modal carrying nothing actionable is worse than a paragraph — it teaches people
to dismiss without reading, and the next thing dismissed without reading is a
disclaimer.

**UC-09 is a hand-off.** At least two different people approve before any money moves, three above the money threshold, and never the requester. A modal on this panel would be an interruption whose only possible content is "wait" — and the one place that sentence must not be devalued is the money path, where the disclosures around it are the control.

## 19. The panel named a UUID where a person belongs (2026-08-20)

The project owner, reading the live ZAF sidebar: *"In that Zendesk bar I never
even saw any relevant info of the employee — not even name. That is bad."*
`RemoteClient.getEmployment()` normalises a display name onto every employment
it returns and **none of the nine by-ticket views published it** — the stores
persist `employment_id` and nothing about the person.

Both `GET` views now carry **`employee`** (`src/shared/employeeSubject.js`) and
**`requester`** (`src/shared/requesterSubject.js`), in the one shape every use
case publishes them, so the sidebar needs a single renderer. `employee` is read
LIVE when the panel opens — the same read the action on the screen already
performs before it acts — and reports five states rather than a blank:
`available`, `not_found` (404, an answer *about the record*), `unavailable`
(403/5xx, the request was never evaluated), `not_looked_up` and
`no_employment_id`. A failed read degrades the block and never the case.

### The fields, and the one rejection worth arguing

`full_name`, `status`, `contract_type`, `country_code`.

This is the money path — a real off-cycle payment behind a floor-of-two
multi-role approval — so it is the screen where a uuid instead of a name was
least defensible.

- **`status`** — paying someone who has left, off-cycle, is the classic error
  *and* the classic fraud.
- **`contract_type`** — a contractor is not paid through payroll; an off-cycle
  payroll adjustment against a contractor engagement is a finding in itself.
- **`country_code`** — UC-09's own high-tax list is read against it, and it is
  the jurisdiction the payment lands in.

**Why the employee's salary is NOT here.** The obvious argument for it is a
plausibility check: is a 50,000 adjustment reasonable for someone paid 30,000?
That want is real — and it is a **comparison**, which is a gate, not a display
field. Publishing base pay beside the adjustment amount would ask an approver to
make a proportionality judgement this system has never made, has no threshold
for, and cannot record the result of — on two figures that may be in different
currencies and are both ×100-scaled integers. If UC-09 ought to have a
proportionality gate, that is its own reviewed unit of work with its own tests.
Until it exists the honest screen shows the amount being paid — which **is**
published, from the adjustment row — and not a second number to eyeball against
it.

**Rejected** for the ordinary reason: `job_title` and `start_date`; no gate
reads either.

### `requester` names the four-eyes floor

An authenticated company actor is authorised to **ask**, and the block says that
is precisely why a second, different, entitled approver is required regardless:
*"the requester can never also be the approver."*

**Tests:** `test/employeeSubjectAcrossUseCases.test.js`, plus
`test/employeeSubject.test.js` and `test/requesterSubject.test.js` for the
mechanism.
