# UC-01 — Employment Verification Request Automation & Resolution

> Inherits everything in `00-FOUNDATION.md`. This spec states only what is specific to UC-01.
> **Canonical source:** `UC-01 BUILD CASE ChatGpt — EMPLOYMENT VERIFICATION`. **Supporting:** `Remote UC-01 … Deep-Dive Research`.

## 0. Business case

**[VENDOR-PUBLIC/INFERRED]** Employment verification requests (visa, mortgage,
tenancy proof) are a well-known, high-frequency category across the EOR/HR
industry precisely because they're triggered by third parties (banks,
landlords, immigration offices) on the employee's timeline, not the
employer's — Remote already ships employee self-service letter generation,
which is itself evidence the category is common enough to invest product
engineering in. **Cost mechanism**: the self-service path only covers the
standard case; anything that arrives as a non-standard form, an external
verifier portal, or a third-party direct request still lands in support,
where it's low-complexity but not zero-effort — exactly the shape this
project can absorb without inventing legal judgment. **[UNCONFIRMED]**:
actual ticket volume, and what fraction of verification requests already
fail out of the self-service path into support — no public data exists.
**Ships regardless**: the classify → validate → auto-issue path for the
standard case, and the disclosure-scope whitelist (cost is fixed and low,
value doesn't depend on volume). **Gated on real data**: whether the
non-standard-artifact/third-party-consent paths (§2) are worth building out
further than the current HITL handoff.

## 1. Summary

| Field | Value |
|---|---|
| **Trigger** | Employee / customer admin / third party requests proof of employment (visa, mortgage, tenancy) |
| **Risk tier** | 🟢 Low |
| **Automation boundary** | 100% zero-touch for active employees + standard template; exception-gated otherwise |
| **Primary actor** | Employee (also third-party verifier, customer admin) |
| **Design principle** | *AI interprets. Rules decide. Humans control exceptions. Zendesk manages the case.* |

**Framing (do not lose this):** UC-01 is a **request-routing and resolution** problem, not merely a PDF generator. Remote already lets employees self-generate a standard letter; the CX automation opportunity is the operational handling of requests that *enter support* — non-standard forms, third-party verifications, external portals, ambiguous asks. This framing is what makes the demo credible rather than a toy.

## 2. Trigger & user story

Requests arrive via Zendesk and vary widely:
- "I need a standard employment verification letter." → automatable
- "My bank needs proof of employment." → clarify scope, likely automatable
- "My bank sent this form, please complete it." → uploaded artifact → human review
- "Here's a link to my bank's verification portal." → external URL → human review
- "My mortgage company wants to verify directly." → third-party consent path → escalate

The system must classify which path a request belongs to before doing anything.

## 4. Tools

- **MCP reads:** optional, conversational only (e.g. "what's my employment status?"). Not the retrieval backbone.
- **REST reads (backbone):** employment (including embedded basic-information), legal entity.
- **REST writes:** none to Remote — the deliverable is a generated letter + Zendesk resolution. (No employment state changes.)
- **LLM:** real OpenAI call (`src/shared/llm.js`, `gpt-4o-mini` **by default only** — `OPENAI_MODEL` overrides it, and on the live deployment it does: `/__cx/health` reported `gpt-5-nano` on 2026-08-29, while the four n8n Code nodes still request `gpt-4o-mini`. - **Foundation components used:** `identity-service` (`identity.js`) · `risk-engine` (`riskEngine.js`) · `remote-rest-client` (`restClient.js`, incl. `normalizeEmployment()`) · `audit-logger` (`audit.js`, writes to Supabase `audit_log` when a `pgPool` is supplied) · `case-store` (`caseStore.js`, writes to Supabase `cases`/`review_queue`/`documents`, same optional-`pgPool` pattern). ## 5. Workflow (n8n)

```
Zendesk ticket created
   │ webhook → n8n
   ▼
1. Normalize + identity verify (requester = employee? third party w/ consent?)
   ▼
2. LLM: intent classify + artifact/URL detection + requested-field extraction
   │       (standard? form upload? external portal? third-party? out-of-scope?)
   ▼
3. REST: fetch employment + basic-information + legal entity
   ▼
4. Deterministic policy engine:
   - in scope for UC-01?                        → else REFUSE (no case created)
   - employment status ∈ {active}?              → else EXCEPTION
   - request = standard template scope?         → else HUMAN REVIEW
   - disclosure scope within standard fields?   → else HUMAN REVIEW
   - consent present (third party)?             → else ESCALATE
   ▼
5a. AUTO path (all checks pass):
      render letter (HTML/Jinja2 → PDF via pdf-service)
      → attach to Zendesk → reply → resolve → audit
5b. HUMAN REVIEW path:
      post AI case summary + recommended action to Zendesk (ZAF)
      → specialist decides → audit
5c. ESCALATE path:
      route to HR Ops queue, tag `verification_exception` → audit
5d. REFUSE path (out-of-scope):
      reply with a polite boundary message, create no case, write no audit
```

### 5e. Who the ticket is handed to — and where that is decided

*"Route to HR Ops queue"* above was, until 2026-08-20, a sentence in this
document and a node in the n8n graph — **and nothing at all on the Node path**
(`npm run live`, `npm run livedemo`, the demo scripts). `src/uc01/workflow.js`
did not import `src/shared/escalationRouting.js`, so a UC-01 outcome raised
through it reached Zendesk carrying `verification_exception` and no
owning-team signal of any kind, while the identical decision through n8n was
tagged and assigned by its `Assign Routing` node. Two execution paths, one of
which silently dropped the hand-off — nothing went red, the decision was right,
and the ticket landed in an undifferentiated queue.
`docs/ESCALATION-DESTINATIONS.md` §2.5 found it; both paths now do the same
thing:

| Decision | Tags applied | Group |
|---|---|---|
| `auto_resolve` | `queue_hr_ops` | *none — see below* |
| `human_review` | `queue_hr_ops` | HR Ops |
| `escalate` | `verification_exception`, `queue_hr_ops`, `escalation_hr_ops` | HR Ops |

**Both tags, and why the split is load-bearing.** `queue_hr_ops` answers *whose
queue is this* and goes on **every** ticket; `escalation_hr_ops` answers *did
the automation give up* and goes on only when it did. They were one string
once, applied to everything, which made the escalation rate a constant 100% and
sent routine approvals to escalation queues (`src/shared/escalationRouting.js`'s
header carries the full argument). The queue tag on the auto-resolved ticket is
what gives that rate a denominator.

**No group on the auto path, deliberately.** The ticket is answered and solved;
nobody is waiting for it, so there is no hand-off to make, no queue to place it
in, and no assignment failure to report. Reading `GET /api/v2/groups` there
would add a network call — and an "assignment skipped" note — to the one path
where neither buys anything.

**A missing group is said out loud, never silently skipped.** The group is
looked up (live read first, `src/shared/escalationGroupIds.js`'s synced ids as
the fallback when the account could not be read at all) and **never created** —
`scripts/setup-zendesk-groups.mjs` is the only thing that creates one. When the
group does not exist, the ticket still gets its tags and the internal note
carries `ASSIGNMENT SKIPPED — the Zendesk group "…" does not exist in this
account…`, the same sentence the portal and the n8n node emit. Two of the nine
routing teams are genuinely absent from the live account today, so that is an
ordinary path rather than a hypothetical.

Routing is computed **after** the decision and **after** the durable
`audit_log` write, so it cannot change a verdict and cannot cost a decision its
record — a routing failure costs a ticket its group and nothing more.
`test/uc01Routing.test.js` drives the positive cases: a negative test proves
nothing here, because a path that never routes and a path that correctly
declined to route look identical from outside.

## 6. LLM reasoning scope

**LLM does:** intent classification (`standard_letter`, `non_standard`, `out_of_scope`); detect uploaded doc / image / external URL / form link; detect whether the request is in scope for employment verification; extract any fields the requester explicitly asks to include (`requestedFields`); summarize the request; draft the case-assist note for specialists.

**LLM must NOT:** decide eligibility; fabricate employment facts; disclose compensation or fields beyond the standard template; complete third-party forms autonomously; assert legal guarantees.

---

## 7. Deterministic logic

- In-scope check: requests that are not about employment verification are refused before a case is created.
- Employment status check (`active` gate).
- Request-scope classifier: standard vs. non-standard (rule-based on artifact/URL flags).
- Disclosure-scope enforcement: only standard template fields may auto-populate; requests for non-standard fields (e.g. salary, manager name, home address) route to human review with an `over_scope_disclosure_requested` flag.
- Consent gate for third-party verification.
- Template population is deterministic from fetched fields (no LLM-authored facts).

---

## 8. Human control points

- Any non-standard artifact (uploaded form, external portal) → **specialist review** in ZAF sidebar with AI summary + recommended action.
- Terminated/suspended status → **exception**, never auto-resolve.
- Third-party direct verification without recorded consent → **escalate**.

**Built** — `zaf-app/` + `src/review/`. The sidebar shows the decision, the flags
that drove it, and the reason, then offers approve/decline. The specialist must
enter a reason before either button is accepted; the reason is stored in
`review_queue.notes` and in the `audit_log` details. What it will *not* do,
each asserted by test:

| Case state | Sidebar offers | Why |
|---|---|---|
| `human_review`, still pending | Approve / Decline (with required reason) | This is the HITL gate |
| `escalate` | Nothing — read-only | An escalation needs a specialist working it; a 1-click close would make the safe path a dismiss button |
| Already approved/declined | Nothing | One decision per case; a second attempt is refused, not silently re-run |
| 🔴 high-tier use case | Nothing, ever | Those specs mandate no execution path; this is the backstop if an upstream bug produces an approvable one |
| Employee no longer active | Refuses at approve time | The gate checked this when the ticket arrived; approval can be days later |
| Missing reason | Refused with `reason_required` | Every human decision must be attributable and justified |

Approving re-renders the letter through the *same* `letter.js` as the auto path,
so the field whitelist applies to human-approved letters too — a specialist
cannot approve a wider disclosure than the automation is permitted to make.
Every approve and every decline appends to `audit_log`, carrying the AI's original
recommendation, the human's verdict, and the reason, which is what makes "did
the specialist agree with the AI, and why?" answerable from history alone (§11).

## 9. Failure modes & fallbacks

| Failure mode | Guard / fallback |
|---|---|
| Letter issued for inactive employee | Hard status gate before render |
| Over-disclosure of compensation/fields | Disclosure-scope whitelist; explicit over-scope flag routes to human review |
| Request asks for non-standard field (salary, manager, address, etc.) | `over_scope_disclosure_requested` → human review |
| Out-of-scope / gibberish request | Refuse with a polite boundary message; no case created |
| Wrong legal-entity address | Entity fetched from API, never inferred |
| Misread non-English / ambiguous request | Low-confidence → human review |
| Third-party request without consent | Escalate to consent workflow |

Any failed check → tag `verification_exception`, route to HR Ops queue (out-of-scope requests are refused before this point). The routing half of that sentence is now real on both execution paths — §5e.

## 10. Audit & logging

Two distinct Supabase tables, deliberately not conflated:

- **`audit_log`** — the immutable event trail: `use_case`, `action` (the decision), `actor`, `risk_tier`, `details` (jsonb: requester identity + verification result, classified intent + confidence, fields fetched, policy checks + outcomes, path taken, generated-document flag, and the `caseId` linking back to the current-state row below). Append-only, never updated.
- **`cases`** — the mutable, queryable *current state* of the request: `source`/`external_ref` (Zendesk ticket id), `employment_id`, `requester`, `classification` (jsonb), `decision`, `reason`, `flags` (jsonb), and a `status` that starts at `resolved` / `pending_review` / `escalated` per the decision and is expected to change as a specialist works it (a `updated_at` trigger keeps that honest). One row per request, always created.
- **`review_queue`** — one row per case that needs a human (`human_review` or `escalate`): `case_id`, `status` (`pending`/`approved`/`rejected`), `assignee`, `notes`, timestamps.
- **`documents`** — one row per generated artifact (currently just the letter): `case_id`, `type`, `content` (the HTML), a sha256 `content_hash`, `created_at`.

All four tables have RLS enabled with zero policies (backend-only: only the `postgres` role, used via the app's direct Postgres connection string, can read/write — see `.env.example`). `AuditLogger`/`CaseStore` both keep the SAME in-memory-first design regardless of whether a real database is configured, so `npm test`/`npm run demo` never touch Supabase; `npm run live` does, and reads every row back to confirm it landed.

**Invariant 7 (per-attempt tracing) is built** — this paragraph used to
announce it as a "known gap … not yet fixed", and that had been false for
months. Two things happen, in this order: `src/uc01/workflow.js:247` calls
`audit.logDurable()` at STEP 7, **before** the letter is rendered and before any
Zendesk action, so a decision is durable before anything customer-facing; and
`src/uc01/classifier.js:226` records a `logTraceStep()` for **every** LLM
attempt, success or failure, so a failed attempt does leave a trail — which is
the exact opposite of what this paragraph told its reader. Removed
2026-08-20 as `qa/SPEC-DRIFT-INDEX.md` DRIFT-001; §15's own "Write ordering —
**Real** (F-25)" row four screens below had contradicted it the whole time.

**Invariant 8 (source tagging) is now built**, closing a gap found while
reviewing an external production-AI framework against this project's actual
code: `classifyRequest()` now tags its return value with `source: "llm"` vs.
`source: "rule_based_fallback"`, matching what this use case's own n8n port
(`workflows/nodes/validateClassification.js`) already did.

## 16. Why this result panel carries no offer — and what its dialog does carry (2026-08-20)

**CORRECTED THE SAME DAY, and the heading above changed with it.** The project
owner: *"I want the answer for everything to always be in the pop up, and then
in this case a recommendation."* That does not overturn the rule below — it
corrects its premise. **An answer is not nothing.** It is the one thing the
requester came for, and it was measured below the fold on every result this
portal produces, at both 1180×900 and 340×740 (`UC-03.md` §21 has the fourteen
numbers). So every decided result now opens with a dialog carrying the ANSWER,
and this section's real subject is narrower than its original title: what this
panel has no **offer** to put underneath it.

The reasoning that follows is unchanged and is why that dialog holds an answer
and a way out and nothing else — an interruption carrying a button nobody can
act on is the thing the rule refuses, and it would refuse it just as firmly
inside an answer's dialog as on its own.

The rule is written down once, with the full nine-row table, in
`docs/use-cases/UC-03.md` §19: **a result earns a modal when it offers the
reader a next action they would otherwise have to discover by scrolling.** An
offer interrupts; a hand-off says so in place; a refusal is never a modal. A
modal carrying nothing actionable is worse than a paragraph — it teaches people
to dismiss without reading, and the next thing dismissed without reading is a
disclaimer.

**UC-01 has no result panel to interrupt.** Its answer is posted to the customer's own Zendesk ticket, and its demo surfaces are `src/livedemo/` and `src/chatdemo/`. There is therefore no result for a modal to sit on top of. Recorded rather than skipped, because "across all the use cases" has to mean nine considered answers and not seven — and because if a portal panel is ever built here, the thing to promote is the letter, which is the one item on a UC-01 answer that the reader can act on.

## 17. An `auto_resolve` that carries no reference is refused (2026-08-23, rca-fawf / K3)

`handleVerificationTicket()` will not auto-resolve a request that arrives
without an `externalRef`, and neither will the deployed n8n graph. Every other
outcome is unaffected.

Two reasons, and the second is the operational one:

1. **A letter nobody can trace.** The reference is what ties the decision to the
   request that asked for it — `src/auditview/readStore.js` looks a decision up
   by `details->>'externalRef'` by name. A verification letter stating someone's
   employment to a bank, with no record of who asked for it, is precisely the
   artifact that has to be traceable.
2. **The exactly-once ledger has no key.** The idempotency claim runs only when
   a reference exists (`workflow_claims` is keyed on use case + ref). An
   unreferenced decision therefore skipped the ledger entirely, and a
   redelivered webhook would have issued a **second** letter unopposed — the
   defect real Zendesk ticket #5 already caused once.

**What a refusal looks like.** `decision: "refused"`,
`reason: "unreferenced_request"`. No `cases` row, no `review_queue` row, no
`documents` row, no `audit_log` decision row, no Zendesk reply — refusing rather
than recording an untraceable decision is the whole ruling. One standalone
`audit_trace` row (`uc01.unreferenced_auto_resolve`, `ok: false`) records that it
happened, so the rate is countable. On the n8n graph the same rule is a throw in
"Identity + Policy Gates", upstream of the claim node and every write, with
`RCX OPS · Error Alerts` writing the durable `ops_alerts` row.

**In practice no production surface is affected**: Zendesk supplies the ticket
id, the portal mints a reference, and the third-party door mints a UUID. What
this refuses is a direct programmatic call that omitted one.

Guarded by `test/uc01UnreferencedAutoResolve.test.js` (both paths, each negative
paired with a positive control). Ruling: `qa/HUMAN-DECISIONS-REQUIRED.md` §K3.
Full write-up: `docs/BUILD-LOG.md` §3.91.
