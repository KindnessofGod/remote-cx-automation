## 0. Business case

**[VENDOR-PUBLIC/INFERRED]** Employees approach support with requests that sound
simple ("I need a travel letter," "can I work remotely while
abroad?") but represent very different operational processes underneath —
some are pure documentation asks, some are compliance-heavy work-authorization
questions. **Cost mechanism**: without triage, every one of these lands on a
human to figure out which process it actually is before any work on the
substance can start — pure routing overhead on top of whatever the real
process requires. **[UNCONFIRMED]**: request volume and how often ambiguity
actually causes mis-routing today — no public data. **Ships regardless**: the
classifier + the two genuinely zero-touch letter types (cost is fixed and
low, and misrouting a compliance-heavy request to the wrong human is a worse
failure mode than not automating it at all — a routing judgment is itself a
"knowing when not to automate" artifact). **Gated on nothing further** — this
UC's entire value is the routing judgment itself, not a volume-dependent
automation depth.

## 1. Summary
| Field | Value |
|---|---|
| **Trigger** | Employee asks about travel documentation or working from abroad |
| **Risk tier** | 🟢 Low |
| **Automation boundary** | Classifies request type; auto-issues the two genuinely zero-touch letter types itself; routes everything compliance-heavy elsewhere with a stated reason. **Never** determines tax residency, calculates Schengen/183-day thresholds, or makes an immigration-legality call — those are UC-04/07/08/09's job, not UC-03's |
| **Primary actor** | Employee |
| **Design principle** | *What is this employee actually trying to do, what already exists in the platform, and which process should handle it — UC-03 answers that question, it doesn't answer the compliance question underneath it.* |

## 2. Trigger & user story
Employees ask things like: "I need a travel letter," "can I work
remotely while I am abroad?", "I'm travelling to another country for a few
weeks," "what documents do I need for my trip?" These map to at least three
different downstream processes (simple documentation, formal work
authorization, potential tax/immigration exposure) that look identical from
the first sentence. UC-03's job is to tell them apart and either resolve the
simple case itself or hand the complex case to the UC that owns it, with the
classification reasoning attached so the receiving human/UC doesn't start
from zero.

## 4. Tools

- **REST writes:** none that create new state Remote doesn't already track — at most a `PATCH` acknowledging/routing an existing request, matching the schema-enforced boundary UC-04's research already found (client-side automation cannot originate or finally approve one of these requests; only Remote's own UI/Mobility Team can).

## 5. Workflow (n8n)
```
Zendesk ticket → n8n → identity verify
 → LLM: classify request type (business travel letter / personal no-objection
        letter / formal RWA-workation inquiry / ambiguous) — extraction only,
        never a compliance decision
 → deterministic router:
     - business travel letter, in-scope fields present   → AUTO-ISSUE (§ zero-touch)
     - personal no-objection letter, in-scope fields present → AUTO-ISSUE
     - Schengen/183-day/tax/immigration-flavored request  → ROUTE to UC-04
       (temporary) or UC-08 (tax) with classification + extracted facts attached
     - looks like permanent relocation                    → ROUTE to UC-07
     - payroll/contract-change flavored                    → ROUTE to UC-06
     - ambiguous / low LLM confidence                      → HUMAN REVIEW, no
       auto-route (a wrong route wastes more time than no route)
 → audit every branch, including the routed-elsewhere ones
```

## 6. LLM reasoning scope
**Does:** classify request type from free text; extract itinerary/date facts
to hand to the receiving UC; draft the plain-language letter body from
already-fetched employment fields.
**Must NOT:** determine tax residency; calculate Schengen 90/180 or 183-day
thresholds; make an immigration-legality call; decide whether a routed
request should be approved — UC-03 routes, it does not adjudicate.

## 7. Deterministic logic
- Request-type classification confidence gate (low confidence → human review, never a guessed route).
- Letter-type eligibility check (in-scope fields present, employment active) before auto-issue.
- **Letter-scope check (standard vs. non-standard), before anything is drafted.** A requested letter is
  STANDARD only when every row the template asserts has a value AND nothing outside the template was asked
  for; anything else is `escalate / letter_scope_exceeded` with **no letter drafted**. Default is
  non-standard, and a model may only ever ADD a finding — it can route a request into the human path and
  never out of it. See §18. [CONFIRMED for the field list — Remote's own `TravelLetterRequest`]
- Routing table from classified type → target UC, not an LLM decision.
- Mandatory disclaimer on any issued letter.
- **Sanctioned/restricted-destination hard override**, checked before and independently of anything else about the destination (§9's block list). [PROPOSED — the list is illustrative; see §7.2]
- **Destination-jurisdiction check** against Remote's country registry. **This gate is in the code but was never in this spec** — see §7.1, which is a documentation defect being repaired rather than a new decision. [INFERRED]

### 7.1 The destination-jurisdiction gate — what it actually tests

**Why this subsection exists.** `src/uc03/policyEngine.js` step 7 and its n8n
port refuse any destination absent from `GET /v1/countries`. Nothing in §7, §9
or §12 of this document ever asked for that gate: the spec specifies a
**sanctions block list only**. The gate entered during the build. It is not
wrong — the argument for it is below — but *a gate that exists in code and not
in the spec is a documentation defect regardless of whether the gate is right*,
because nobody can review a control they cannot find. Recorded here 2026-08-17.
Full evidence base: `docs/research/COUNTRY-SUPPORT-SEMANTICS.md`.

**What the gate tests.** Whether the destination's ISO alpha-2 code appears in
Remote's country registry — no more than that. It does **not** test whether
Remote "supports" the country in any colloquial sense, and it makes no
statement about travel legality, visas, or tax exposure. [CONFIRMED — this is
literally the predicate: set membership.]

**Why membership, and not `eor_onboarding: true`.** The two are genuinely
different questions, and Remote documents them separately in its own words:

| | Registry membership (**what UC-03 uses**) | `eor_onboarding: true` (**rejected**) |
|---|---|---|
| Remote's own definition | *"The countries present in the list are the ones where creating a company is allowed."* [CONFIRMED — <https://developer.remote.com/reference/get_v1_countries.md>] | *"A boolean that indicates whether Remote supports EOR onboarding in this country."* [CONFIRMED — <https://developer.remote.com/docs/working-with-countries.md>] |
| Live size, 2026-08-17 | 224 of 249 ISO codes | 91 of 224 |
| What it excludes | 26 codes: the sanctioned/embargoed set plus uninhabited and dependent territories | 133 codes, including French and US overseas territories and most workation destinations |
| Subject of the question | *may a company exist in this jurisdiction* | *can Remote employ someone here* |

Neither answers UC-03's actual question — *may an already-employed person visit
and be present here for N days* — and the API exposes no field that does.
[CONFIRMED — no row field in `GET /v1/countries` concerns visits or presence.]
Registry membership is nonetheless the defensible input, for two reasons:

1. **Its exclusions are the sanctions set.** The 26 absent codes are, with near
   perfect precision, the sanctioned / signup-prevented jurisdictions — which
   is exactly what a travel router wants to refuse, and is corroborated by
   Remote naming that same exclusion rule elsewhere in the API (*"COR-supported
   countries exclude sanctioned and signup-prevented countries"*). [CONFIRMED —
   live capture + llms.txt]
2. **`eor_onboarding` would refuse ordinary travel.** It is `false` for
   Martinique, Guadeloupe, Réunion, Guam and the US Virgin Islands — meaning a
   **French employee's trip to Martinique**, an integral part of the French
   Republic, would escalate as an unsupported destination. It is also `false`
   for Montenegro, the Maldives, the Bahamas and Barbados. An operations lead
   reading that flag on such a ticket would conclude the automation is broken,
   and would be right. [CONFIRMED — live `eor_onboarding` values]

`eor_onboarding` is therefore **not a gate input in UC-03 and must not become
one.** A positive test pins this: `test/uc03.test.js` asserts that Montenegro
— present in the registry, `eor_onboarding: false` — reaches `auto_resolve`, so
a later "tightening" to the EOR flag fails the suite instead of silently
refusing legitimate travel. `test/n8nUc03Parity.test.js` asserts the same of the
n8n port. [CONFIRMED — the tests exist and pass.]

**Naming.** The flag and reason are `destination_jurisdiction_excluded`. They
were `unsupported_destination` until 2026-08-17; that string asserted "Remote
does not support this country", which is a claim the gate cannot make and which
a specialist could not act on. Renamed in code only — `audit_log` is
append-only, so rows written before the rename keep the old string, and
`rankExceptionReasons()` in `src/metrics/compute.js` folds the two onto the
current name explicitly so one cause is not reported as two.

**Fail-closed.** An absent, empty or unparseable countries response confirms
nothing, and yields `escalate`. This matters more than it looks: UC-03's
`auto_resolve` posts a public reply and solves a real ticket. [CONFIRMED —
tested in both copies.]

**Known limitation, carried openly.** Membership excludes 26 jurisdictions and
nothing else, so the gate is *narrow* — after it, UC-03 will auto-answer
documentation questions for ~198 jurisdictions where Remote has no entity and
no local counsel. Two things bound that risk: the auto path issues an
**informational answer with a mandatory disclaimer**, never a formal Travel
Support Letter (`letterIssued: false` always, §15), and anything phrased as
*working* from abroad routes to UC-04 before this gate is ever reached. A
registry built for company creation is being borrowed as a sanctions screen;
that is a coincidence of today's data, not a contract, which is why §7.2's
local list is kept as well. [INFERRED]

### 7.2 The local sanctions list, and why it duplicates the registry

`SANCTIONED_OR_RESTRICTED` is checked **first**, before §7.1's gate. Every code
in it is already absent from the registry, so on today's data it is redundant —
**and that is the argument for keeping it.** A control that only works while an
upstream list stays correct is not a control, and the registry's stated
membership rule is about company creation: a jurisdiction could become
company-creatable while remaining a travel-compliance problem. [INFERRED]

The list holds `CU, IR, KP, SY, RU, BY, MM, VE, AF, IQ`. **`AF` and `IQ` were
added 2026-08-17 from Remote's own exclusions, not from any judgement made
here**: among sovereign states, the registry's 26 exclusions are a strict
superset of the eight codes originally hand-written, additionally omitting
Afghanistan and Iraq. [CONFIRMED — live 2026-08-17: `AF`, `IQ` and `RU` are all
absent from the 224 rows.] The change is strictly more restrictive, so it is
fail-closed-safe by construction; what it alters is *which gate fires* and
therefore which reason a specialist reads — a sanctions decision now says so,
instead of a registry lookup catching it one gate later. The list remains
**[PROPOSED]** overall: it is an illustrative demonstration subset, not Remote's
authoritative compliance list, which this portfolio has no access to and which
production would source from the compliance team on a stated review cadence.

## 8. Human control points
- **The informational answer OFFERS the formal letter, and the offer is not a control point — it is a way of REACHING one.** Accepting it (`POST /api/cases/:id/request-letter`, by the traveller's own authenticated session) records a second decision and drafts the letter; it issues nothing. Every letter still stops at the signature below. See §15.3.
- **The formal travel letter is the one signature this use case has.** It is drafted, never auto-issued, and released only by a named Travel & Mobility Support specialist (`uc03:travel_support_specialist`) — `POST /api/cases/:id/signoff`. See §15.2 for the four outcomes that deliberately have no control at all. **The signature is Remote's own rule, not this project's caution**: `TravelLetterRequest.status` documents `approved_by_remote` as *"Fully approved by both the manager and Remote. The travel letter will be generated"*, and no API client can set that status. §18.1. [CONFIRMED]
- **A letter the template cannot express is not drafted at all**, and that is a fifth outcome with no control: `escalate / letter_scope_exceeded` asks a specialist to WRITE a letter, not to sign one. §18.2.
- Ambiguous/low-confidence classification → human review before any letter issues or any route is taken. This is a re-reading of the request, **not** a sign-off: nothing is drafted, and the sign-off route refuses it by its own name (`classification_unconfirmed`).
- Every routed-elsewhere case is visible with the classification + extracted facts attached, so the receiving human/UC isn't starting from raw ticket text.
- Same escalation backstop as every 🟢 UC: inactive employment → exception, never auto-issue.

## 9. Failure modes & fallbacks
| Failure mode | Guard |
|---|---|
| Compliance-heavy request misrouted as a simple letter | Classifier trained/gated to route Schengen/tax/immigration keywords to UC-04/08 by default, never auto-issue on ambiguity |
| Auto-issuing a letter for a restricted/sanctioned destination | Hard block list checked before issue, same as prior compliance-engine draft's intent, kept as a deterministic gate not a judgment call |
| Wrong route chosen | Low-confidence → human review, never a guessed route; routed cases carry the classification reasoning so a human catches a bad route fast |
| Auto-answering for a jurisdiction Remote's own registry excludes | Destination-jurisdiction gate (§7.1) — membership in `GET /v1/countries`, checked after the sanctions override. Fails closed: an absent, empty or unparseable list confirms nothing and escalates |
| A specialist signs a letter that silently omits what the requester asked for | Letter-scope gate (§18.2). The template has fixed rows and no free-text block, so an addressee, a passport number or a required sentence used to be dropped without trace. A non-standard request now escalates with the findings attached and **no document written** — refusing to ISSUE a bad document still leaves the bad document written |
| A model talks a request out of the human path by calling it standard | Structural, not asserted: `standard` is the ABSENCE of findings and there is no input field meaning "this is standard". The model supplies a LIST OF PROBLEMS, unioned with a deterministic scan; an unusable list or an unreadable request is itself a finding (§18.3) |
| The countries read succeeds but yields an unusable list (the F-25 class) | Rows are placed on the alpha-2 axis with an asserted `/^[A-Z]{2}$/` shape check, never an `??` fallback chain that can smuggle in the alpha-3 `code`; an unplaceable row is dropped rather than guessed at. The audit row records the set **as the gate saw it**, so an empty list is visible instead of looking like a policy outcome |

Seven markers, each citing the property on Remote's own `TravelLetterRequest` (or the Visa Code Handbook clause) that says the field is real, plus a template-completeness check and a re-applied confidence floor. `standard` is the absence of findings and there is no input meaning "this is standard", so a model can only ever route a request INTO the human path. See §18.
- `confidenceFloor.js` — one constant, extracted so `policyEngine.js` and `letterScope.js` are not an import cycle. `policyEngine.js` re-exports it; every existing importer is unchanged and there is still one definition.
- `letterOffer.js` — the pure gate over the OTHER direction: which answered inquiries may become a formal letter request, what the offer promises, and what each non-offerable case is instead. Plus `letterClaimRef()`, which is why a second decision on one ticket is recordable at all. See §15.3.
- `signoffPolicy.js` — the pure gate over that one action, and over which cases may have it at all (§15.2). Same split as `src/uc05/signoffPolicy.js`: `policyEngine.js` decided once whether a letter should be DRAFTED; this decides, possibly days later, whether one named human may RELEASE it.
- `caseAttachments.js` — a case's `review_queue` row and its documents read memory-first-then-pool, the same precedence `CaseStore.findById()` already uses. The server read both straight off the in-memory arrays, which is correct in a seeded run and empty on the deployment, where the API and the workflow are different processes. That was survivable while the panel only displayed them; it is not survivable now that a sign-off refuses without them.
- Shared additive edits (pre-existing, not from this session): `RemoteClient.listCountries()`, mock `GET /v1/countries` + `COUNTRIES` fixture, `CaseStore.findById()` / `findByExternalRef()` (memory-first, then pool — the cross-process pattern), `"uc03-api"` npm script.
- `workflows/nodes-uc03/travelRouterGates.js` — an n8n Code-node port exists and is parity-tested against `policyEngine.js`/`workflow.js` by `test/n8nUc03Parity.test.js` (19 tests, all passing). This corrects an earlier version of this section, which said the n8n port was not built; it was, just not reflected here. **Not verified against a live n8n instance or a live Zendesk trigger from this session** — parity here means "matches the Node reference implementation," which per §7.1 is not the same as "matches the real Remote API."

**Since built, and this paragraph corrected accordingly** (2026-08-17): the **n8n workflow port** exists and is active — `WORKFLOW_UC03_ID`, "Travel Router Gates" (`workflows/nodes-uc03/travelRouterGates.js`), kept in lockstep with `src/uc03/` by `test/n8nUc03Parity.test.js`. **Still deliberately NOT built** (matching the staged order every use case in this repo follows): PDF rendering, and a Slack/any other notification path. The specialist sign-off that used to head this list is now built — see §15.2, which also records the one wire still missing (the sidebar loader) and why the n8n path cannot yet produce a signable letter.

### 15.2 The sign-off surface: one signature, and four refusals

`docs/APPROVAL-QUEUE.md` §0 pointed a live scan at production and put UC-03 in
its own category:

> `no_approval_surface` — **correctly ticketed, correctly queued, and no route
> anywhere records a sign-off.**

That was true, and the obvious fix would have been wrong. Read against the
database on 2026-08-19, every UC-03 row in `review_queue` waiting on a person —
all four, tickets #48/#49/#50 and the reference `9002` — was
`route_to_uc04 / work_authorization_requested`. Not one of them is something a
person signs.

| UC-03 cases in production | 7 | |
|---|---|---|
| `auto_resolve / all_gates_passed` | 3 | resolved, nobody needed |
| `route_to_uc04 / work_authorization_requested` | 4 | **all four of the stuck rows** |
| `human_review / formal_letter_requested` | **0** | the one signable outcome — never yet reached live |
| `escalate` | 0 | |
| `documents` of type `travel_support_letter` | **0** | no letter has ever been drafted in production |

So the stuck list was measuring a real blockage and naming the wrong remedy. A
`route_to_uc04` case does need a human, and what that human owes is an
**outreach**, not a signature: the employee has to raise a work-authorisation
request in Remote's own Request Hub, because no API can create one on their
behalf (§16). An approve button on those four rows would have been a 🟢 router
minting a 🟡 work authorization by click — the exact dispatch §16 argues
against at length.

**What genuinely could not be finished is the formal travel letter.** Gate 11
exists for one stated reason, in its own `means`: *"a letter is never sent until
a specialist has read it and signed it off — that sign-off is the whole reason
this stops here."* The letter is drafted on the legal entity's letterhead, it
carries base compensation, it is written for a destination authority — and until
this work it could never leave the building. `audit_log` carried
`letterIssued: false` on every UC-03 row ever written, because no code path
anywhere could set it true.

**What was built** (`src/uc03/signoffPolicy.js`, `submitTravelLetterSignoff()`
in `workflow.js`, two POST routes in `server.js`):

| UC-03 outcome | Signable? | What the refusal says instead |
|---|---|---|
| `human_review` / `formal_letter_requested` | **YES** — one signature | — |
| `human_review` / `low_confidence`, `confidence_unknown` | no — `classification_unconfirmed` | a reading of the request is owed, not a signature; nothing was drafted |
| `route_to_uc04` | no — `no_signoff_path` | names the Request Hub filing that IS owed |
| `escalate` | no — `no_signoff_path` | worked on its own ticket; an escalation is never closed from a sidebar |
| `auto_resolve` | no — `no_signoff_path` | answered informationally; there is no artifact and never was |

The approver is **one named Travel & Mobility Support specialist** — the team
`src/shared/escalationRouting.js` already assigns UC-03 to, and its row's own
`source` cites the held letter as the reason. The role is declared in the shared
vocabulary as `uc03:travel_support_specialist`
(`src/review/approverEntitlement.js`'s `USE_CASE_ROLES`), never invented locally,
so the sidebar's role names and the operator's grant strings cannot drift. The
gate follows the discipline the rest of the repo already has: identity comes from
`resolveApprover()` and never from the request body; entitlement is consulted
last and can only refuse; an escalation is visible and not actionable; a decided
case cannot be decided twice; and the employment record is **re-read at sign-off
time** — the gate asked "was this true?", a letter asserting current employment
to a border authority has to ask "is it still?".

`actionable` is answered server-side on both GET routes and the panel only
renders it, along with `approvalRoles` in the shape
`docs/SIDEBAR-APPROVAL-ROLES.md` §3 specifies.

**A defect this found, and fixed.** `workflow.js` branched its letter rendering
on the DECISION rather than the reason, so all three routes to `human_review`
drafted a formal travel letter. Driven with a 0.05-confidence classification it
produced a letter reading *"business travel to **null**"* beside a real
employee's real salary, stored durably as a document, for a request that never
mentioned a letter. That document is precisely what a naive sign-off surface
would have asked somebody to sign. The fix is in the drafting, not only in the
gate: refusing to ISSUE a bad document still leaves the bad document written.

**Two things still open, both outside this unit of work.**

1. **The sidebar loader.** `zaf-app/assets/main.js`'s `loadUc03` hard-codes
   `actionable: false` in the browser — the only one of the nine loaders that
   decides it client-side — and supplies no `post`. It fails closed, so it is
   safe, and it is now also wrong: the server has an answer. Wiring it is a
   one-function change in that file, and the API is reachable meanwhile.
2. **The n8n path cannot produce a signable letter.** `WORKFLOW_UC03_ID` writes
   `audit_log` and updates the ticket; it writes no `cases` row, no
   `review_queue` row and no `documents` row, and it renders no letter — its
   `human_review` branch flags the ticket for "Formal Letter Review" and drafts
   nothing. A case with no drafted letter is refused `letter_missing` rather
   than issued unseen, which is the correct fail-closed answer and not a
   working hand-off. **Parity is unaffected**: the port is
   `travelRouterGates.js`, a copy of `evaluate()` only, and nothing in it
   changed — `test/n8nUc03Parity.test.js` still passes 59/59.


### 15.1 Driven from the portal, 2026-08-19 — what a human at the end of a UC-03 decision could actually see

Full write-up: `docs/BUILD-LOG.md` §3.41. Found by starting

spec says they should, including the positive one (`auto_resolve`), and the

auto-resolves, and the audit row records the set the gate actually tested.

What did not survive checking is what happens *after* the decision.

**1. The request itself was never recorded. FIXED.** `cases` has carried a

origin country, no dates, no employment id. The payload had been in

### 15.3 The answer offers the letter — one question, one request

**The owner's observation:** *"the system is meant to be intelligent, because
they are qualified — even though they asked a question, there should be an
option to get a letter. Won't anybody travelling for business need a letter?"*

They were right, and the measurement agreed: `documents` in production held
**3 `travel_informational_response` rows and 0 `travel_support_letter` rows.**
Nobody had ever got a letter out of this system. An employee who wrote *"I'm
travelling to Spain for a client meeting from 14 September to 2 October, can you
confirm business travel is fine?"* passed every gate, was answered
informationally — and, on discovering they needed the letter for a visa
appointment, had to submit a **second request**, phrased so the classifier
detected a letter ask, starting from the beginning.

Worse than the friction, and found while building this: on the n8n path that
second request **could not be a reply to the same ticket at all**. The graph
claims `(UC-03, <ticket id>)` in `workflow_claims` on the first run, so a reply
that re-triggers it is a duplicate delivery and stops silently at
`Duplicate Delivery — Stop`. The informational answer's own closing line told
the employee to *"reply to this ticket and a specialist will review and issue
it"*, which on the live path is advice to do the one thing that produces
nothing. That line is now the offer instead.

#### What was built

`src/uc03/letterOffer.js` (pure policy) + `acceptTravelLetterOffer()` in
`workflow.js` + `POST /api/cases/:id/request-letter`. On `auto_resolve /
all_gates_passed` the decision now carries a `letterOffer` block — what the
letter is, that a specialist signs it before it is issued, and **the destination
and dates it would carry**, so accepting is confirming a trip the employee has
been shown rather than agreeing to an unseen document. Accepting re-runs
`handleTravelInquiry()` on the STORED classification with the letter flag set,
and lands where a typed-out letter request lands: `human_review /
formal_letter_requested`, drafted, queued, awaiting §15.2's signature.

#### The line, and the three things that hold it

**The offer is not the letter.** `auto_resolve` is 🟢 — validate, execute,
resolve — and the formal letter is deliberately not on that path: legal-entity
letterhead, base compensation, read by a consulate or a border officer. Nothing
on the accept path can issue one:

1. it produces a `human_review` decision, and `submitTravelLetterSignoff()`
   remains the only code in the repository that sets `letterIssued: true`;
2. `letterOffer.js` names neither `renderTravelLetterHtml` nor
   `resolveWithLetter` — asserted structurally, on the source with comments
   stripped, the same check UC-08's no-execution-path guarantee uses;
3. a test drives the whole chain and asserts that after acceptance **no** audit
   row anywhere says a letter was issued, until the signature.

And it cannot be reached from a classification the router distrusted, three
independent ways: only `all_gates_passed` carries an offer, and that outcome is
below the confidence gate; the confidence figure travels with the carried
classification, so the gate decides again on the same number; and STEP 5 drafts
only when the **re-run's own** reason comes back `formal_letter_requested`. A
hand-forged `auto_resolve` row carrying a 0.05-confidence reading is pinned by
test: it re-decides as `low_confidence` and drafts nothing.

#### Why accepting creates a NEW case rather than reopening the answered one

Both were defensible; this is the argument, recorded because the alternative is
the one a reader will ask about.

| | new case | transition the old one |
|---|---|---|
| `audit_log` | two decision rows, joined by `offerAcceptedFrom` | two decision rows and one case row that disagrees with them |
| `cases.decision` | each row states the decision that produced its own document | `auto_resolve` rewritten to `human_review`, so `src/metrics/compute.js`'s 🟢 auto-resolve rate falls retroactively for work done correctly |
| documents | the answer hangs off the answer, the letter off the letter | two artifacts of different kinds under one `decision` column that can only describe one |
| approval queue | a `review_queue` row created with its case, as every other case does | a queue row minted after the fact against a case recorded as needing nobody |
| the truth | two decisions, at two times, about two questions — *may I travel?* and *will you certify it?* | one row pretending the second question was the first |

The link is not lost: the letter decision's audit row carries
`offerAcceptedFrom: <answer case id>`, and its classification carries
`formalLetterRequestedVia: "offer_accepted"` — so a `true` a **person** set can
never be misread as a `true` a **model** read.

#### The idempotency key is the ticket's, and the letter's is not

`workflow_claims` is keyed `(use_case, external_ref)` and the informational
answer already claimed the ticket. A second decision under that ref is refused
as a duplicate delivery — the letter would be dropped in silence, which is the
worst of the three available failures. UC-04's `textIntake.js` met the same wall
from the other side and answered it by making the clarification turn write
nothing at all; that is not available here, because both turns are decisions.

So the ticket id and the claim key stop being the same string:
`ticket.claimRef` defaults to `externalRef` for every inbound request and is
`<ref>#letter` for an accepted offer. The ticket id still goes on the case row —
it is where the conversation is, and it is what Zendesk and the sidebar look up
by. Two simultaneous accepts are separated by the **primary key**, not by the
follow-on lookup, and a test drives them concurrently to prove it: one letter,
one decision, from two clicks.

#### Is every `all_gates_passed` case letter-eligible? Yes on policy, no on data

Read down `GATE_SEQUENCE`: rungs 1–10 decide the answer and the letter
identically, and only the last rung differs (11 `formal_letter_requested`
vs. 12 `all_gates_passed`). So there is no trip this router will answer but
must not certify, and the offer is uniformly available — which is why the
informational answer states it unconditionally.

What is **not** identical is the data. The letter goes out on the employing
entity's letterhead, which the auto path never reads, and
`remote.getLegalEntity()` returns null on a 404. Rendering anyway would put
`undefined` where the company name goes; throwing would lose a decision that had
already been made, to a read that only ever fed a document. So an unreadable
letterhead now leaves the case exactly where it is — `human_review /
formal_letter_requested`, queued — with **no letter drafted**, the reason said
out loud on the queue entry (*"NO LETTER WAS DRAFTED … what is missing is the
letterhead, not the permission"*), in the audit row (`letterDrafted: false`,
`letterDraftBlocked`), and in the API response. `signoffPolicy.js` already
refuses that state by the name it was written for: `letter_missing`, *"re-run
the request rather than issuing an unseen document"*.

One eligibility rule was considered and deliberately **not** added: withholding
the offer for a trip that has already ended. The ladder has no such gate for the
answer, so adding one only for the letter would make the letter path stricter
than the router — and a letter is legitimately wanted after the fact (expense
substantiation, a later visa application citing prior travel). Refusing that
would be a new failure, not a fix.

#### `letterDrafted` on the audit row

`letterIssued: false` was the only thing a UC-03 decision row said about the
letter, so *"asked for one and got a draft"* and *"asked for one and got
nothing"* were indistinguishable in history. They are opposite situations for
the specialist who picks the case up. Both fields are now recorded.

#### What still has to be wired, by the owners of those files

The mechanism and its route exist; two surfaces render nothing yet, and both are
one-function changes in files this unit of work does not own:

- **`zaf-app/assets/main.js`** — `loadUc03` hard-codes `actionable: false` and
  ignores the server's answer. It should read `view.actionable` /
  `view.actionableReason` (already answered server-side by §15.2) and render
  `view.letterOffer` as a read-only block when `offered` is true. The sidebar's
  reader is a specialist, not the traveller, so the offer belongs there as
  *information about what the employee may still ask for* — **not** as a button
  a specialist can press on the employee's behalf. Accepting requires the
  traveller's own authenticated session, and the API refuses without one.
- **`src/portal/server.js`** — its `uc03` adapter already holds
  `persona.session`, and the workflow result now carries `letterOffer`. It
  should render the offer on the decision panel and, on accept, call
  `acceptTravelLetterOffer({ caseId, session: persona.session }, …)` with the
  same store it submitted through. That is the surface where a real employee
  can take the offer today.

#### Tests

`test/uc03LetterOffer.test.js`, 14 tests, hermetic. The headline is a **positive
chain that had never run**: answer → offer → accept → drafted → signed off →
issued, asserting the delivered bytes are the signed bytes and the audit row
carries the document's own sha256. Beside it: an accepted offer never issues; a
terminated employee re-decides to `employee_not_active` and drafts nothing; an
unreadable letterhead drafts nothing and the sign-off then refuses
`letter_missing`; a low-confidence case has no offer on either guard; a
`route_to_uc04` and an `escalate` case are refused with a sentence naming what
they actually are; only the traveller may accept, and an unauthenticated accept
writes nothing at all; and the two idempotency tests above.

## 16. `route_to_uc04` says what it did, not what it did not

**The owner asked: *"How is this supposed to work? Am I supposed to just go to
UC-04 and see what was forwarded to it?"*** The answer is no. Nothing is
forwarded. `workflow.js` builds a handoff event, records it in `audit_log` and
returns it — no UC-04 record is created, nothing enters a UC-04 queue, and a
person who goes and looks at UC-04 finds an empty queue, correctly.

The system said otherwise. Two lines contradicted each other, and the false one
was the one the customer read:

| Where | What it said |
|---|---|
| `workflow.js` (comment) | *"recorded and returned for inspection, **never dispatched to UC-04**"* — accurate |
| `policyEngine.js` rung 5 `means` (rendered to the requester) | *"It **has been handed to** the work-authorisation case (UC-04)"* — false |

This is the **inverse of `docs/CORRECTIONS-LOG.md`'s P7**. P7 is the system
saying *less* than it knew while every sentence stayed true. Here it said *more
than it did*, and the overstatement lived in the customer-facing string while
the truth sat in a code comment nobody outside the repo reads. Logged as
**C-31**, and it opened a new pattern row, **P9**.

### The fix is the wording, not a dispatch — three independent reasons

Any one of these is sufficient on its own. They are recorded here because
"just forward it to UC-04" is the obvious repair and it is wrong.

1. **There is nothing to dispatch into.** `POST /v1/work-authorization-requests`
   does not exist — `docs/REMOTE-VOCABULARY.md` §13.1, `[CONFIRMED]` from
   Remote's own `llms.txt` (77 `post_…` entries, none for this resource) and
   from the resource's own description: a `WorkAuthorizationRequest` is
   *"submitted by an employee"*, `pending` means *"awaiting manager review"*,
   and the update body is a closed `oneOf` over approve/decline. The contract is
   **create-by-employee, decide-by-API**. `src/uc04/requestLink.js` exists
   because UC-04 used to invent the record it decided on (`docs/BUILD-LOG.md`
   §3.66); a UC-03 dispatch would reintroduce that defect one use case upstream.
2. **It would be a tier escalation performed by automation.** UC-03 is 🟢
   (validate → auto-execute). UC-04 is 🟡 (AI prepares → **a human approves** →
   execute). A 🟢 workflow that manufactures a 🟡 record has created the *object*
   of a human approval with no human anywhere in it — `CLAUDE.md` §3 directive 2.
   UC-04's `ready_for_approval` is a one-click specialist approve, so the
   manufactured record would arrive already pointed at a real decision.
3. **The data does not exist.** Of UC-04's seven required intake inputs
   (`request_completeness` → `blocked / factors_invalid`), UC-03 can source
   **one** reliably, **two** best-effort, and **four** not at all:

   | UC-04 input | UC-04's refusal slug | UC-03's source |
   |---|---|---|
   | `homeCountry` | `missing_home_country` | ✅ the employment record UC-03 already reads (authoritative, not the ticket text) |
   | `destination.country` | `missing_destination_country` | ⚠️ the classifier — **and may be null**: the routing gate is ladder position 5, the destination gate is 6 |
   | `startDate` / `endDate` | `missing_dates` | ⚠️ the classifier — same, the duration gate is position 9 |
   | `nationality` | `missing_nationality` | ❌ never — not on `normalizeEmployment()`'s output, not in the classifier's schema |
   | `visaType` | `invalid_visa_type` | ❌ never — a closed seven-member enum nothing in UC-03 asks about |
   | `jobDuties` | `invalid_job_duties` | ❌ never — a closed seven-member enum |
   | `hasContractSigningAuthority` | `missing_signing_authority` | ❌ never — must be a **boolean**; absent is not `false`, because guessing `false` understates permanent-establishment risk |

   So a dispatched record would land `blocked / factors_invalid` immediately —
   a refusal describing *our own incomplete forwarding* while reading as a
   finding about the employee's trip. That is the manufactured-refusal shape
   `docs/BUILD-LOG.md` §3.30 names, and it is worse than not dispatching.

### What changed

- **`policyEngine.js` rung 5's `means`** now says what happened (nothing was
  sent, no case exists, there is no queue to look in), what *does* exist (the
  handoff event on this decision), where the work-authorization request is
  really raised (the employee, in Remote's own Request Hub — no API can create
  one), and **names the four inputs a travel ticket never carries**. The four
  names are imported from `UC04_INPUTS_UC03_CANNOT_SOURCE`, never retyped. This
  one string reaches every surface that renders the gate ladder — the portal
  panel, the audit viewer, the ZAF sidebar and UC-03's own API — so the
  correction is made once.
- **`src/uc03/uc04Intake.js`** — the table above, as data, plus
  `describeUc04Intake(handoffEvent)`, which reports per run which inputs this
  handoff carries and which it does not, and distinguishes *"you did not say"*
  from *"we never ask"*. It carries literal `dispatched: false` /
  `uc04RecordCreated: false`, so the audit row **asserts** that nothing was sent
  rather than leaving it to be inferred from a missing UC-04 row. It decides
  nothing: computed after the decision, consulted by no gate, structurally
  incapable of changing an outcome. UC-03 is still the thin router this document
  says it is.
- **The two internal notes** carried the same overstatement one audience over.
  The Zendesk note said `Handoff: CROSS_BORDER_WORK_REQUESTED → destination PT`
  and the review-queue note said `Routed to UC-04 work authorization` — both
  read, to the specialist who is in fact the only person who will ever act on
  it, as *somebody else already has this*. Both now say it was recorded and not
  dispatched, and the Zendesk note names what the request does not carry.
- **The portal panel printed the gate's sentence twice** (as the reason
  paragraph and as the "What happened" row). Tolerable for one line; not for
  four sentences. `src/portal/assets/app.js` now drops a detail row whose value
  is *character-for-character* the paragraph already on screen — by value, never
  by label, so it can remove a repeat and never remove information.

### The drift guard

UC-03 **declares** UC-04's requirement list rather than importing it: UC-04's
list lives inside a non-exported `factorValidationIssues()`, and its `evaluate()`
runs identity, employment-status, sanctions and employer-permission gates
*before* completeness — so calling it as an oracle would answer a different
question and couple a 🟢 router to a 🟡 engine's whole gate order. A declared
copy can go stale, so `test/uc03.test.js` reads `src/uc04/policyEngine.js` and
asserts the slug sets match exactly. Add a required factor to UC-04 and this
test goes red. Same idiom as `test/uc04Portal.test.js`, which reads the portal's
own HTML rather than agreeing with it by hand.

### Still open

**A dispatch may one day be right, and it is not an agent's call.** If Remote
ever exposes a create endpoint, or if UC-03's intake grows the four missing
fields, forwarding becomes buildable — and it would still be a **tier-crossing
automatic write**, which is a decision for the project owner. Nothing here
builds toward it silently: `dispatched: false` is a literal in one file, so the
day someone builds a dispatch they have to change that line, and every consumer
of the shape is already reading it.

## 17. The continuation had to be completable — a real user reached gate 5 anyway

**Reported 2026-08-19.** An employee filed a travel request, it decided
`route_to_uc04`, they took the continuation, they filled the form in, and the
work-authorization assessment came back:

```
blocked / factors_invalid
flags: factors_invalid, missing_nationality
decided by gate 5 of 17 — request_completeness
```

**Gate 5 was right and is unchanged.** `nationality` drives the Schengen 90/180
branch and the visa-annex question; UC-04's matrix must never guess it. The
gate's own `means` sentence already says out loud that this is *"a request to be
completed, not a request that was refused"*. The defect was one layer up, in the
page.

### What was actually wrong

§16 built the continuation: the trip details carry across, and the banner at the
top of the UC-04 form names — in the server's own words, and distinguishing *"you
did not say"* from *"we never ask"* — every input the routing could not supply.
Then it rendered those inputs **as ordinary empty boxes**. Three problems
compounded:

1. **The marked fields were the wrong ones.** `is-carried` put a border and a
   "(carried over — check it)" note on every box that already had a value. The
   boxes with nothing in them wore nothing at all, so on a form where some
   fields are genuinely optional (`Evaluate as at`), the empty required one was
   the *least* conspicuous thing on the page.
2. **The list and the fields were in different places.** The banner named five
   things at the top; the boxes were in a three-column grid inside a collapsed
   `<details>`. Nothing tied one to the other.
3. **Nothing held the submission back.** The server had *already answered* which
   inputs it could not supply — in the same response that filled the form in —
   and the page posted anyway. That spends a real decision (a durable
   `uc04_authorizations` row, an `audit_log` row and a claimed idempotency key)
   to be told back what we were told before we asked, in the vocabulary of a
   policy refusal that reads as a finding about the employee's trip. That is the
   manufactured-refusal shape `docs/BUILD-LOG.md` §3.30 names.

The employee filled four of the five and missed one. The flags say so exactly:
`missing_nationality` alone, with no `missing_dates`, no `invalid_visa_type`, no
`invalid_job_duties`. They did everything the page made visible.

### UC-04's real required list, read out of the engine

`factorValidationIssues()` in `src/uc04/policyEngine.js`, in its own order:

| Input | Refusal slug | Where it can come from |
|---|---|---|
| `homeCountry` | `missing_home_country` | the employment record UC-03 read — **prefilled** |
| `destination.country` | `missing_destination_country` | the classifier's reading — **prefilled, and editable because a reading is not a fact** |
| `nationality` | `missing_nationality` | **the employee. Nowhere else.** See below |
| `startDate` **and** `endDate` | `missing_dates` | the classifier's reading when it read them; asked otherwise. **Both**, always |
| `visaType` | `invalid_visa_type` | the employee — a closed seven-member enum |
| `jobDuties` | `invalid_job_duties` | the employee — a closed seven-member enum |
| `hasContractSigningAuthority` | `missing_signing_authority` | the employee — must be a **boolean**; absent is not `false` |

### Nationality: Remote has it, and nothing this system may call returns it

Re-verified live 2026-08-19 rather than inherited from the earlier note, and the
answer is sharper than "the field does not exist":

- `GET /v1/employments/{employment_id}` — OpenAPI fetched live: **zero**
  occurrences of `nationality`, `citizenship` or `passport`. The committed
  Sandbox capture (`test/fixtures/sandboxCapture.js`, same day) agrees: zero.
- Remote's **work-authorization object** — the resource this assessment is
  *about* — carries `travel_document_number` ("the employee's travel document
  (passport) number") and **no nationality field at all**.
- The one place the word appears in Remote's whole API index is
  **`PUT /v1/employee/personal-details`**, whose own description names
  nationality among the fields it *updates*. That is a **write**, on the
  **employee-session** `/v1/employee/…` family — the same family
  `/v1/employee/expense-categories` belongs to, which returns
  `403 Forbidden, invalid role for this endpoint` to a company token (CLAUDE.md
  §7's closed expense-categories finding, verified live the same day). The
  portal and UC-04 hold a company token.
- The only read beside it, `GET /v1/employee/personal-information`, types its
  200 as a bare `SuccessResponse` — **no personal field is documented on it**.

So the value exists somewhere in Remote and nothing this system is permitted to
call returns it. **It must come from the user, and the form must ask.** No
default, and specifically no inference from country of employment: an employee
working in the Netherlands is not necessarily Dutch, and manufacturing that fact
to satisfy a gate is precisely what this project exists to refuse.

`src/remote/mockServer.js`'s fixtures used to carry a flat `nationality`, which
`normalizeEmployment()` handed straight back — so reading it would have worked
offline, for ever, against a field production never returns. It was removed
(BUILD-LOG §3.73), and a test now asserts the capture stays clean: if Remote
*starts* publishing it, that test is where the conversation begins.

### What changed

All of it in `src/portal/assets/`. No gate moved, no policy changed, and
`src/uc04/` was not touched.

- **The empty boxes are marked, from the server's own answer.** Each field the
  continuation named gets `is-still-needed` (a `--r-danger` border and a left
  bar, deliberately a *different* signal from `is-carried`'s warn colour), the
  words "(still needed)" appended to its label, and `aria-required`. Three cues,
  because the fields that were already filled were previously the only ones
  wearing any.
- **The mark comes off as the box is filled**, on `input` and on `change`, and
  is re-evaluated after a scenario quick-fill — assigning `.value` from script
  fires neither event, so a quick-fill would otherwise leave "(still needed)" on
  a box that now has a value.
- **A continuation is not submitted while a box it named is empty.** The page
  says which ones, in the server's sentences, and puts the cursor in the first.
  It renders nothing decision-shaped: no `result-box`, no `refused` class, no
  decision word — nothing has been judged and no gate has run, and a panel
  dressed as the verdict panel would be the page imitating a verdict it has no
  standing to reach.
- **The guard is scoped to a continuation and nothing else.** A UC-04 request
  filed straight from the form still goes to the server and still reaches gate 5
  with whatever it carries. That refusal is a real demonstration of a real gate,
  and swallowing it in the browser is the mistake `REQUIRED_FIELDS`' own comment
  warns about one form down.
- **A checkbox is treated as answered, because it always is.** Unchecked submits
  `false`, `false` is a boolean, and gate 5 wants a boolean —
  `missing_signing_authority` is structurally unreachable from this form.
  Marking it would put a marker on a box no click can clear.

### Why the page is safe to trust with this

**It holds no list of what UC-04 requires, and gains none.** The boxes it marks
and checks are the ones the server named, in the response that filled the form
in — `stillNeeded` plus any `prefill` entry that arrived with `value: null`.
Reading both lists also closes the one imprecision `src/uc03/uc04Intake.js`
documents about itself (it reports the date *pair* against the start date alone,
so a routing that read a start and no end would report its dates as carried while
UC-04 still refuses `missing_dates`) — without the page forming a rival opinion
about dates, because both facts are the server's.

`test/portalUc03ContinuationForm.test.js` pins this by reading the gap machinery
out of `app.js` and asserting it names **not one** UC-04 field id of its own,
checked against the real ids rather than a restated list. Add an eighth required
input to UC-04 and the chain still holds with no page change: the engine's list →
`uc03Continuation.js`'s map (drift-tested) → `stillNeeded` → the marker.

### The tests, and why the positive one is the point

CLAUDE.md §4: *"refusing correctly and being unable to succeed look identical
from outside."* Every assertion this flow had was a refusal.

- **POSITIVE (mandatory).** A UC-03 routing, continued, with the form completed,
  reaches `ready_for_approval / all_gates_passed` — **gate 17 of 17**, the one
  rung that opens a specialist approval.
- **POSITIVE, second shape.** The same completed form with an executive who signs
  contracts abroad reaches `escalate / high_risk_pair` with `pe_risk_dape` — a
  finding the matrix could only compute *because* the five answers arrived, and
  unreachable from a request that stops at gate 5. A fix that only ever produced
  `ready_for_approval` would have swapped one structural outcome for another.
- **NEGATIVE.** Nationality blank still gives `blocked / factors_invalid`,
  `[factors_invalid, missing_nationality]`, gate 5, `request_completeness` — the
  user's exact result. The gate is not loosened.
- **NEGATIVE, the half-range.** A start date with no end date still refuses
  `missing_dates` at gate 5.
- **Structural.** Every box a continuation can ask for sits inside a `.r-field`
  wrapper — `closest()` returns `null` rather than throwing, so a field outside
  one gets no marker, no border and no announcement, silently, in production
  only.

## 18. The standard letter and the one it is not — and why the signature stays

**The project owner's observation:** *"you forget that Remote gives automated
letters, so we can — if the person meets all requirements. Or if the person
wants something special then human review, and all the research needed to make
that decision is provided to a specialist."*

The distinction is real and it is Remote's own. What this section establishes,
against primary sources rather than by analogy, is **which half of it applies to
the travel letter** — because the answer is not the same as for the employment
verification letter, and building as if it were would have made this system
strictly more permissive than the platform it is built against.

### 18.1 The evidence, checked before anything was changed

Remote has **three** letter-issuance models, not one. Each was read from its own
primary source on **2026-08-20**.

| Letter | How it is issued | Evidence |
|---|---|---|
| **Employment verification letter** | Instant, templated, self-service, ~11 languages, **no human anywhere**. No API endpoint at all — for the standard case the product *is* the endpoint. | `docs/INTAKE-RESEARCH.md` §2/§6.5. Endpoint absence **[CONFIRMED]** from `docs/REMOTE-API-INDEX.txt`; the self-service behaviour **[INFERRED]** (help-centre article existence confirmed, body reached only through a search index) |
| **Probation completion letter** | `POST /v1/probation-completion-letter` with **nothing but an `employment_id`**. Status enum `submitted → in_review → done`. No approver in the schema, no approval status. | **[CONFIRMED]** — <https://developer.remote.com/reference/post_v1_probation-completion-letter.md> |
| **Travel letter** | **Two named human approvals, and generation is conditioned on the second.** | **[CONFIRMED]** — <https://developer.remote.com/reference/get_v1_travel-letter-requests.md> |

`TravelLetterRequest.status` documents its own enum, in Remote's words:

> - `pending`: **Submitted by the employee and awaiting manager review.**
> - `approved_by_manager`: Approved by the employer manager, **awaiting Remote's review.**
> - `approved_by_remote`: Fully approved by both the manager and Remote. **The travel letter will be generated.**
> - `declined_by_remote`: Remote declined the request after manager approval (e.g. compliance reasons).

And `UpdateTravelLetterRequestParams` is a closed `oneOf` over
**`ApprovedTravelLetter`** (`status` enum with the single value
`approved_by_manager`) and **`DeclinedTravelLetter`** (`declined_by_manager`,
`reason` required). `approved_by_remote` / `declined_by_remote` are **readable
and unsettable by any client**.

**So the sign-off stays, and this is the honest outcome of the investigation
rather than a failure of it.** The document Remote generates is generated only
after two humans have approved, and no API caller can even reach the state that
generates it. A UC-03 that auto-issued a formal travel letter would be more
permissive than the platform. The `docs/INTAKE-RESEARCH.md` finding that
verification letters are self-service does **not** transfer: it is a different
letter, with a different reader, and Remote treats it differently in its own
schema. `[CONFIRMED]`.

**Two design notes worth keeping from the comparison.** The probation letter
shows Remote *will* mint a letter from an id alone when the letter asserts
something the platform already knows for certain — so the gate is not "letters
are scary", it is specific to what a travel letter claims. And the travel
letter's approval is the **employer's** first: the three cost-responsibility
enums are documented *"Set by the employer during approval"*, which means part
of the document's content does not exist until a human has supplied it.

### 18.2 What DID change: standard vs. non-standard

Before this pass, **every** letter request drafted the same template and put it
in front of a specialist. `renderTravelLetterHtml()` has fixed rows and no
free-text block, so a request reading *"address it to the German Consulate
General in Lagos, state my passport number, and confirm the company covers all
costs"* produced a letter opening **"To Whom It May Concern"** with none of
those three things in it — and **that** was the document a specialist was asked
to sign. Nothing recorded that three things had been asked for and dropped.

That is this repository's most expensive recurring failure shape, rotated once
more: a correctly-drafted standard letter and a silently-truncated non-standard
one are indistinguishable from outside, and the specialist cannot see the
request's words in the document, so the omission is invisible exactly where it
matters.

| | Standard | Non-standard |
|---|---|---|
| What it is | The template as it stands, for a trip every gate cleared, with nothing unusual asked for | Anything the template cannot express, or a row it asserts with no value behind it |
| Decision | `human_review` / `formal_letter_requested` — **unchanged** | `escalate` / **`letter_scope_exceeded`** (new gate, ladder position 11 of 13) |
| Document | Drafted, stored, queued, awaiting the one signature | **None drafted.** Refusing to *issue* a bad document still leaves the bad document written, so the refusal is in the drafting |
| What the human is asked to do | Put a signature on a prepared document | **Write** one this system cannot prepare |
| Team | Travel & Mobility Support | Travel & Mobility Support (same row in `escalationRouting.js`, both paths) |

The case, the queue entry, the Zendesk note and the audit row all carry the
findings: **what was asked, what the template cannot carry, and the source that
says the field exists.**

### 18.3 A model may route INTO the human path, never out of it

`standard` opens a drafting path, so prime directive 1 makes the asymmetry
structural rather than asserted. `src/uc03/letterScope.js`:

1. **`standard` is never a value anything reports** — it is `findings.length === 0`.
   There is no field, on any input, meaning "this is standard". A model cannot
   set one because none exists. Pinned by a source-scan test asserting exactly
   one place produces the verdict.
2. **The model's contribution is a list of problems** (`letterSpecialRequests`),
   **unioned** with the deterministic scan. A union can only grow the
   non-standard set.
3. **A model list that is present but not an array of strings is a finding**
   (`model_reading_unusable`), never an ignored value.
4. **Absent or blank request text is a finding** (`request_text_unavailable`) —
   *"we saw nothing unusual"* and *"we had nothing to look at"* are opposite
   statements. `evaluate()`'s new `requestText` parameter therefore has no
   default meaning "fine": a caller who forgets it gets a refusal.
5. **The confidence floor is re-applied inside the assessment**, imported from
   `policyEngine.js`'s own constant (via `confidenceFloor.js`, which exists only
   to keep the two files out of an import cycle). Rung 3 already refuses a
   low-confidence request — this is the guard that makes the property hold for
   *any* caller rather than as a consequence of gate ordering, the same lesson
   the four repaired identity gates taught.

The markers are **narrow in one direction only**: each needs a *requesting
construction*, not merely the topic. *"for my visa appointment at the
consulate"* names a consulate and asks for nothing; *"please address it to the
consulate"* asks. A false positive here is safe (a person writes the letter); an
over-broad pattern is not, because if `standard` becomes unreachable then
"cannot succeed" and "appropriately cautious" look identical and every negative
test still passes. `test/uc03LetterScope.test.js` pins both halves — **the
positive one first**, and a further test asserts every marker in the table is
reachable from a real sentence, so no marker can go dead the way the sanctions
gate did.

### 18.4 What a travel letter is expected to contain — and what this one holds

**The Commission's Visa Code Handbook I** — Commission Implementing Decision
**C(2024) 4319** Annex, fetched 2026-08-20, sha256
`f671a0cff5a800d723784826739c46129e24056d45e8823cfd07eae24b3142ac` — is the
primary source that survived retrieval. It does **not** prescribe a letter
template. What it does is name the evidential heads a business traveller's
documents must satisfy, and a letter of this kind is offered against three of
them:

- **Purpose of the journey** — Annex A(1)(e): *"documents proving the
  applicant's employment status in the company"* (examples: *"Contract, proof of
  social security contributions"*). Note that A(1)(a), *"an invitation from a
  firm or an authority"*, is the **host's** document, not the employer's — a
  distinction the template must not blur.
- **Intention to leave before the visa expires** — Annex B(3): *"proof of
  employment or professional activity"*, which *"may be proved by a work
  contract; **certificate of employment**; information on professional status,
  bank statements, and proof of social security contribution."*
- **Means of subsistence** — §5.2.2(d) *"salary slips"* and (e) *"certificate of
  employment"*; and *"Account should be taken as to whether … the cost of the
  stay is covered entirely or partly by a reliable sponsor."*

§5.1.1 names *"statement of employment from the applicant's employer"* among the
originals a consulate keeps. **This is the primary source for the compensation
row**, which until now rested only on the research blueprint. `[CONFIRMED]`.

**The single most important finding is that there is no universal answer.**
§5 states that consulates in a given location *"shall prepare a harmonised list
of supporting documents … in order to take account of local circumstances"*,
adopted by the Commission under Visa Code Art. 14(5a), and that *"Implementing
decisions establishing harmonised lists of supporting documents are legally
binding on Member States."* On invitations specifically: *"The Visa Code does
not provide a legal basis for drawing up national forms for invitations.
However, harmonised lists of supporting documents should provide details on the
content of such invitations."* Translation (§5.1.2) and legalisation (§5.1.3)
are likewise set per location. **So "a destination authority's particular
requirement" is not an edge case — it is the normal case, and it is precisely
what a fixed template cannot enumerate.** That is the strongest argument for
§18.2's split.

## 19. Which results interrupt — the predicate, and the nine-row answer (2026-08-20)

The project owner, on the "Also available — Every gate passed, so the same trip
can be certified in a formal travel letter" block at the bottom of a UC-03
result:

> "I should not have to scroll up to see this, it should be a popup, plus
> redirect if need be, **across all the use cases**."

The block sat below the decision, below the gate ladder, below the facts table.
A traveller who did not scroll never learned the letter existed — which made an
offer that is built, tested and proven end to end reachable by nobody. That is
this repository's most persistent defect and it had by then happened three times
in one day.

`af07de0` had already solved exactly this for the other UC-03 outcome, a
`route_to_uc04` routing, with a native `<dialog>` + `showModal()` and the trick
that makes it honest: **one node, built once, rendered in the page, moved into
the dialog, and moved back on close** — so dismissing takes nothing away and
there is one button with one listener. This section records the generalisation
of that mechanism and, more importantly, the rule that decides who may use it.

### 19.1 The predicate

> **A result earns a modal when it offers the reader a next action they would
> otherwise have to discover by scrolling.**

"Across all the use cases" is a correct instruction and *"give every panel a
popup"* is the wrong reading of it. A modal interrupts, and an interruption
carrying nothing actionable is worse than a paragraph: it teaches people to
dismiss without reading, which is precisely how the disclaimer work would get
undone. Three kinds of result exist on the portal and only the first qualifies:

| Kind | What it is | Does it interrupt? |
|---|---|---|
| **Offer** | Something the reader can take up now, themselves | **Yes** — one per result |
| **Hand-off** | Someone else must act; the reader's next step is to wait | No. It says so plainly, in place |
| **Refusal** | Nothing is offered | Never |

### 19.2 The nine, decided one at a time

The portal is the intake surface for seven use cases; UC-01 and UC-06 have their
own entry points and no result panel here, so their rows record where the
question actually lives rather than pretending the portal answers it.

| UC | Result panel | Kind | Modal? | Why |
|---|---|---|---|---|
| 01 | not on the portal — `src/livedemo/`, `src/chatdemo/`, and the Zendesk ticket itself | — | — | The auto-resolved answer is *posted to the customer's ticket*; there is no portal result to interrupt. If a surface is ever built here, the letter is the offer to promote |
| 02 | Expense validation | Hand-off (or auto-settled) | **No** | A claim that passes is settled with nobody reading it — nothing is left to do. A flagged one goes to Finance Ops and the reader waits. The one action the page does offer, "File this as a new claim", is on the FORM, not the result |
| 03 | Travel / letter | **Offer × 2** | **Yes** | `route_to_uc04` → the continuation (already built, `af07de0`); `auto_resolve` → the formal travel letter (built here). Mutually exclusive on the wire — see §19.4 |
| 04 | Work authorization | Hand-off | **No** | One named mobility specialist approves or declines. The requester's next step is to wait, and the panel says so. `blocked` is a refusal and offers nothing at all |
| 05 | Resignation notice | Hand-off | **No** | HR Ops signs the figures off, and that signed-off summary IS the record. Nothing here is the employee's to take up |
| 06 | not on the portal — `src/remoteui/` | Hand-off | **No** | Dual approval, in the ZAF sidebar. Two named roles, neither of them the requester |
| 07 | Relocation dossier | Hand-off, and permanently | **No** | 🔴, no execution path anywhere, asserted structurally and behaviourally. An offer here would be a lie with a button on it |
| 08 | Cross-border tax dossier | Hand-off, and permanently | **No** | Same guarantee, same reason |
| 09 | Off-cycle adjustment | Hand-off | **No** | At least two people, three above the money threshold, and never the requester |

**So one use case of the seven earns the interrupt, and it earns it twice.**
That is the honest answer and it is written down rather than padded: five more
offers would have had to be manufactured to make the pattern look general, and
on UC-07 and UC-08 manufacturing one would contradict the guarantee those two
exist to demonstrate.

### 19.3 What the letter offer lost, and what it kept

The modal's body must not restate its own title. `offer.reason` — *"Every gate
passed, so the same trip can be certified in a formal travel letter — drafted
from this decision and issued only after a Travel & Mobility Support specialist
signs it off"* — is no longer printed, because every clause of it is already on
the panel: "every gate passed" is the decision in the head of the result and
every rung of the ladder below it, the middle clause is now the heading, and the
drafting and sign-off are stated at greater length by `signoffNote`, which also
carries the fact the sentence lacked (*"Nothing is sent to you or to anyone else
before that"*). What is printed is `produces`, the three trip facts from
`carries`, the correction sentence, `signoffNote`, and the server's own `label`
on the button.

**One reported change this build did not make**, because `src/uc03/` is another
build's territory: `describeLetterOffer()` should carry a `notice: {headline,
sentence, action, dismiss}` block in the shape `WORK_AUTHORIZATION_NOTICE`
already uses, so the heading is the server's words rather than the page's. Until
then the heading is a page-authored label — the same class of thing as the
"Also available" badge it replaces — held in one constant,
`LETTER_OFFER_HEADLINE`.

**What the offer MEANS is unchanged.** It is the traveller's, accepted with the
traveller's own server-held session, which is why this page can carry a button
at all and why the ZAF sidebar deliberately renders the same offer read-only
(§18, `test/zafUc03LetterOffer.test.js`). Moving where a thing appears is not a
change to what it is.

### 19.4 The mechanism, and the two rules it holds

`offersOn(payload)` returns the offers a result carries, in priority order: a
routing outranks a letter, because a routing is a **redirection** — nothing else
about the request can move until it is taken — where the letter is an extra on
an answer that is already complete. The first is promoted (`promoteToInterstitial`)
and shown as the modal; **any others still render in the panel, unpromoted.**

- **One modal per result, maximum.** Two stacked interruptions is a dark pattern
  and the second is never read.
- **But "not the interruption" never means "not on the page."** A second offer
  quietly dropped would be the very defect this change exists to fix, committed
  by the fix. The two UC-03 offers cannot in fact co-occur — the server sends a
  continuation only on a routing and a letter offer only on an auto-resolve — so
  the branch is usually dead; it is written this way so the impossible case
  degrades to *quieter* rather than to *gone*.

**A modal is only allowed at all because the browser supplies its
accessibility.** `showModal()` traps focus, closes on Escape, makes the rest of
the page inert and restores focus, in the engine. A hand-rolled overlay does
none of that and the focus traps people write by hand are subtly wrong. Without
`<dialog>` support the node simply stays where it was appended — a prominent
interstitial at the top of the result — so the information is reachable either
way and the modal only decides how loudly it arrives.

**One thing the browser could not restore, and why.** `<dialog>` returns focus
to whatever had it when `showModal()` ran, and in this flow that is `<body>`:
`submit()` disables the submit button while the request is in flight, which
blurs it, and re-enabling does not take focus back. So the engine faithfully
restored focus to nothing and a keyboard user pressing Escape was dropped at the
top of the document. Verified in a real browser (`document.activeElement` read
`BODY`), and repaired only in that case: if focus was restored somewhere real,
the browser has done the right thing and the page must not overrule it.

### 19.5 Driven in a real browser

### 19.6 The banner under it, cut to its heading

The same editorial rule, one level finer, on the banner the continuation lands
on. The owner: *"remove this part — only the heading is needed. Same for every
use case."* The two sentences were *"Working from another country needs a work
authorization check first, and this form is it. What your travel request already
told us is filled in below — check those answers, then complete the boxes marked
'still needed'."* The first half is the heading again; the second narrates the
form the reader is looking at — and the form already says it about itself, on
the boxes, where it can be read against them: each carried box wears its
"carried over" mark and each empty one wears "(still needed)" and
`aria-required`.

`WORK_AUTHORIZATION_NOTICE.sentence` lost its opening clause for the same
reason — *"This is a different request from a business trip"* is the headline
paraphrased, and inside a modal whose accessible name IS that headline, a body
opening with its own title is the defect with a spotlight on it. What survives
is what the headline cannot carry: what continuing does to the trip details, and
that **nothing is submitted until you send that form**.

**A heading plus a fact is not redundancy** and was kept everywhere it appears —
"Spain, 14 September to 2 October, carried over" tells a reader something the
heading cannot. And **nothing that says what this system did or did not do was
touched**: that no work-authorisation case was created, that nothing was sent
anywhere, the destination the router read and the confidence it read it with.
Those are how a requester knows whether anything is waiting on them.

Pinned in both directions rather than deleted: the test that used to allow "one
paragraph, at most two sentences, under 320 characters" now asserts **no
paragraph at all** — a budget is a thing prose grows back into — while still
asserting the heading is present and the surviving facts are printed
(`test/portalUc03ContinuationForm.test.js`, `test/portalInterstitial.test.js`).

## 20. The accepted letter had nowhere to be signed (2026-08-20)

> *"I went to Zendesk as the specialist, and I did not see anywhere to approve
> the letter to be sent to that individual."*

They accepted a travel-letter offer on the portal. The letter drafted correctly.
Then nobody could sign it.

### 20.1 What was actually wrong

Queried against production before anything was changed:

```
c2df9893…  UC-03  human_review  formal_letter_requested  pending_review
           external_ref = "uc03-20260820095458-18k04"     ← a PORTAL reference
b4026e79…  UC-03  route_to_uc04  work_authorization_requested  routed
           external_ref = "57"                            ← a real Zendesk ticket
```

Both rows are correct. The second one has a ticket because the submission path
runs `raiseTicketIfNeeded()` after the gates; the first does not, because
`POST /api/requests/uc03/request-letter` called `acceptTravelLetterOffer()` and
returned. **The ZAF sidebar finds a case by ticket id.** With no ticket there
was no ticket to open, so no panel rendered — the specialist was not missing a
sign-off button, they were missing the whole case.

Everything else was already built and already correct: §15.2's sign-off policy,
§15.3's offer, the drafted document, the `review_queue` row, the audit trail.
This is §7's honest-gaps item 11 in its third shape of the same day — **correct
at the store layer, wrong at the hand-off layer.** A decision that is durable,
audited, and reaches nobody.

The tag had been sitting in `src/portal/ticketing.js` the whole time:
`'UC-03': { human_review: "uc03_formal_letter_review" }`. The route was the only
thing that never asked for one.

### 20.2 The design question: a new ticket, or the answer's existing one?

A letter request is a **second decision on a trip that already has one**
(`cc551b4` made it a new case rather than mutating the first, with its own
idempotency claim `<ref>#letter`). One layer up, the same question has to be
asked about the ticket: does it follow the **case** — one row per thing that
needs doing — or the **trip** — one conversation about one journey?

**It follows the trip**, and the choice was already half-made:
`acceptTravelLetterOffer()` has always REOPENED a Zendesk-sourced ticket rather
than raising another, because the informational answer had solved it. Deciding
the other way here would mean one act produced one ticket from Zendesk and two
from the portal.

Three reasons, in the order they matter:

1. **The specialist reads a conversation, not a row.** Signing means reading
   what was asked, what was answered, and what is now being certified — to a
   consulate, on the legal entity's letterhead. Split across two tickets, they
   would have to find the other half, and nothing would link them: `readStore.js`
   resolves a reference by `details->>'externalRef'` alone, so a pointer that is
   not in that field is a pointer nobody can follow.
2. **The queue still counts one row of work.** That is the objection to
   following the trip, and it does not apply: the `review_queue` row is what a
   queue counts, and `CaseStore.findByExternalRef()` returns the **newest** UC-03
   case for a reference. The newest is the letter. So the sidebar opened on that
   ticket renders the letter panel with its sign-off control, not the settled
   answer beside it.
3. **A trip with no ticket still needs one** — and that is the actual gap. Every
   portal-answered trip has none, because an auto-resolved answer raises no
   ticket by design (`NO_TICKET_DECISIONS.uc03`, and rightly: a ticket asking a
   human to notice a zero-touch answer is exactly the work the automation
   removed). The letter request is the first thing on that trip a person must
   act on, so it is the first thing that earns a ticket.

**Whether the trip already has a ticket is derived, never assumed.** Not "the
source is portal, so there is no ticket" — that restates today's deny-list in a
second place, free to drift the moment an offer is made on an outcome that does
raise one. `letterTicketPlan()` reads it off the answered case: a Zendesk-sourced
case's `externalRef` **is** its ticket id, and a portal case's `externalRef` is
the ticket id exactly when its own decision needed one, because `linkTicket()`
replaced it at that moment.

### 20.3 What the hand-off keeps from the submission path

Nothing about the ordering or the failure handling is new; the accept route now
reaches the same machinery the submission route always did.

- **The ticket is raised after the decision is durable.** `acceptTravelLetterOffer()`
  has already returned: the case row, the `review_queue` row, the drafted
  document and the audit row all exist. A Zendesk failure from there is a
  hand-off that did not happen — reported on the response and recorded as
  `portal_ticket_creation_failed` — and can never erase a decision that was
  genuinely made.
- **A ticket that cannot be raised is visible, not swallowed.** Production
  already carries one such row with no retry (`293b0f4e`, `CLAUDE.md` §7 item 9).
  The response carries `ticketError` and the accept panel prints it, so a case
  that reached nobody never looks complete.
- **The team is looked up, never typed.** `src/shared/escalationRouting.js` is
  the only source: `queue_travel_support`, **Travel & Mobility Support**, and the
  id from `escalationGroupIds.js`. The tag is `queue_*` and not `escalation_*` —
  a drafted letter awaiting a signature is the human gate working, not the
  automation giving up.
- **A refusal hands nothing over.** An unauthenticated accept, a non-traveller
  and a second accept all return before the hand-off: nothing was decided, so
  there is nothing to hand to a human, and a ticket there would be the duplicate
  the exactly-once ledger exists to prevent, arriving in a real support queue.

The subject line is the one thing the submission path's default could not carry.
A `human_review` on a travel request is either "the router distrusted its own
reading" or "a letter is drafted and needs a signature", and those are different
work; a specialist scanning a queue reads the subject first. It reads
**"UC-03 — formal travel letter, awaiting sign-off"**.

### 20.4 The regression the relink caused, and the parent link that fixes it

Raising the ticket repoints the letter case's `externalRef` at it — that
substitution is the whole point, and `recordTicketRelink()` audits it so the
reference the requester holds still resolves. It also **silently broke the
duplicate-accept refusal**, and the break is worth recording because nothing
errored.

"Has this offer already been taken?" was answered by looking up the newest UC-03
case sharing the answered case's reference. That held only while both rows kept
the same reference. After the relink they share none: the lookup finds nothing,
a second accept reads as a first, and an answered case goes on advertising an
offer somebody has already taken. Both wrong quietly.

The fix is a **durable parent link**: `carryClassificationForward()` now writes
`offerAcceptedFrom` onto the letter case's classification, and
`findLetterCaseFor()` (`src/uc03/caseAttachments.js`) asks by it — scoped to the
traveller via `listByOwner()`, which is indexed, rather than scanning every
UC-03 case. A case id is never rewritten, so it survives every relink; the
reference lookup stays as the fallback for rows written before the link existed.
It is still a **display** input — what actually stops two letters is the
`workflow_claims` primary key on `(use_case, <ref>#letter)`, and that key is
computed from the answered case's reference, which the hand-off does not touch.

## 21. The answer first, the recommendation second — and the measurement that decided "always" (2026-08-20)

§19 wrote the predicate down and answered it honestly: **one** use case of the
seven earned a modal, and six panels deliberately got none. The project owner,
looking at the modal that produced — which opened *"A formal travel letter for
this trip"* while the answer to the question they had actually asked sat on the
page behind it:

> "I want the answer for everything to always be in the pop up, and then in this
> case a recommendation, starting with something like **'Do you need a formal
> letter for your trip?'** In this case just two sentences above the
> recommendation that answers the user's question."

So the dialog's contents invert. **The answer comes first and always; the offer
becomes a recommendation underneath it.**

### 21.1 This refines §19's predicate rather than overturning it

§19's *reasoning* was that an interruption carrying nothing actionable trains
people to dismiss without reading, and that the next thing dismissed unread is
the 🔴 disclaimer. That reasoning is intact, and it is still why five of the
seven get no button in their dialog and why UC-07 and UC-08 will never get one.

What the instruction corrects is the predicate's **premise**: it treated an
answer as nothing. **An answer is not nothing** — it is the single thing the
requester came for, and on this page it was the thing they had to scroll to. The
rule is therefore:

> **The modal carries the answer, always, and the recommendation when there is
> one.**

§19.2's nine-row table is unchanged in what it decides. It answers *"who has
something to OFFER"*, and the answer is still `UC-03 × 2`.

### 21.2 The measurement, because two readings were defensible

Either every result opens with the answer in a dialog, or only the results whose
answer is not already the first thing on screen. `267b01d` had already put the
plain answer at the top of the panel body, so on a short result it might be
visible without scrolling — and then a dialog would add an interaction and
remove nothing.

Measured rather than argued. Chromium, one quick-fill per request type,
`window.scrollY === 0` in every case, distance from the top of the viewport to
the **answer's first pixel**:

| Request type | 1180 × 900 | 340 × 740 |
|---|---:|---:|
| UC-02 expense | 1153 px | 2090 px |
| UC-03 travel | 926 px | 1681 px |
| UC-04 work authorization | 1795 px | 3707 px |
| UC-05 resignation | 1653 px | 3251 px |
| UC-07 relocation | 2037 px | 3887 px |
| UC-08 cross-border tax | 1482 px | 2831 px |
| UC-09 off-cycle payment | 1246 px | 2196 px |

Fourteen measurements, **fourteen below the fold** — the nearest 26 px past it,
the furthest more than five screens down. The cause is structural rather than
incidental: the result panel renders *below* the form that produced it, the
forms are long, and nothing scrolls.

So "only when the answer is off screen" is not a different rule from "always" —
it is the same rule with a condition that is currently true every time.
Implementing the condition would mean branching on `getBoundingClientRect()` in
a file whose whole discipline is that it renders what it is given, and would
make the same request behave differently by window height. **Written as
"always", with the table above as the thing to re-measure** if the page ever
scrolls its result into view or the forms get short.

### 21.3 The one exception, and it is argued rather than omitted

**An intake refusal gets no dialog.** Measured the same way, it is just as far
down — 1152 px and 1482 px at 1180 × 900, 2108 px and 2781 px at 340 × 740 — so
this is not "its answer was already visible".

It is left out because a refused submission is a **correction loop**: the form is
still on screen with their answers in it, their next act is to fix it, and a
modal in front of that form would be dismissed on every attempt. And `267b01d`
deliberately gives an intake refusal no `plainAnswer` — its reason already *is*
one plain sentence — so a dialog there would have to be labelled by a heading the
page invented, which is the one thing `app.js` may not write.

It is not left where it falls either: `render()` scrolls the refusal panel into
view. The answer is reached without scrolling either way; the loudness matches
what the reader has to do next. Nothing is focused, because `#result-ucNN` is
already an `aria-live="polite"` region and moving focus into it would announce
the refusal twice.

### 21.4 The wording

**The recommendation's heading is a question addressed to the reader** — *"Do
you need a formal letter for your trip?"* — and not a label for a feature. The
difference is what each one asks of them: *"A formal travel letter for this
trip"* asserts that the letter exists and leaves the reader to work out whether
the assertion is about them; the question is the decision actually in front of
them, and the only one this block asks them to make.

**The answer above it is at most two sentences and comes from
`src/portal/plainAnswer.js`**, which already writes exactly that shape
(`lead` + `next`). No second answer generator was written.

**One sentence read wrongly in a dialog where it read correctly in a panel, and
it was fixed in `plainAnswer.js` where both surfaces get it.** UC-03's answered
lead was one sentence ending *"…, and nobody has to approve it."* Four lines
below it in the dialog, the letter recommendation says the letter is signed off
by a Travel & Mobility Support specialist if the letterhead cannot be read. A
screen apart those are two facts about two different things; four lines apart,
"nobody has to approve it" followed by "a specialist picks it up" reads as a
contradiction and leaves the reader to work out which *it* is which. The clause
is now its own sentence and names what it is about:

> **Yes — a business trip like this one to Spain needs nothing further from
> Remote.**
> Nobody has to approve the trip itself.

**What was NOT written, and why.** The instruction's example sentence was *"Yes
you are allowed to travel."* This system may not say that. `plainAnswer.js`'s
rule 2 is that it never overstates, and an `auto_resolve` here means *"short-term
business travel of this kind requires no additional action on the Remote
platform"* — it is not a finding about the destination's entry rules, which this
system has never checked and does not hold. The sentence above is the honest
form of the same answer, and the refusal to write the shorter one is deliberate.

### 21.5 Accessibility — what changed and what did not

| Property | Before | Now |
|---|---|---|
| Element | native `<dialog>` + `showModal()` | unchanged |
| Accessible name | the **offer's** heading (`h3`) | the **answer's** heading (`h3`), by `aria-labelledby` on the element itself — the offer's heading is demoted to `h4` and is the fallback only for a payload carrying no answer |
| Heading outline | card `h2` → offer `h3` | card `h2` → answer `h3` → recommendation `h4`, which is the one place the subordination is stated for a screen-reader user |
| Focus on open | inside | unchanged |
| Escape | dismisses | unchanged |
| Dismissing | the offer returns to the page in place | **every** block returns in place, restored back-to-front so each anchor is present before anything is inserted ahead of it |
| Focus after dismissal | the restored offer | the restored **answer**, which also scrolls it into view |
| Ways out | the offer's own dismiss | exactly one — the offer's when there is an offer, a "Close" added by the presenter when there is not, and removed with the dialog either way |
| Modals per result | one | one |

### 21.6 Verified

**43 quick-fills across the seven forms, driven through the real handlers**, then
through the page's own answer/offer/dialog code: **39 decided results open
exactly one dialog each; the four intake refusals open none.** Every dialog's

## 22. The signer was never shown who they were signing about (2026-08-20)

The project owner, reading the live sidebar on a real ticket:

> *"In that Zendesk bar I never even saw any relevant info of the employee — not
> even name. That is bad."*

Exact. `zaf-app/assets/main.js` had already found it and could not fix it from
where it stood: `RemoteClient.getEmployment()` normalises a display name onto
every employment it returns, and **none of the nine by-ticket views published
it**. The stores persist `employment_id` and nothing about the person, so a
Travel & Mobility Support specialist was asked to put their name on a document
about `emp_active_001`.

### 22.1 What UC-03's view now publishes

`GET /api/cases/by-ticket/:ref` and `GET /api/cases/:id` carry two new blocks.

**`employee`** — `full_name`, `job_title`, `status`, `contract_type`,
`start_date`, `country_code`, in that order.

The first five are **exactly the rows `renderTravelLetterHtml()` prints**:
Employee, Job title, Employment status, Contract type, Start date. That is the
whole argument for including them and the reason there is no sixth from the
record: *a signature over an assertion nobody was shown is not a control*, and
the panel now shows precisely what the letter will assert.

`country_code` is the one that is not on the letter. It is here because
`workflow.js` reads it as `origin_country` and hands it to UC-04 on every
`route_to_uc04`, and `policyEngine.js` already calls it *"Home country on the
record"* in its decision facts — a trip's origin is what makes its Schengen and
183-day framing mean anything at all.

**Compensation is deliberately absent, and pinned by a test.** The letter
template does carry a base-pay row, and it is unreachable on a real record:
`normalizeEmployment()` produces no flat `base_salary`, on purpose, and
`restClient.js` says so in its own words. Beyond that, `CLAUDE.md` §3 makes
money on a screen a decision rather than a default, and nothing about this
signature turns on what the traveller is paid. `src/shared/employeeSubject.js`
has no money field for any caller to ask for.

**Work email is absent too**, for a different reason: the identity gate has
already compared the requester's address to the record's and recorded its
verdict on `flags`. Printing both invites a reader to re-adjudicate a check the
system made, while putting a second personal identifier on the screen.

### 22.2 It is a live read, and that is the point

The block is read from Remote **when the panel opens**, not frozen on the row at
decision time. The alternative — persisting a display name — was rejected for
three reasons, and the third is the one that decides it:

1. it freezes a fact that changes;
2. it puts personal data in a second place, in nine tables, permanently, where
   the stores today hold only an opaque id;
3. **`submitTravelLetterSignoff()` already re-reads the employment and refuses
   `employment_no_longer_active`.** A stored name would have shown the signer
   the decision-time snapshot while the button acted on a record it had never
   displayed. Now the screen and the button read the same record at the same
   freshness.

An unavailable record is never a blank and never the id relabelled. Five states,
carrying the distinction `src/shared/upstreamFailure.js` exists for:
`available`, `not_found` (Remote answered 404 — an answer *about the record*),
`unavailable` (403/5xx/transport — the request was never evaluated),
`not_looked_up` (this API was wired with no Remote client) and
`no_employment_id`. A failed read degrades the block and never the case: the
decision, its flags and `actionable` are byte-identical with a blinded client,
which a test drives directly.

### 22.3 `requester` — who asked, and what "verified" proved

The same views now publish `requester` in the shape
`src/shared/requesterSubject.js` defines, which UC-04 publishes too. UC-03's
answer is usually *"the traveller, about their own trip"* — and that is exactly
why it is **compared** rather than assumed: `actingFor` reads the session's
employment id against the case's, so a mismatched session says so instead of the
sentence staying quietly wrong. Driven against a real mismatch, the case
escalates `identity_not_verified` and the block reports
`on_behalf_of_the_subject` / `not_verified` together.

`identity.finding` states what the gate actually proved — *"an authenticated
session for this employment … not proof of who was at the keyboard"* — because
a tick beside a person's name asserts the second.

**Tests:** `test/employeeSubject.test.js`, `test/requesterSubject.test.js`.

## 22. The letter existed and nobody could fetch it (2026-08-20)

The project owner, reading "My requests" with a UC-03 letter request in it:

> "This should not end here. A travel letter was requested. It should be
> recorded, and the user should be able to download the letter. **The question
> now is: from where?**"

The letter was real the whole time. It is rendered, hashed and stored as a
`travel_support_letter` row in `documents`, and its sha256 is on the decision's
audit row. The history row showed a status and a sentence, with **no sign a
document existed, no way to see it and no way to get it** — a decision that is
correct, durable, audited and reaches nobody, which is the failure shape
`CLAUDE.md` §7's honest-gaps list now names five times over. An **issued**
document nobody can fetch is its worst version, because the audit row records a
delivery that did not happen.

### 22.1 Three states, and only one of them gets a button

| State | What it means | What the row shows |
|---|---|---|
| **Issued** | The document exists and has gone out | "Ready", the sentence, and **Open the letter** / **Save it** |
| **Drafted** | Written and held for a Travel & Mobility Support specialist | "With a specialist" and the gate's own sentence naming who has it. **No control** — a button here would promise a document the sign-off gate exists to withhold |
| **None** | No letter was written | Whichever of the four "no letter" situations this is, in the server's words (`describeNoLetter()`), and nothing that implies a document |

### 22.2 The gate is UC-03's, and the row and the route are the same verdict

`src/portal/letterAccess.js` restates no rule. It **calls**
`evaluateLetterDelivery()` (`src/uc03/letterDelivery.js`) and translates the
verdict into something a history row can render; the fetch route calls the same
function with the same session. That is the property that makes the button safe:
the page structurally cannot offer a save on a letter the route would refuse,
which is the same class of defect as an approve button on a case nobody can
approve. `test/portalLetterAccess.test.js` §3 drives both for every row and
asserts they agree.

**The reader's real session, never the case's own employment id.** It comes from
`src/portal/personas.js`'s server-owned map — prime directive #3 — and
`ownerScopeFor()` has already scoped the listing to that same person, so the two
agree by construction rather than by luck. Comparing a row against itself is the
shape this repository has had to fix four times.

**An access problem never reads as an absence.** `case_not_found`,
`session_required` and `not_the_traveller` render as the gate's own sentence with
no control — not as "you have no letter", which is the reassuring direction and
therefore the one that gets believed.

### 22.3 The route, and why a POST for a read

`POST /api/requests/uc03/letter`, body `{persona, caseId}`. It matches
`/api/requests/uc03/request-letter` beside it and `src/uc03/server.js`'s own
`/api/cases/:id/letter`: the traveller's identity is a persona key in a body,
which keeps an employment id out of a URL and out of every access log that URL
passes through. It **creates nothing, mutates nothing and audits nothing** — the
document already exists and already went out, so the read-only boundary "My
requests" states in its own payload is untouched.

Response: `{ok, code:"letter_available", caseId, documentId, type, contentType,
filename, contentHash, issuedAt, issuedWithoutSignature, content}` — the
`describeIssuedLetter()` shape, unchanged. The hash travels **with** the content
and never instead of it, so a reader holding the letter can check that what they
were handed is what history says was issued.

### 22.4 Serving HTML that this page must not execute

The letter is HTML this system rendered and it names an employee, their job
title, their employer and their base compensation.

- **Viewing** — an `<iframe sandbox="">`. The **empty** attribute is the
  restrictive one: no `allow-scripts`, so nothing in the document runs, and no
  `allow-same-origin`, so the frame holds an opaque origin. Verified in
  Chromium: `iframe.contentDocument` reads `null` from this page. `srcdoc`
  rather than a `blob:` URL **deliberately** — a blob URL *inherits the creating
  page's origin*, so navigating to one would run the letter as the portal.
- **Saving** — `Blob` + `<a download>`, which never navigates, so no document is
  ever loaded and the HTML cannot execute anywhere. The filename is the
  server's: `travel-letter-<case id>.html`, built from the case id rather than
  the employee's name, because a filename ends up in shared folders and mail
  clients. Verified in Chromium rather than claimed: the download event fires
  with `travel-letter-033b15ab-….html` and 1,857 bytes beginning `<!doctype
  html>`.

**One defect this found, in a real browser and not in a test.** `showModal()`
focuses the first focusable element, which is the iframe — and with focus inside
a sandboxed frame **Escape does nothing at all**, because the key is delivered to
that frame's own browsing context and a cross-origin frame cannot forward it.
"Escape dismisses" is not negotiable, so focus now starts on the dialog's
heading, in this document. The frame stays tabbable, deliberately: it is a
scrollable region and removing it from the tab order would make a two-page letter
unreadable by keyboard. The honest statement of the behaviour is that Escape
works from everywhere in the dialog **except while focus is inside the letter
itself**, and one Tab from there reaches "Save it" and "Close", which always
work. Verified tab order: heading → frame → Save → Close.

### 22.5 The other six, checked for the same shape

Asked of every request type: does it produce an artifact a requester can never
see?

| Use case | Artifact | Reachable? |
|---|---|---|
| UC-03 letter | `travel_support_letter` in `documents` | **Now yes** — this section |
| UC-03 informational answer | `travel_informational_response` in `documents` | **Shown once, on the result panel, and never again.** A requester coming back to "My requests" a week later cannot re-read the answer they were given. Reported, not built: it is a different artifact with a different rule (there is nothing to *withhold*, so it needs no delivery gate — only a place to show it) |
| UC-01 verification letter | `employment_verification_letter` in `documents` | Not on this portal, and correctly so — UC-01 has no portal form. Its delivery is the public reply on the customer's own Zendesk ticket, which is where the request came from |
| UC-05 resignation report | **none** — there is no document row. §15 calls the signed-off report "the durable artifact", and that artifact is the RECORD: the notice period, the last day, the payout and the sign-off, all columns on `uc05_resignations` | Yes, already — "My requests" renders every one of them through `resolutionFacts` |
| UC-02, UC-04, UC-07, UC-08, UC-09 | none | Nothing to reach |

So one real gap remains and it is named above rather than fixed here: the
informational answer is written to `documents` and shown once.

## 23. The signature moved to where the risk is (2026-08-20)

**The project owner's decision, in their own words:**

> "For a short business trip where the user is qualified, that should be fully
> automated — no need for anybody to sign. It is only when it is a higher level,
> where things are a bit complex and the legal risk is high, or when the user is
> not qualified by normal standards, that the expert gets to review it. Anything
> that is too risky to decide using deterministic engines, or has legal
> implications or great financial situations, should not be automated — it
> should just go straight [to a human]. Some parts of things that have some
> legal implications, the system can decide and recommend an action to the
> expert, but submit for approval."

That is **prime directive 2 applied to a document rather than to a use case**.
Until this change, every formal travel letter stopped for a signature — the
routine one and the exceptional one alike — which is exactly the flattening the
tier model exists to prevent. A 🟢 use case whose only real product needs a human
every time is a 🟡 use case with a green label on it.

### 23.1 Why §18's finding does not bind here, and is not being dropped

`1e14f46` (§18.1) read Remote's own `TravelLetterRequest` against the primary
source and found the document generated only at `approved_by_remote`, after two
named human approvals, with `UpdateTravelLetterRequestParams` a closed `oneOf`
that no API client can use to reach that state. It concluded the signature should
stay. **That reasoning was correct and it is about a flow this system does not
use.**

UC-03 does not call `POST /v1/travel-letter-requests`. It reads the employment
record and the legal entity and renders **its own** letter from
`renderTravelLetterHtml()`. So there is no platform whose permissiveness this
could exceed: the comparison in §18.1 is between Remote's Request Hub and
Remote's Request Hub. What §18 actually established, and what still stands, is
that a travel letter is **not** the employment-verification letter — different
reader, different assertions, different risk — and therefore that "Remote
self-serves verification letters" was never an argument for self-serving this
one. The argument for issuing it is the one above: it is a routine document for a
qualified traveller on a short trip, and this system holds every fact in it.

Recorded rather than deleted because **a reader who finds `1e14f46` and not this
section will think the gate was removed by accident**, which is the worst
possible reading of a control that disappeared.

### 23.2 What "qualified" is — the ladder, not a new test

Nothing new was invented to define it. Reaching the letter rung at all already
means every one of these held, in this order:

| Rung | What it established |
|---|---|
| 1 | Identity proved against the record Remote returned — never a claim in the ticket |
| 2 | The employment is **active** |
| 3–4 | The reading of the request scored at or above the confidence floor, and the floor was applied to a number that exists |
| 5 | The trip is **business travel**: work-authorisation intent left here for UC-04, so "short business trip" is what a request reaching this rung *is* |
| 6 | A destination country was read |
| 7 | It is not sanctioned or restricted |
| 7b | Remote's country registry was actually **read** — an unread list is not an empty one |
| 8 | The destination is in that registry |
| 9 | The trip's length is computable from two dates |
| 10 | It is inside the duration cap |
| 11 | The letter is the **standard** template: nothing outside it was asked for, and every row it asserts has a value |

**A second, tighter "short trip" number would have been invented, so there is
none.** `DEFAULT_DURATION_CAP_DAYS` (30) is the band this repository already
defines and already defends; "short" is what being inside it means. The
demonstration trip in `test/uc03AutoIssue.test.js` is seven days.

**One rung was checked for the failure shape this repo has paid for twice, and it
is genuinely reachable.** Rung 11's `standard` is the *absence* of findings over
a live scan of the request's own words — `test/uc03LetterScope.test.js`'s leading
test asserts a plain request reaches it, precisely so an over-broad marker cannot
make the issuing path unreachable while every refusal below it still passes.

### 23.3 The rung split three ways, and `formal_letter_requested` changed meaning

| Condition | Decision | Document |
|---|---|---|
| Not the standard template | `escalate` / `letter_scope_exceeded` (rung 11) | **None.** Refusing to *issue* a bad document still leaves it written |
| Standard, but not issuable here | `human_review` / `formal_letter_requested` (rung 12) | Drafted **or** none — see below |
| Standard and issuable | `auto_resolve` / **`standard_letter_issued`** (rung 13) | Written, hashed, stored, delivered |

**Rung 12 is reached two ways and they are opposite jobs**, so the flags say
which:

- **`letterAutoIssue: false`** — a deployment that has chosen to require a
  signature on every travel letter. The letter **is** drafted; the specialist has
  a prepared document to read and sign. This is a policy parameter with the same
  standing as `durationCapDays` and `sanctionedRegions`: nothing in this
  repository sets it, the default is the owner's decision, and it exists because
  a company, a country or a month could each be a reason to want the signature
  back. Turning it on restores the pre-change behaviour exactly.
- **`letterhead_unavailable`** — `getLegalEntity()` returned nothing usable, so
  there is no letterhead. **Nothing is drafted**, and `signoffPolicy.js` refuses
  the case by name (`letter_missing`). The outstanding work is a record fix and a
  re-run, not a signature, and the queue note, the Zendesk note, the decision
  facts and the recommendation all say so before anybody goes looking for a
  document.

Both inputs **default to the cautious answer**: `letterheadAvailable` defaults to
`false` in `evaluate()`'s own signature, so a caller that has established nothing
gets the signature path. **A letter is never issued by omission.**

The letterhead moved from a post-decision read in `workflow.js` STEP 5 to a
pre-decision read in STEP 3b, because it now *selects between two decisions* and
a decision belongs to the gate that owns it — establishing it afterwards would
mean the recorded reason named one rung while a later line changed the outcome.
It is read only when a letter was actually asked for, so the ordinary
informational inquiry still makes exactly the two Remote reads it always did.

### 23.4 The compensation row, re-argued because nobody reads the letter now

Auto-issuing means the document's contents are decided entirely by code, and the
row a person is most likely to object to is their own pay. **It stays**, on three
legs:

1. **It answers the question the letter is offered against.** The Commission's
   Visa Code Handbook I names *means of subsistence* as its own evidential head
   and names a certificate of employment against it (§5.2.2(d)/(e)). Without the
   row the letter answers two of the three heads it is written for. UC-01's
   verification letter is pay-free because pay answers nothing *it* is asked;
   here it answers something specific.
2. **The signature was never a control over it.** On the path this replaces, a
   specialist read the letter and signed — with no gate, no field and no prompt
   asking them to weigh the compensation row, and no outcome available to them
   other than signing a correct standard letter or declining it wholesale.
   Removing them removes a check on the document's *correctness*, which the gates
   and the scope check now do. It does not remove a check on disclosure, because
   there was not one.
3. **A path-dependent body would be two documents wearing one name.** If the
   auto-issued letter dropped a row the signed one carries, an employer could
   hand a consulate two "Travel Letters" asserting different things with nothing
   on either saying which kind it was — and the shorter one would be a silently
   truncated document, which is the exact defect `letterScope.js` exists to
   prevent, arriving from a new direction.

**Pinned in both directions.** `test/uc03AutoIssue.test.js` asserts the issued
letter carries the row at its ×100-scaled value, asserts it is byte-identical to
what `renderTravelLetterHtml()` produces for the same inputs (so no second
renderer can appear), and asserts the signature-required posture produces the
identical bytes — the two paths differ only in who releases it.

**What replaces the signature as the employee's consent**, both of which already
existed and now carry weight they did not before: `describeLetterOffer()`'s
`produces` lists **every row the letter will contain, base compensation named**,
before the accept control; and `letterScope.js`'s `omission_requested` marker
routes *"please leave my salary out"* to a person who writes it by hand. A marker
only fires on an ask, and nobody asks about a row they were never told was there
— which is why the listing is not decoration. It is on the offer rather than in
the informational answer on purpose: that answer's money-free invariant
(`test/uc03.test.js`) is worth more than a second copy of the list, because a
zero-touch reply that has learned to say the word "compensation" is one edit away
from saying a number.

### 23.5 The audit record, which had to become at least as strong as a signature's

A signed letter's row names the approver and the document's sha256. An
auto-issued one has no approver, so the row records **what took that place** — or
an artifact reaches a foreign authority with no accountable origin, which is
worse than one waiting for a signature.

`audit_log.details` on a `standard_letter_issued` decision now carries:

- **`letterIssued: true`** — derived from the deciding **rung**, never from
  `Boolean(letterHtml)` (a draft is also a document) and never from
  `decision === "auto_resolve"` (now reached two ways). For most of this file's
  life the field was the literal `false`.
- **`letterContentHash`** — the sha256 `caseStore.createDocument()` computed.
- **`autoIssue`**: `issuedWithoutSignature: true`, a plain-words `basis`, the
  **twelve rungs that passed** named one at a time with what each checked, the
  rung that decided and how many there are, the **scope verdict in the positive**
  (`standard: true` plus every check that ran), and the document's id and hash.

None of it is re-derived: the ladder is `GATE_SEQUENCE` walked against this
decision's own reason, and the scope object is the one the gate itself consulted.

**And the write became durable on this path only.** `audit.logDurable()` before
the Zendesk delivery, matching `src/uc01/workflow.js`'s rule for an auto-issued
letter: the log has to be durable before the irreversible action, so a failure
refuses the action instead of orphaning it. Every other UC-03 decision keeps its
best-effort write — nothing irreversible follows them, and making a database blip
fail a correctly-refused request is a worse answer than the one it replaced.

### 23.6 What this costs the sign-off surface, said plainly

**On the default posture, no new case reaches a signable state.** A standard
letter for a qualifying trip issues; a non-standard one escalates with nothing
drafted; a letterhead failure lands on rung 12 with nothing to sign, which
`signoffPolicy.js` refuses by name.

So `submitTravelLetterSignoff()`'s success path is now reachable in exactly two
situations: a deployment that sets `letterAutoIssue: false`, and the cases decided
before this change, which are real and which `documents` and `review_queue` still
hold. That is written here, in `signoffPolicy.js`'s own header, and pinned by
tests on both postures — because **a gate whose success path cannot be reached
and a gate being appropriately cautious look identical from outside**, and this
repository has paid for that confusion more than once.

The module is kept rather than deleted for the same reason its refusals are
worded the way they are: the pre-change cases exist, and these sentences are the
only thing that explains them to whoever opens one.

### 23.7 The specialist now gets a recommendation, not only a compiled case

The second half of the owner's statement — *"the system can decide and recommend
an action to the expert, but submit for approval"* — was **not built** before this
pass, and the gap was real. A specialist opening a UC-03 letter case received the
decision slug, the deciding rung in plain words, the whole gate ladder, the
figures each rung compared, the request's own text and the drafted document:
everything needed to *reconstruct* the reasoning, and not one sentence saying what
this system thought should happen.

`recommendLetterAction()` (`src/uc03/signoffPolicy.js`) states the proposal, its
reasons, and **what the reviewer is being asked to confirm that this system could
not** — starting with the one thing the gates cannot see, whether the drafted
document suits the authority that will read it. Three properties, each pinned by
test rather than promised:

1. **It decides nothing.** Pure function over rows, returning prose. The
   structural test asserts only `signoffPolicy.js` and `server.js` name it, and
   that `workflow.js` — where every decision and every write lives — does not
   mention it at all.
2. **It never proposes a click the policy would refuse.** It is computed *from*
   `evaluateLetterActionability()`'s verdict, so an escalation proposes nothing
   and a letter-less case proposes the record fix rather than a signature that
   would 403.
3. **It carries its own cautions.** A recommendation listing only reasons to
   agree is an argument, not advice.

Why this matters beyond politeness: a proposal a reviewer disagrees with is a
**measurable** event — `src/metrics/compute.js` already counts approve/decline
against the automation's recommendation — and a case with no proposal in it can
never disagree with anybody.

### 23.8 Collecting the letter

An issued letter nobody can fetch would be *"correct, durable, audited, reaching
nobody"* in its worst form, because the audit row records a delivery.
`src/uc03/letterDelivery.js` answers "is this the **traveller** the document is
about?" — a different question from `signoffPolicy.js`'s "may this **specialist**
release it?", a different namespace and a different failure if got wrong.

    POST /api/cases/:id/letter    body: {session:{authenticatedEmploymentId}}
    → 200 {ok, caseId, documentId, type, contentType:"text/html", filename,
           contentHash, issuedAt, issuedWithoutSignature, content}
    → 401 session_required · 403 not_the_traveller
    → 404 case_not_found | no_letter_on_this_case · 409 letter_not_issued

Identity is checked **before** the artifact's existence: "no letter on that case"
is itself a fact about somebody else's request. `GET /api/cases/:id` names the
route in a `letter` block and carries the **hash without the bytes** — a
specialist's panel has no business holding an employee's pay.

The portal's own surface for this (`src/portal/letterAccess.js`, §22) calls
`evaluateLetterDelivery()` rather than restating it, so the row and the route are
one verdict and the page structurally cannot offer a save on a letter the fetch
would refuse.

### 23.9 The n8n port, and a redeploy that is owed

`workflows/nodes-uc03/travelRouterGates.js` carries the same three-way rung and
the same fail-closed defaults, with the letterhead read from a
`Fetch Legal Entity (Remote)` node **guarded** — `$()` throws for a node that is
not on the canvas, and the failure resolves to `false`, which is the signature
path. So the deployed graph `WORKFLOW_UC03_ID`, which has no such node, keeps the
behaviour it has today rather than issuing letters on a half-built graph.

**`verify-deployed` read `39 nodes, 0 drifted` before this change and will not
now.** The repo copy is ahead of the deployed body. Republishing it is a separate
unit of work, and it needs the `Fetch Legal Entity (Remote)` node added to the
graph in the same pass — publishing the Code node alone would leave production
permanently on the signature path while the repo, the tests and every reader of
the code agree on something else.
